### 예상 (검증 대상) — W0 는 *어떻게*, *얼마나* 깨지는가

브리프 5.2 는 "W0 가 깨진다" 까지만 적었다. 기전과 규모를 미리 적어 두고 실측과 대조한다.

W0 의 차감은 **더티 체킹**이다 (`IssueCore.DIRTY_CHECKING`). Hibernate 는 읽은 값에 1 을 더한 **절대값**을 쓴다:

```sql
UPDATE coupon SET issued_count = 100 WHERE id = 1   -- 99 를 읽었으면 100 을 쓴다. issued_count + 1 이 아니다
```

한 JVM 안에서는 `ReentrantLock` 이 읽기부터 커밋까지를 직렬화하므로 이 방식이 안전하다. 3 JVM 에서는 **각자 자기 락을 통과한 트랜잭션 셋**이 동시에 같은 행을 읽고 쓴다.

```
JVM1  SELECT → 99 ─ UPDATE SET 100 (행 락 획득) ──────── COMMIT
JVM2    SELECT → 99 ─ UPDATE SET 100 (행 락 대기) ........ 진행 → 100 을 100 으로 덮어쓴다   ← 갱신 손실
JVM3      SELECT → 99 ─ UPDATE SET 100 (행 락 대기) .......... 진행 → 같은 일
결과: coupon_issue 행 +3, issued_count +1
```

PostgreSQL Read Committed 는 락 대기 뒤 최신 행으로 **WHERE 만** 다시 평가한다 (`id = 1` 은 여전히 참). SET 값은 바인딩된 그대로다. `docs/transaction-isolation.md` 1장의 갱신 손실이 **인스턴스 단위로** 재현되는 것이다.

매진 판정은 `issued_count` 로 하므로 **카운터가 100,000 에 닿을 때까지 발급이 계속된다.** 그래서:

| 항목 | 예상 |
|---|---|
| `over_issue` (W0, 3대) | 경계에서 몇 건이 아니라 **수천~수만 건**. 손실률이 L 이면 발급 ≈ 100,000 ÷ (1 − L). L > 1/3 이면 150,000건 **전부** 발급되고 SOLD_OUT 응답이 한 번도 나오지 않는다 |
| `counter_drift` (W0, 3대) | **큰 음수** — 카운터 − 실제 행 = 손실된 UPDATE 수. 이 열이 기전을 직접 보여준다 |
| `duplicate_users` (W0, 3대) | **0** — UNIQUE 가 막는다. 초과는 서로 다른 유저로 일어난다 (브리프 5.4) |
| W1 · W2 · W3 · W4 | 전부 0. W1 은 행 락을 잡은 **뒤에** 읽고, W2 는 조건부 UPDATE 가 손실을 충돌(재시도)로 바꾸고, W3 는 Redis 락이 JVM 사이를 직렬화하고, W4 는 Redis 단일 스레드 안에서 차감한다 |

손실 창은 JVM1 의 UPDATE → COMMIT 구간(INSERT + fsync, 트랜잭션 3.9ms 의 대부분)이다. 셋이 쉼 없이 돌므로 이 창에 다른 JVM 의 SELECT 가 들어갈 확률이 높다. **L 은 작지 않을 것이다** — 이것이 검증 대상이다.

> 예상이 틀리는 경우도 값지다. over_issue 가 0 이면 먼저 **분배**를 의심한다 (nginx 가 한 대에만 보냈는가 — 6장). 셋에 고르게 갔는데도 0 이면 기전 설명이 틀린 것이고, 그것을 적는다.

### 왜 3 고정인가 (2/3/5 가 아니라)

브리프 13장은 "3 고정 vs 2/3/5 로 늘려가며 W0 붕괴 정도 관찰" 을 열어 두었다.

1. **완료 기준과 산출물이 "1대 vs 3대 표" 다** (8장, 10장 3번). NFR-07 도 3대로 정의돼 있다.
2. 1장의 기전대로면 붕괴는 **2대에서 이미 일어나고 규모가 포화**한다. 손실률은 인스턴스 수보다 트랜잭션 겹침 확률에 좌우되므로, 2/3/5 의 차이가 "정도" 를 깨끗하게 보여주지 않을 가능성이 크다.
3. 비용: 인스턴스 수 하나에 15회 ≈ 2.5시간. 셋이면 7.5시간이고, 5대는 인스턴스당 풀 6 이라 W1 의 조건도 달라진다.
4. **선택:** W0 만 2대 1회를 덤으로 돌리면 "첫 걸음부터 깨진다" 는 문장을 얻는다. 정식 표에는 넣지 않고 summary 의 보조 자료로. 비용 10분.

#### [x] 1단계 — 3 인스턴스 스택 ✅ <sub>반나절</sub>

기존 `docker-compose.yml` 은 건드리지 않고 **오버레이 파일** `docker-compose.scale.yml` 을 겹친다. 1단계 명령(`docker compose up -d`)이 그대로 동작해야 한다 (작업 규칙 5).

```
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=2
```

| 구성 | 내용 |
|---|---|
| `nginx` | `nginx:1.27-alpine`, `infra/nginx/nginx.conf`. upstream `server app:8080; server app-worker:8080;` — Docker DNS 가 `app` 을 주소 2개로 풀어 **3대 라운드로빈**. `worker_connections 8192`, upstream `keepalive`, `proxy_read_timeout 120s`, access log off |
| `app` | 호스트 포트 매핑 해제 (`ports: !reset []`, compose v2.38). 3대가 8080 을 나눠 쓸 수 없다. `DB_POOL_SIZE=10`, `COUPON_W4_WORKER=false` |
| `app-worker` | `app` 과 같은 이미지·환경, **`COUPON_W4_WORKER=true` 하나만 다르다.** W4 워커는 한 대만 (D-06) |
| `infra/prometheus/prometheus.yml` | dns_sd names 에 `app-worker` 추가 |
| `PROJECT_BRIEF.md` 5.3 · 7장 · 10장, `docker-compose.yml` 머리말, `prometheus.yml` 주석 | `--scale app=3` 표기 5곳을 확정한 구성(오버레이 + `--scale app=2` + `app-worker`)대로 고친다 |

**W4 워커를 한 대만 돌려야 하는 이유는 "실험 변수가 아니라서" 만이 아니다.** 워커는 큐를 `range` 로 읽고 커밋 뒤 `trim` 으로 지운다. 둘이 돌면 **서로가 아직 처리하지 않은 항목을 지운다** — 유실이다. 앱에 `coupon.w4.worker-enabled` (기본 true → 1단계 무변경) 를 두고 `W4DbSyncWorker` 의 `@ConditionalOnProperty` 조건에 추가한다.

**nginx 는 기동 시점에 DNS 를 푼다.** app 컨테이너를 재생성하면 주소가 바뀔 수 있으므로 러너가 앱 기동 **뒤에** nginx 를 재시작한다.

**검증**
- 3대 기동 후 nginx 로 `POST /issue` 30번 → 응답의 `instance` 가 3종 나온다
- Prometheus targets 에 app 3개 (`app_instance` 라벨 3종)
- 오버레이 없이 `docker compose up -d` → 이전과 동일 (포트 8080/8081 그대로), 15 tests 통과
- 메모리: JVM 3대 × 힙 1GB + PG + Redis 가 Docker VM 11.5GiB 안 — conditions.md 에 실측 기록

`run-experiment.ps1` 에 `-Instances 3` 을 추가한다. **풀 크기는 인스턴스 수에서 계산한다** (30 ÷ N, D-01) — 따로 넘기다 어긋나는 사고를 막는다.

**인스턴스별 처리 건수는 유효성 검사다.** 3대에 고르게 가지 않았다면 그 실행은 3대 실험이 아니다. 각 인스턴스 25% 이상을 기준으로 하고, 어긋나면 결과에 표시한다.

**nginx 가 끼면 5xx 의 출처가 둘이 된다.** 502/504 는 nginx 가 만든다. k6 의 `coupon_server_error` 와 앱 메트릭의 5xx 를 함께 기록해 차이를 남긴다. 2단계는 NFR-04 를 판정하지 않지만, **앱에 닿지 못한 요청이 많으면 경합 조건 자체가 약해진다** — D-09 의 교훈이다.

`run-week3.ps1` — `-Phase stage2 | soak-followup | cache`. **stage2 배치가 끝나면 오버레이 서비스(nginx, app-worker, 추가 replica)를 내린다.** 안 내리면 다음 단일 인스턴스 측정에 app-worker 의 풀 10 이 섞여 커넥션 예산 30 이 깨진다.

**검증** W0 spike 축소 실행 (`-Instances 3 -K6Env VUS=200,TOTAL=20000`) 이 끝까지 돌고 runs.tsv 에 분배가 기록된다. 재고를 넘기지 않으므로 이 실행에서 초과 발급은 나오지 않는다 — **배관 확인용**이다

## 6. 2단계 결과의 유효성 — "3대 실험이었는가"

2주차의 D-09 (spike 요청 4~47% 미도달) 처럼 **측정 배관이 결과를 오염**시킬 수 있다. 3대 실험에서 확인할 것:

2. **도달** — k6 요청 수 = 3대 앱 요청 수 합 (`http_server_requests_seconds_count`) + nginx 5xx
3. **예산** — 3대 풀 합 = 30 (`hikaricp_connections_max` 합)
4. **워커** — W4 에서 `coupon_w4_reflected_total` 이 **한 인스턴스에서만** 는다

1 은 러너가 기록하고, 2~4 는 summary 에서 PromQL 로 확인해 적는다.

## 7. 왜 후반은 덜 자세한가
