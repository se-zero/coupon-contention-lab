## 1. 이 주차가 답하는 질문

> 브리프 2장 1번 — **동시 요청이 늘어날 때 쓰기 경로에서 가장 먼저 포화되는 구간은 어디인가?**
> (락 대기인가, 커넥션 풀 고갈인가, 네트워크 왕복인가)

1주차에 W0로 답의 절반을 얻었다.

| 1주차 관측 (W0, ramp 200→2,000) | 값 |
|---|---|
| 처리량 | **240~270 RPS 로 평평** — 동시성 10배에도 불변 |
| `hikaricp_connections_active` | **1.0 고정** |
| `hikaricp_connections_pending` | **0.0** — 풀은 한 번도 압박받지 않음 |

**락 대기가 먼저 왔고, 커넥션 풀은 놀고 있었다.** 2주차는 나머지 네 전략에서 이 순서가 어떻게 뒤바뀌는지를 본다.

**예상 (검증 대상)** — `pending` 이 0 에서 처음 떠오르는 것은 **W1**. W1 은 락 대기가 DB 안에서 일어나므로 대기 중에도 커넥션을 쥐고 있다.

## 2. 2주차 착수 시점에 확정한 것

| 항목 | 확정 | 근거 |
|---|---|---|
| spike 총 요청 | 1,000,000 → **150,000** (재고 100,000 유지) | 브리프 D-02 개정 |
| soak 측정 범위 | 5전략 **1회 스크리닝** → 징후 있는 전략만 3회 | 브리프 D-05 |
| 2주차 문서 | 트랜잭션·격리 수준 / 비관적 락 / 낙관적 락 / 분산 락 / Redis Lua | — |

### 왜 spike 를 줄였는가

1주차 실측 **W0 = 256 RPS** 기준으로 계산하면:

| 구간 | 건수 | 시간 |
|---|---|---|
| 재고 소진까지 | 100,000 | 6.5분 |
| 그 뒤 "품절" 응답 반복 | 900,000 | **58.5분** |

**58분 동안 같은 답만 반복한다.** 단일 행에 걸리는 경합의 세기는 총 요청 수가 아니라 **동시 VU 수**(1,000 유지)가 정하므로, 꼬리를 잘라도 경합 조건은 그대로다. NFR-04(소진 후 5xx 0건)는 50,000건이면 충분히 판정된다.

> 지금이 바꿀 수 있는 마지막 시점이었다. 정식 spike 측정을 한 적이 없어 폐기할 측정치가 없다. 한 번이라도 측정한 뒤에 바꾸면 브리프 5.3 의 "변경 시 전부 재측정" 규칙에 걸린다.

### [ ] 1단계 — 📄 트랜잭션과 격리 수준 <sub>반나절</sub>

W1·W2 **둘 다의 전제**이므로 개별 전략 문서보다 앞에 둔다.

- 왜 `SELECT` 후 `UPDATE` 가 안전하지 않은가 (갱신 손실)
- 격리 수준 4단계와 **PostgreSQL 이 실제로 하는 일** (기본 Read Committed, MVCC)
- 격리 수준을 올려도 이 문제가 풀리지 않는 이유 → 그래서 락이 필요하다

**산출물** `docs/transaction-isolation.md`
**검증** 7번 "이 프로젝트에서" 섹션이 W1/W2 로 채워진다 (docs 규칙 2)

### [ ] 2단계 — 테스트 골격을 전략별로 확장 <sub>2시간</sub>

### [ ] 3단계 — 📄 비관적 락 → **W1 구현** <sub>반나절</sub>

`SELECT ... FOR UPDATE` 로 쿠폰 행을 잠근 뒤 차감.

**관전 포인트 — W0 와의 결정적 차이**

| | 락이 있는 곳 | 대기 중 커넥션 |
|---|---|---|
| W0 | JVM 안 (`ReentrantLock`) | **점유 안 함** — 락을 잡은 뒤 커넥션을 얻음 |
| W1 | DB 안 (행 락) | **점유함** — 커넥션을 얻고 트랜잭션을 연 뒤 락을 기다림 |

**산출물** `docs/pessimistic-lock.md`, `W1PessimisticLockStrategy.java`
**검증** `W1ConcurrencyTest` 통과

### [ ] 4단계 — 📄 낙관적 락 → **W2 구현** <sub>하루</sub>

`Coupon` 에 `@Version` 을 둘 수 없다. JPA 낙관적 락이 전 전략에 암묵 적용되면 W0 의 다중 인스턴스 붕괴가 가려진다 (브리프 5.2).

**채택 방식 — 조건부 UPDATE**

```sql
UPDATE coupon SET issued_count = issued_count + 1, version = version + 1
WHERE id = :id AND version = :version
```

영향 행 수 0 → 충돌 → 재시도. `version` 컬럼은 테이블에 두되 `@Version` 으로 매핑하지 않는다.

- 다른 전략에 영향 0
- SQL 이 그대로 드러나 리포트에 싣기 좋다
- 재시도 횟수를 직접 셀 수 있다 (브리프 7장 "커스텀 카운터: 재시도 횟수")

**예상 결과** 이 실험은 **쿠폰 행 하나**를 전원이 경합한다. 낙관적 락이 잘 맞는 조건의 정반대다. 재시도 폭주로 처리량이 W0 보다 낮게 나올 수 있다. 이는 실패가 아니라 **"낙관적 락을 여기에 쓰면 안 되는 이유"의 증거**다.

**결정 필요** 재시도 한계 N (4장 참조)

**산출물** `docs/optimistic-lock.md`, `W2OptimisticLockStrategy.java`, `version` 컬럼, 재시도 카운터
**검증** W2 통과 **+ W0/W1 이 여전히 통과** ← 낙관적 락이 다른 전략에 새지 않았다는 증거

---

### [ ] 5단계 — 📄 분산 락 → **W3 구현** <sub>하루</sub>

Redisson `RLock` 으로 임계 구역 보호 후 DB 차감. Redis 의존성이 처음 들어온다.

**이 전략의 위치** W0 와 한 쌍이다 (브리프 5.2). 단일 인스턴스에서 W3 는 Redis 왕복만큼 느릴 뿐이라 **근거 없이 느린 선택지처럼 보인다.** 3주차에 W0 가 깨지는 순간 이 오버헤드가 정당화된다. 2주차는 그 대비의 앞쪽 절반을 채우는 일이다.

**주의** `leaseTime` 을 짧게 잡으면 트랜잭션이 끝나기 전에 락이 만료되어 정합성이 깨진다. 이건 관측 대상이 아니라 **버그**다.

**결정 필요** 락 대기 타임아웃과 초과 시 응답 (4장 참조)

**산출물** `docs/distributed-lock.md`, `W3DistributedLockStrategy.java`, Redisson 의존성, 테스트용 Redis 컨테이너
**검증** `W3ConcurrencyTest` 통과

### soak 판정 규칙 (D-05)

| 1회 결과 | 조치 |
|---|---|
| 처리량 곡선이 평평 | 그대로 "열화 없음" 기록 |
| 우하향 또는 애매 | **그 전략만 3회를 채워 결론** |

3회 반복의 목적은 **숫자의 편차** 확인인데, soak 에서 보는 것은 값이 아니라 **곡선의 모양**이다. 30분 내내 평평한 곡선이 우연히 나오지는 않는다. 잘못 넘어갈 수 있는 쪽(우하향)에만 비용을 쓴다.

## 6. 왜 측정을 마지막에 한 블록으로 하는가

전략을 하나 만들 때마다 바로 측정하지 않는다.

W1~W4 는 `IssueCore` 등 **공통 코드를 함께 쓴다.** W1 을 2일차에, W4 를 6일차에 측정했는데 그 사이 공통 코드가 한 줄이라도 바뀌면 **두 측정은 서로 다른 프로그램을 잰 것**이 된다.

> 브리프 7장 — 모든 비교군은 **동일한 하드웨어, 동일한 DB 커넥션 총량, 동일한 데이터 볼륨**에서 측정한다

`runs.tsv` 에 커밋 해시를 기록하는 이유가 이것이다. **전 전략을 같은 커밋 하나로 측정해야 비교가 성립한다.**

## 7. 왜 문서를 전략 구현 직전에 쓰는가

문서 5개를 먼저 몰아 쓰지 않는다. 각 전략마다 **아직 정하지 않은 것**이 하나씩 붙어 있고(4장), 문서를 쓰는 과정이 곧 그 결정의 근거를 만드는 과정이기 때문이다.

몰아 쓰면 구현 전 추측으로 쓰게 되고, 구현하면서 틀린 것을 발견해 다시 고치게 된다.
