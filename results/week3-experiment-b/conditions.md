# 측정 조건 — 3주차 후반 (실험 B, 캐시 C0~C4)

> 5개 읽기 전략(C0~C4)을 **단일 인스턴스**에서 같은 읽기 부하로 돌리고, **TTL 만료 순간의 DB 조회 피크값**을 잰다.
> 정합성은 판정하지 않는다 — 부하에 쓰기 요청이 없다. 비교군 간 차이는 오직 캐시 전략뿐이어야 한다 (브리프 5.4).

> 배경 개념은 [`docs/cache-basics.md`](../../docs/cache-basics.md) · [`docs/cache-stampede.md`](../../docs/cache-stampede.md).
> 예상값은 `cache-stampede.md` 7장에 **측정 전에** 적어 두었다.

## 시드

실험 A 의 `seed/seed.sql` 은 **건드리지 않는다.** 러너가 `reset.ps1`(쿠폰 1·2 재주입) 뒤에 `seed/seed-cache.sql` 을 따로 적용한다. 실험 A 의 시드가 달라지면 이미 끝난 측정과 비교 조건이 깨지고 `verify.sql` 의 출력 행 수도 바뀐다.

| 쿠폰 | id | 용도 |
|---|---|---|
| `spike-coupon` · `sustained-coupon` | 1 · 2 | 실험 A 시드 그대로. **2 는 JIT 워밍업 대상** |
| `cache-coupon-01` ~ `cache-coupon-20` | **101~120** | 실험 B 측정 대상 20개 키 (D-12) |

`issued_count` 를 키마다 다르게 넣는다(`(id − 100) × 137`). **응답이 키마다 달라야 캐시가 키를 섞지 않는지 확인된다.**

## 부하 설정 (`loadtest/scenarios/stampede.js`)

| 구간 | 설정 | 대상 | 의도 |
|---|---|---|---|
| `jit` | 20 VU, 30초 | **쿠폰 2** | JVM·JIT·커넥션 풀 워밍업. **측정 대상 20개 키는 일부러 건드리지 않는다** — 여기서 캐시가 채워지면 TTL 시계가 30초에 걸쳐 흩어져 동시 만료가 깨진다 |
| `warm` | 1 VU × 20회, `startTime` 35초 | 키 101~120 각 1회 | 20개 키를 한꺼번에 채운다. 1 VU 라 수백 ms 안에 끝나 **TTL 시계가 거의 같은 순간에 시작**한다 |
| `measure` | **200 VU** constant, **5분**, `startTime` 40초 | 20개 키 균등 랜덤 | 측정 구간 |

만료 파동은 측정 구간(40~340초) 안에 **60초 간격으로 5회** 온다 (35 + 60 = 95초부터).

**총 15회** — C0~C4 각 3회. C2~C4 는 9단계에서 구현한 뒤 측정한다.

## 무엇을 보는가 (판정 아님)

| 지표 | 어디서 |
|---|---|
| **TTL 만료 순간의 DB 조회 피크값** ← 핵심 | `series/<tag>.tsv` 의 `db_load_per_s` 최대값, `runs.tsv` 의 `peak_db_load` |
| 히트율 | `runs.tsv` 의 `hit_ratio` — **다섯 전략 모두 99% 대라 변별력이 없을 것이다** (`cache-stampede.md` 3-5) |
| 미스 창 (DB 를 읽는 데 걸린 시간) | `series` 의 `load_sum_delta` ÷ `load_count_delta` — **구간을 잘라서** 본다 (한계 4) |
| C3 의 대기 비용 | `series` 의 `wait_*`, `runs.tsv` 의 `wait_mean_ms` · `wait_timeout` |
| 응답 시간 P99 | `runs.tsv` 의 `k6_p99_ms` — 참고값. **전체 P99 로는 C3 의 대가가 안 보인다** (`cache-stampede.md` 7장) |

## 실행의 유효성 — "제대로 잰 실험이었는가"

측정 배관이 결과를 오염시킨 전례가 있다 (2주차 한계 10, 3주차 `app_5xx`). 실행마다 확인한다.

| 확인 | 기준 |
|---|---|
| 도달 | `hit + miss` = k6 요청 수 |
| 미스 경로 | `load_count` = `db_load` (러너가 다르면 경고한다) |
| C1 · C2 | `miss` = `db_load` — 미스가 전부 DB 로 간다. **C3 · C4 에서 갈라지는 것이 관측 포인트**다 |
| 적용 확인 | 메트릭 공통 태그 `cache="C1"` 이 요청한 전략과 같다 (러너가 다르면 throw) |
| 교차 확인 | `series` 의 `load_count_delta` 총합 = `runs.tsv` 의 `load_count` |
| 5xx | `coupon_read_error` 0건 |

## 알려진 한계

1. **동시 만료가 인위적으로 정렬돼 있다.** `warm` 이 20개 키의 TTL 시계를 같은 순간에 시작시킨다. 실제 서비스는 키가 시간에 걸쳐 채워져 **자연 지터**가 있으므로, C1 의 피크는 최악값이고 **C2(지터)의 개선 폭은 실제보다 크게 보일 수 있다.**
2. **닫힌 루프 부하다.** k6 의 VU 는 응답을 받아야 다음 요청을 보내므로 원본이 느려질수록 유입이 줄어든다. 그래서 `cache-stampede.md` 1장의 악순환(느려질수록 더 몰림)은 **재현되지 않는다.** 다만 VU 가 매 반복 키를 새로 뽑으므로 키당 동시 미스의 실제 상한은 VU 수가 아니라 **미스 창의 길이**가 정한다.
3. **무효화 스탬피드는 보지 않는다.** 실무에서 더 흔한 쪽이지만, 쓰기를 섞으면 피크의 원인이 만료인지 무효화인지 분리되지 않는다 (`cache-basics.md` 3-2).
4. **`runs.tsv` 의 `load_mean_ms` 는 전 구간 평균이라 콜드 스타트가 섞인다.** `jit`·`warm` 의 첫 DB 읽기 40건은 JIT 미완료·커넥션 첫 생성 때문에 건당 수백 ms 다 (스모크 실측: `jit` 308ms/건, `warm` 11ms/건). 파동 구간의 값을 보려면 **`series` 에서 해당 초만 잘라** 계산한다.
5. **피크의 지속 시간은 보이지 않는다.** 스크레이프가 1초라 1초 버킷 안의 **총량**만 남는다. 스크레이프 지터로 한 초가 비고 다음 초에 두 배로 잡힐 수 있으므로, 단일 실행의 피크값보다 **3회 반복의 평균과 편차**를 본다.
6. **`cache` 공통 태그가 모든 메트릭에 붙는다.** 실험 A 를 다시 돌리면 그 메트릭에도 `cache="C0"` 이 붙는다. 값이 붙을 뿐 기존 라벨은 그대로이고, 판정에는 영향이 없다.
7. 2주차 한계 1 · 2 · 4 (로컬 환경, k6 동거, 컨테이너 자원 무제한)는 그대로다.

## 측정에 쓴 커밋

전 전략을 **같은 커밋 하나**로 측정한다. `runs.tsv` 의 `commit` 열이 전부 같은지, `-dirty` 가 없는지 확인한다.

> 8단계 스모크(C1 1회)는 배관 검증이므로 **결과를 폐기했다.** 확인한 값은 `plan/week3.md` 9장 진행 기록에 남겼다.
