## 2. W0 기준선 관측

> **정식 측정이 아니다.** 3회 반복(브리프 7장)을 하지 않았고 요청 수도 축소했다.
> 2주차에 `run-experiment.ps1` 로 다시 측정한다. 여기서는 **경향만** 기록한다.

### 2-1. ramp — 동시성 200 → 2,000

총 147,940 요청 / 10분 15초. Prometheus 30초 간격 샘플에서 관측한 값:

| 지표 | 관측 |
|---|---|
| 발급 처리량 | **240 ~ 270 RPS 로 평평** — 동시성이 10배 올라도 늘지 않음 |
| HikariCP `active` | **1.0 고정** |
| HikariCP `pending` | **0.0** — 풀이 한 번도 압박받지 않음 |
| 커넥션 홀딩 시간 | 약 3.5 ms |
| P99 (k6, 클라이언트) | 1.77 s → **9.92 s** |
| 5xx | **0건** |

**해석.** W0 는 `ReentrantLock` 하나로 임계 구역을 감싸므로 어느 순간에도 트랜잭션이 1개만 실행된다.
`active = 1.0` 이 그 직접 증거다. **커넥션 풀 30 은 W0 에서 아무 역할도 하지 않는다.**

따라서 W0 로는 "풀이 언제 고갈되는가"를 관측할 수 없다. 브리프가 W0 를
**"락 오버헤드의 하한선 참고값"** 으로 규정한 이유가 수치로 확인된 셈이다.
풀 포화(`pending` 상승)는 W1 에서 처음 나타날 것으로 예상한다.

### 2-2. spike — 동시성 200, 20,000 요청

| 지표 | 값 |
|---|---|
| 처리량 | 256 RPS |
| 평균 응답 시간 | 778 ms |
| 역산한 직렬 구간 `t` | **3.9 ms** |

세 값이 서로 검증된다.

```
200 VU ÷ 0.778 s = 257 RPS   ≈ 실측 256
1 ÷ 256          = 3.9 ms    (직렬 구간)
200 × 3.9 ms     = 780 ms    ≈ 실측 778
```

응답 시간 778 ms 중 **실제 일한 시간은 3.9 ms 이고 나머지 774 ms 는 대기**다.

## 3. 구축 과정에서 발견해 고친 것

| 문제 | 영향 | 조치 |
|---|---|---|
| actuator 가 워크로드와 톰캣 스레드 풀 공유 | 포화 순간에 스크레이프가 타임아웃되어 **가장 필요한 구간의 메트릭이 유실** | 관리 포트 8081 분리 (7.6 s → 41 ms) |
| 매핑 없는 경로가 500 반환 | 오타 하나로 5xx 가 찍혀 **NFR-04 판정 오염** | `NoResourceFoundException` 핸들러 추가 |
| `gradle-wrapper.jar` 가 `.gitignore` 에 걸림 | 클론 후 빌드 불가 | 예외 규칙을 `*.jar` 뒤로 이동 |
| `gradlew` 가 CRLF 로 체크아웃 | 리눅스 컨테이너에서 실행 불가 | `.gitattributes` 추가 |
| 리셋 없이 k6 2회 실행 | 같은 `user_id` 재사용으로 결과 오염 | `run-experiment.ps1` 로 절차 자동화 |

## 4. 이 폴더의 raw / log / integrity 파일에 대하여

이 주차의 `W0-spike-run1.*` 은 **측정 결과가 아니라 `run-experiment.ps1` 의 동작 검증 산출물**이다.
(`VUS=50`, `TOTAL=2000` 축소 실행, 3회 반복 없음)

파일 형식의 실물 예시로 남겨 둔다. 실제 측정은 2주차 폴더부터 시작한다.

검증된 것: 전략 적용 → 앱 재기동 → **적용 전략 확인** → DB/Redis 초기화 → k6 → `verify.sql` → 결과 저장이
한 커맨드로 순서대로 실행되고, 임계값 미달(k6 exit 99)과 실행 실패를 구분한다.

## 5. 2주차로 넘기는 것

- **`synchronous_commit` 은 `on` 유지.** 락을 커밋까지 쥐는 W0/W1/W3 에서는 fsync 가 직렬화되고, W2/W4 에서는 group commit 이 이를 분산시킨다. 이 비대칭은 노이즈가 아니라 실험 A 가 드러내야 할 차이다.
- **NFR-03 판정은 k6 기준.** Grafana 응답 시간 패널은 서버 처리 구간만 재므로 판정에 쓰지 않는다.
- 예상: W1 에서 `hikaricp_connections_pending` 이 0 에서 처음 떠오른다. 이 예상이 맞는지가 2주차의 관전 지점이다.
