## 알려진 한계

1. **로컬 Docker 환경이므로 절대 수치는 실제 서비스와 다르다.** 특히 WSL2 가상화 계층을 거치는 커밋 fsync 가 서버급 NVMe 보다 느리다. 의미가 있는 것은 비교군 간의 상대적 차이와 꺾이는 지점이다. (브리프 3.4)
2. **k6 를 부하 대상과 같은 Docker VM 안에서 돌린다.** 부하 생성기가 CPU 를 나눠 쓰므로 최대 처리량이 다소 낮게 나온다.
3. **Grafana 의 응답 시간 패널은 서버 처리 구간만 잰다.** Micrometer 타이머는 요청이 톰캣 워커 스레드에 배정된 뒤부터 시작하므로 스레드 대기 큐 시간이 빠진다. 1주차에 같은 실행에서 k6 P99 9.92초 / Prometheus P99 2.46초로 갈렸다. **NFR-03 판정은 k6 결과로 한다.** (브리프 3.3 의 측정 방법과 일치)
4. 컨테이너에 CPU·메모리 제한을 걸지 않았다. 같은 호스트에서 순차 측정하므로 비교군 간 조건은 동일하지만, 호스트에서 다른 작업이 돌면 영향을 받는다. **측정 중에는 다른 작업을 하지 않는다.**
5. **chaos 의 kill 시점은 1초 폴링이다.** 발급 50,000건에서 죽이지만 실제로는 50,000 + 1초분(W4 는 수천 건)에서 죽는다. 실제 값은 `log/<tag>.chaos.txt` 에 기록된다. 정전 길이도 10초 + docker 명령 지연(약 2~3초)이다.
6. **Redisson 은 Redis 가 죽으면 기본 설정으로 재시도한다** (타임아웃 3초 × 재시도 3회). 정전 구간의 요청 대부분은 5xx 가 아니라 **최대 10초 안팎 멈췄다가 재시작 후 성공**한다. 재시도 예산을 넘긴 일부만 5xx 다. 정전은 그래프에서 에러 구간이 아니라 **지연 구간**으로 보인다.
7. **ramp · soak 의 `k6_issued − db_rows` 는 음수가 나온다.** 부하가 끝날 때 k6 가 줄 서 있던 요청을 끊는데, 서버는 이미 받은 요청을 끝까지 처리해 커밋한다. k6 는 응답을 못 받아 발급으로 세지 않는다. 직렬 전략일수록 끊기는 순간 줄이 길어 차이가 크다 (사전 실행 W0: −865). 정해진 건수를 다 채우는 spike · chaos 에서는 0 이어야 하며, **음수 차이는 정합성 문제가 아니다.** W3 는 3초 락 대기 한계에서 포기하므로 0 에 가깝다.
8. **Prometheus 에서 전략별 합계를 낼 때는 실행 시간 창으로 자른다.** `strategy` 라벨만으로 합치면 같은 전략의 이전 컨테이너(사전 실행, 스모크)가 섞인다. `runs.tsv` 의 `timestamp` + `elapsed_s` 로 창을 잡거나 `app_instance` 로 구분한다.
9. **W4 는 DB 반영이 비동기다.** 부하 종료 직후에 `verify.sql` 을 돌리면 아직 반영되지 않은 건이 "미달 발급"으로 보인다. `run-experiment.ps1` 이 큐(`coupon:w4:queue`)가 빌 때까지 기다린 뒤 판정하며, **그 대기 시간을 `runs.tsv` 의 `reflect_wait_s` 열에 기록한다** (1초 단위 폴링이므로 그만큼의 오차가 있다). 부하 중 큐가 쌓이는 곡선은 `coupon_w4_queue_size` 로 본다.

10. **k6 를 호스트에서 돌리면 안 된다 — Docker Desktop 포트 프록시.** 첫 정식 측정(2026-09-13 밤, 41회)은 호스트 k6 로 `localhost:8080` 을 때렸고, spike 요청의 **4~47% 가 앱에 닿지 못했다** (`http_req_failed` 가 5xx 보다 훨씬 컸고, 앱 메트릭의 요청 수가 k6 의 요청 수보다 그만큼 적었다). 원인 확인 실험(W0, 1,000 VU, 30,000건, 같은 k6 1.6.1): 호스트 k6 → 연결 실패 786건, 전부 `connectex: actively refused`, 전부 spike 시작 순간 2초 안 / 컨테이너 k6(compose 네트워크) → **0건**, 처리량 228 → 302 RPS. 1,000 VU 가 동시에 연결을 여는 순간 Windows 쪽 프록시가 일부를 거부하고, 거부된 VU 가 즉시 다음 반복을 열어 연쇄된다. ramp 는 20초에 걸쳐 올라가 걸리지 않았다. 그 41회는 `results/week2-experiment-a-proxy/` 에 조건을 밝혀 보관하고, 정식 측정은 컨테이너 k6 로 다시 했다.

11. **`W4 / soak / 1` 한 건은 후반부를 수동으로 마무리했다.** `run-experiment.ps1` 의 W4 반영 대기 상한이 30분이었는데 실제로 39분이 걸려, 스크립트가 30분에서 무효를 선언하고 판정·기록 단계를 건너뛰었다. 부하와 반영은 정상적으로 끝났으므로(워커가 계속 돌아 12:23:11 에 큐가 비었다) 같은 앱 컨테이너·같은 DB 상태에서 **스크립트가 실행했을 명령 그대로** `verify.sql` 과 앱 로그 요약을 돌리고 `runs.tsv` 한 줄을 채웠다. 다른 40 건과 다른 점은 두 가지뿐이다.

    - `reflect_wait_s` **2345** 는 스크립트의 1초 폴링이 아니라 **Prometheus 시계열**(5초 간격)에서 산출했다 — 발급이 멈춘 11:44:06 부터 `coupon_w4_queue_size` 가 0 이 된 12:23:11 까지.
    - `elapsed_s` **1846.4** 는 래퍼의 스톱워치가 아니라 **파일 타임스탬프**(k6 로그 생성 → 요약 JSON 기록)다. 나머지 네 soak 행에서 이 값은 래퍼 값보다 약 1.1초 작았다.

    이 상한은 3주차를 위해 90분으로 올렸다 (이 측정 **뒤에** 별도 커밋).
