> 5개 전략(W0~W4)을 **인스턴스 3대**에서 spike 부하로 돌리고 **정합성만** 센다.

> nginx 버전과 메모리는 1단계(3대 스택 검증)에서 실측했다. 측정 착수(4단계) 시점에 각 버전을 다시 확인한다.

## 실행의 유효성 — "3대 실험이었는가"

측정 배관이 결과를 오염시킨 전례가 있다 (2주차 한계 10). 실행마다 확인한다.

| 확인 | 기준 | 어디서 |
|---|---|---|
| 분배 | 인스턴스별 처리 건수 각 25% 이상 | `runs.tsv` 의 인스턴스별 건수 열 (러너가 기록) |
| 도달 | k6 요청 수 = 3대 앱 요청 수 합 + nginx 5xx | Prometheus `http_server_requests_seconds_count`, k6 요약 |
| 예산 | `hikaricp_connections_max` 3대 합 = 30 | Prometheus |
| 워커 | `coupon_w4_reflected_total` 이 한 인스턴스에서만 증가 | Prometheus |

기준에 어긋난 실행은 summary 에 표시하고 3회 평균에서 뺀다.

## 알려진 한계

1. **1대 열은 재측정하지 않는다.** 1대 vs 3대 표의 1대 값은 `results/week2-experiment-a/integrity/*-spike-*` 15건이다. 코드가 같아야 비교가 성립하므로, 이 측정의 커밋과 `fff48c3` 사이의 `app/` · `loadtest/` 차이는 W4 워커 토글뿐이어야 한다. `git diff` 로 확인해 summary 에 적는다.
2. **nginx 가 요청 경로에 하나 더 있다.** 응답 시간·처리량은 1단계와 비교할 수 없다. 성능을 보지 않으므로 문제가 아니지만, nginx 가 만드는 502/504 는 앱 5xx 와 출처가 다르다. k6 `coupon_server_error` 와 앱 메트릭의 5xx 를 함께 기록해 차이를 남긴다.
3. **JVM 3대가 CPU 8개를 나눠 쓰고, 톰캣 스레드는 합계 600 이다.** 1단계보다 인스턴스당 자원이 적고, 앱 안에서 줄 서는 요청은 줄어든다. 정합성 판정에는 영향이 없고 성능은 비교하지 않는다.
4. **nginx 는 기동 시 DNS 를 푼다.** app 컨테이너를 재생성한 뒤 nginx 를 재시작하지 않으면 죽은 주소로 보낸다. 러너가 앱 기동 뒤에 nginx 를 재시작한다. 위의 분배 확인이 이것을 잡는다.
5. 2주차 한계 1 · 2 · 4 · 5 · 9 (로컬 환경, k6 동거, 무제한 컨테이너, 1초 폴링, W4 반영 대기) 는 그대로다.
