## 2. W0 는 어떻게 깨졌는가

### 숫자

| | run1 | run2 | run3 | 평균 |
|---|---|---|---|---|
| 실제 발급 행 (`actual_rows`) | 150,000 | 150,000 | 150,000 | **150,000** |
| 재고 (`total_quantity`) | 100,000 | 100,000 | 100,000 | 100,000 |
| **초과 발급** (`over_issue`) | **50,000** | **50,000** | **50,000** | **50,000** |
| 카운터 (`counter_value`) | 50,874 | 50,614 | 50,668 | 50,719 |
| **카운터 불일치** (`counter_drift`) | −99,126 | −99,386 | −99,332 | **−99,281 ± 137** |
| 품절 응답 | 0 | 0 | 0 | **0** |
| 중복 발급 | 0 | 0 | 0 | 0 |

### 기전 — `counter_drift` 가 직접 보여준다

W0 의 차감은 더티 체킹이다. Hibernate 는 읽은 값에 1 을 더한 **절대값**을 쓴다.

```sql
UPDATE coupon SET issued_count = 100 WHERE id = 1   -- 99 를 읽었으면 100. issued_count + 1 이 아니다
```

한 JVM 안에서는 `ReentrantLock` 이 읽기부터 커밋까지를 직렬화하므로 안전하다. 3 JVM 에서는 **각자 자기 락을 통과한 트랜잭션 셋**이 같은 행을 동시에 읽고 쓴다. PostgreSQL Read Committed 는 행 락 대기 뒤 `WHERE` 만 다시 평가하고 `SET` 값은 바인딩된 그대로 쓰므로, 뒤에 쓴 둘이 앞의 값을 덮는다.

```
JVM1  SELECT → 99 ─ UPDATE SET 100 (행 락 획득) ──── COMMIT
JVM2    SELECT → 99 ─ UPDATE SET 100 (대기) ......... 100 을 100 으로 덮는다   ← 갱신 손실
JVM3      SELECT → 99 ─ UPDATE SET 100 (대기) ....... 같은 일
결과: coupon_issue 행 +3, issued_count +1
```

**`counter_drift` −99,281 이 그 손실량이다.** 150,000장이 나갔는데 장부에는 50,719장으로 적혀 있다. 손실률 **66%** — 세 번의 차감 중 둘이 사라졌다. 매진 판정은 장부(`issued_count`)로 하므로, 장부가 100,000 에 닿기 전에 요청 150,000건이 먼저 바닥났다. 그래서 **품절 응답이 한 번도 나가지 않았다.**

### 3회가 똑같이 50,000 인 것은 우연이 아니다

재고 100,000 에 요청 150,000 이므로 **초과 발급의 천장이 50,000** 이다. 손실률이 1/3 을 넘으면 요청이 전부 발급되고 초과는 자동으로 50,000 이 된다. 실측 66% 는 그 두 배다.

즉 이 값은 붕괴의 **크기**가 아니라 **천장에 닿았다는 사실**을 뜻한다. 요청이 더 많았다면 더 나갔다. 계획서 1장이 "L > 1/3 이면 150,000건 전부 발급" 으로 예측한 구간에 정확히 들어왔다.

## 3. 정합성을 지킨 것과 제 역할을 한 것은 다르다

측정 구간 150,000건이 각각 어떤 응답을 받았는지 (3회 평균).

| 전략 | 쿠폰 받음 | 품절 안내 | 5xx | 재시도 포기 (409) | 소요 |
|---|---|---|---|---|---|
| W0 | **150,000** ← 재고 초과 | 0 | 0 | 0 | 7.6분 |
| W1 | **100,000** 완판 | 21,408 ± 9,034 | **28,592 ± 9,034** | 0 | 10.2분 |
| W2 | **29,336 ± 489** | 0 | **75,527 ± 2,660** | 45,137 ± 2,416 | 13.4분 |
| W3 | **87,241 ± 1,798** | 0 | **62,768 ± 1,795** | 0 | 10.6분 |
| **W4** | **100,000** 완판 | **50,000** | **0** | 0 | **1.9분** |

> 합이 150,000 에서 ±10 어긋나는 행이 있다. 5xx 는 k6 카운터라 워밍업 구간 몇 건이 섞인다. 발급 수는 `integrity` 의 `spike-coupon` 행 수이므로 워밍업이 섞이지 않는다.

### 1대보다 나빠졌다

| 전략 | 1대 발급 (2주차) | 3대 발급 | 변화 |
|---|---|---|---|
| W1 | 100,000 | 100,000 | 완판 유지, 그러나 5xx 가 **12건 → 28,592건** |
| W2 | 58,582 ± 1,405 | **29,336 ± 489** | **절반으로 감소** |
| W3 | 100,000 | **87,241 ± 1,798** | 완판 실패 |
| W4 | 100,000 | 100,000 | 변화 없음, 5xx 0 유지 |

원인은 **커넥션 예산의 분할**이다. 총량 30 을 고정했으므로(D-01) 인스턴스당 풀은 10 이 된다. 반면 요청을 받는 톰캣 스레드는 인스턴스마다 200, 합계 **600** 이다. 1대에서는 풀 30 뒤에 200 이 줄을 섰지만, 3대에서는 풀 10 뒤에 200 이 줄을 선다. 커넥션을 쥔 채 락을 기다리는 전략일수록 `connection-timeout` 3초에 걸리는 요청이 급증한다.

**5xx 의 성격은 전략마다 다르다.**

- **W1** `CannotCreateTransactionException` — HikariCP 3초 타임아웃. 트랜잭션조차 열지 못했다. 앱 로그 요약에 그대로 남는다.
- **W2** `CannotCreateTransactionException` + 재시도 한계 초과 409. 재시도가 커넥션을 다시 잡으므로 압박이 배가된다. 재고 70,000장을 남기고 끝났다.
- **W3** 503 `LOCK_TIMEOUT` — 락 대기 3초를 넘겨 **의도적으로** 돌려준 응답이다. 예외가 아니라 정상 경로라 앱 로그 요약(`log/*.app.txt`)에는 0~2건으로만 잡힌다. Prometheus 에서 확인한 앱 5xx 는 k6 와 정확히 일치한다 (5장).
- **W4** 0건. 요청 경로에 DB 가 없어 풀 분할의 영향을 받지 않는다.

> W1 의 5xx 편차가 크다 (39,019 / 23,109 / 23,649). 1회차만 높은 것은 2주차에서도 관측된 배치 첫 실행의 콜드 효과로 보인다 (2주차 summary 4장).

## 4. W3 의 정당화 — 이 실험의 목적

2주차 결론은 이랬다.

> **W3 는 이 표에서 가장 억울한 전략이다.** W0 보다 느리고 NFR-04 도 놓쳤는데, 단일 인스턴스에서는 얻는 게 없다.

3대에서 그 대비가 완성된다.

| | 1 인스턴스 | 3 인스턴스 |
|---|---|---|
| W0 | 정합성 유지, W3 보다 23% 빠름 | **초과 발급 50,000건 — 쓸 수 없다** |
| W3 | 정합성 유지, W0 보다 23% 느림 | 정합성 유지 |

**W0 대비 23% 의 오버헤드는 "인스턴스를 늘릴 수 있는 권리" 의 값이었다.** 단일 인스턴스 그래프만 보면 살 이유가 없는 보험이고, 서버를 한 대 더 늘리는 순간 유일한 선택지가 된다. 브리프 5.2 가 설계한 대비가 이것이다.

**다만 정당화되는 것은 정합성뿐이다.** 3대의 W3 는 재고 100,000장 중 87,241장만 팔고 62,768명에게 503 을 돌려줬다. "정합성을 지키는 분산 락" 과 "쓸 만한 분산 락" 은 다른 문제이며, 후자는 락 대기 한계·커넥션 예산·재시도 정책을 다시 잡아야 한다. 이 실험의 범위 밖이다.

## 5. 실행의 유효성 — "3대 실험이었는가"

2주차에 측정 배관이 결과를 오염시킨 전례가 있다 (D-09). `conditions.md` 의 확인 4가지를 15회 전부에 적용했다.

| 확인 | 기준 | 결과 |
|---|---|---|
| **분배** | 인스턴스별 처리 건수 각 25% 이상 | **15/15 통과** — 최소 33.1%, 대부분 33.3% |
| **도달** | k6 요청 수 = 3대 앱 요청 수 합 | **15/15 통과** — 차이 0 ~ 943건 (k6 종료와 마지막 스크레이프 사이의 시차) |
| **예산** | `hikaricp_connections_max` 3대 합 = 30 | **15/15 통과** — 전부 30, 인스턴스 3 |
| **워커** | `coupon_w4_reflected_total` 이 한 인스턴스에서만 증가 | **3/3 통과** — `app-worker` 만 증가, 나머지 둘은 0 |

**nginx 가 만든 5xx 는 0건이다.** k6 가 센 5xx 와 Prometheus 의 앱 5xx 가 15회 전부 일치한다(차이 0~2건). 즉 표 3장의 5xx 는 전부 애플리케이션이 돌려준 응답이며, 로드밸런서가 만든 것이 아니다.

### 이 폴더의 `app_5xx` 열은 믿지 않는다

`runs.tsv` 의 `app_5xx` 열은 **15행 전부 0** 으로 기록됐다. 러너의 메트릭 집계 정규식 버그다 (측정 중에는 고치지 않았다 — 브리프 7장의 조건 고정 규칙). 실제 값은 위 표대로이며 출처는 Prometheus 다.

**앱 로그 요약을 대체값으로 쓸 수 없다.** W3 의 503 `LOCK_TIMEOUT` 은 의도된 응답이라 예외 로그에 남지 않는다 — k6 는 62,768건을 셌는데 `log/W3-spike-run*.app.txt` 는 0~2건이다. 5xx 를 셀 때 "앱이 터진 것" 과 "앱이 거절한 것" 을 구분해야 한다는 뜻이다.

계획서 [`plan/week3.md`](../../plan/week3.md) 1장에 측정 전에 적어둔 표다.

| 예상 | 결과 |
|---|---|
| `over_issue` 수천~수만. L > 1/3 이면 150,000건 전부 발급, 품절 응답 0건 | **맞음** — 50,000 ×3, 150,000 전부 발급, 품절 0건 |
| `counter_drift` 큰 음수 (손실된 UPDATE 수) | **맞음** — −99,281 ± 137 |
| `duplicate_users` 0 (UNIQUE 가 막는다) | **맞음** — 0 |
| W1 · W2 · W3 · W4 전부 0 | **맞음** |
| "손실률 L 은 작지 않을 것이다" | **맞음** — 66% |

다섯 항목 모두 맞았다. 2주차에 빗나간 예상이 둘 있었던 것과 대비된다 — 그때는 아직 재보지 않은 장치(W3 의 락 대기, W4 의 반영 지연)를 추측했고, 이번에는 **이미 측정된 코드의 기전을 읽어서** 예측했다.

> 예상이 맞았다는 것이 실험의 성과는 아니다. 성과는 **틀렸다면 무엇을 의심할지 미리 적어 둔 것**이다 (계획서 1장: over_issue 가 0 이면 먼저 분배를 의심한다). 그 순서를 쓸 일은 없었다.

## 7. 결론

| | 3대 정합성 | 3대에서 판 재고 | 3대에서의 한 줄 |
|---|---|---|---|
| **W4** | 유지 | **100,000 완판, 5xx 0, 1.9분** | 유일하게 1대와 같은 모습이다 |
| W1 | 유지 | 100,000 완판, 그러나 5xx 28,592 | 커넥션 예산을 3으로 나누면 가장 먼저 타격받는다 |
| W3 | 유지 | 87,241 | **오버헤드가 정당화됐다.** 다만 정합성만 |
| W2 | 유지 | 29,336 | 1대의 절반. 이 워크로드에 맞지 않는다는 2주차 결론이 강화됐다 |
| **W0** | **깨짐** | 150,000 (재고 초과) | 인스턴스 1대 전용. 2대부터 쓸 수 없다 |

세 가지가 분명해졌다.

1. **단일 인스턴스에서 변별력이 없던 정합성이 3대에서 갈린다.** 2주차에는 다섯 전략 전부 0건이라 선택의 근거가 되지 못했다. 서버 대수는 전략 선택을 바꾸는 변수다.
2. **W0 의 붕괴는 락이 아니라 갱신 손실로 나타난다.** 잠금이 JVM 안에 있다는 사실 자체보다, 그 아래에서 절대값 UPDATE 가 서로를 덮어쓴다는 것이 규모를 정했다. 그래서 `over_issue` 뿐 아니라 `counter_drift` 를 같이 봐야 기전이 보인다.
3. **정합성을 지킨 것과 서비스가 되는 것은 다르다.** W2 는 재고의 30%, W3 는 87% 만 팔았고 둘 다 "NFR-01/02 통과" 다. 정합성은 필요조건이지 충분조건이 아니다.
