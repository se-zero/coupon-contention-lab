# 스탬피드 방어 기법 — 지터(C2) / 뮤텍스(C3) / 확률적 조기 갱신(C4)

> **한 줄 정의:** 셋 다 "만료 순간에 N 개가 동시에 원본으로 가는 것" 을 막지만, **건드리는 변수가 다르다.** 지터는 *언제* 만료되는지를, 뮤텍스는 *몇 개가* 가는지를, 조기 갱신은 *만료가 일어나는지 자체*를 바꾼다.

---

## 1. 왜 필요한가

[`cache-stampede.md`](cache-stampede.md) 의 C1 스모크에서 톱니를 실측했다 — 60초마다 DB 조회가 0 에서 **84** 로 뛰고 다시 0 이 된다. 히트율은 99.98% 인데 DB 는 5분에 다섯 번 얻어맞는다.

이 톱니는 세 가지 곱으로 만들어진다.

```
파동 크기 = (동시에 만료되는 키 수) × (키 하나에 겹치는 요청 수)
            └── 20 (워밍업이 정렬)     └── 4.2 (미스 창 8.6ms 동안 도착한 수)
파동 발생 = 만료가 실제로 일어나서 캐시가 비어야 한다
```

세 방어 기법은 이 세 인자 중 **하나씩**을 공격한다.

| | 공격하는 인자 | 결과 |
|---|---|---|
| **C2 지터** | 동시에 만료되는 키 수 → 흩뿌린다 | 파동이 **옆으로 퍼진다.** 높이는 낮아지지만 총량은 같다 |
| **C3 뮤텍스** | 키 하나에 겹치는 요청 수 → **1 로** | 파동이 **낮아진다** (키 수만큼만). 나머지는 기다린다 |
| **C4 조기 갱신** | 만료가 일어나는 것 자체 → 미리 갱신 | **미스가 사라진다.** 대신 갱신 조회가 남는다 |

이 표가 곧 실험 B 의 가설이다. 셋이 다른 인자를 건드리므로 **결과 그래프의 모양도 달라야 한다** — 같은 모양이면 구현이 틀렸거나 실험 조건이 그 인자를 활성화하지 못한 것이다.

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **지터** (jitter) | TTL 에 랜덤 오프셋을 더해 같은 시각에 넣은 키들이 다른 시각에 나가게 하는 것. `TTL ± J` |
| **뮤텍스 / 단일 재계산** (single-flight, request coalescing) | 키마다 "지금 누가 채우는 중" 을 표시해 미스를 만난 요청 중 **하나만** 원본에 보내고 나머지는 기다리게 하는 것. memcache 의 *lease* 가 원형 |
| **더블 체크** (double-checked) | 락을 잡은 뒤 **캐시를 다시 본다.** 기다리던 사이 남이 채웠으면 원본에 안 간다. 뮤텍스는 이 재확인이 없으면 의미가 없다 |
| **확률적 조기 갱신** (XFetch) | 만료 *전에* 요청마다 주사위를 던져 "지금 미리 갱신할까" 를 정하는 것. 만료가 가까울수록, 갱신에 오래 걸릴수록 확률이 오른다 |
| **Δ · β** | XFetch 의 두 매개변수. **Δ** 는 갱신(원본 조회)에 걸리는 시간, **β** 는 "얼마나 일찍" 의 배수. 만료까지 남은 시간이 `−β · Δ · ln(rand)` 보다 짧으면 갱신한다 |

## 3. 동작 원리

### 3-1. C2 지터 — 만료 시각을 흩뿌린다

```
C1:  키1..20 전부 TTL 60          → t=60 에 20개 동시 만료
C2:  키1 TTL 53, 키2 TTL 67, ...  → t=50~70 사이에 하나씩
```

넣을 때마다 `TTL = 60 + U(−J, +J)` 로 정한다. 워밍업이 20개를 같은 순간에 넣어도 **나가는 시각은 2J 폭에 퍼진다.**

그런데 지터가 건드리지 않는 것이 있다. **키 하나 안의 동시 미스는 그대로다.** 키 7 이 t=58 에 만료되면 그 순간 키 7 을 보던 요청 4.2개가 여전히 전부 DB 로 간다. 지터는 "20 × 4.2 = 84 가 1초에" 를 "4.2 가 20초 동안 20번" 으로 바꿀 뿐이다.

```
C1:   ▁▁▁▁▁▁█▁▁▁▁▁▁▁       84 가 한 초에
C2:   ▁▁▂▁▂▂▁▂▁▂▂▁▂▁       4~8 이 20초에 걸쳐
```

두 번째 주기부터는 더 퍼진다 — 키마다 다시 랜덤 TTL 을 받으므로 오프셋이 **누적**되고, 몇 주기 지나면 만료가 60초 주기 전체에 고르게 깔린다. 5분이면 5주기라 완전히 고르지는 않을 것이다.

### 3-2. C3 뮤텍스 — 한 명만 보내고 나머지는 세운다

```
요청 A ──▶ 캐시 미스 ──▶ 락 획득 ──▶ [캐시 재확인: 없음] ──▶ DB ──▶ 캐시 채움 ──▶ 락 해제 ──▶ 응답
요청 B ──▶ 캐시 미스 ──▶ 락 대기 ........................................ ──▶ 락 획득 ──▶ [캐시 재확인: 있음!] ──▶ 락 해제 ──▶ 응답
요청 C ──▶ 캐시 미스 ──▶ 락 대기 ............................................... ──▶ 〃
```

키마다 락 하나(`ReentrantLock`). 미스를 만나면 락을 잡는데, **잡은 뒤 캐시를 한 번 더 본다.** B 와 C 는 A 가 채운 값을 그 재확인에서 만나 DB 에 안 간다.

이 재확인이 핵심이다. 재확인 없이 "락 잡고 → DB" 면 직렬화만 될 뿐 **DB 조회 수는 그대로**다 (4.2 → 4.2, 순서만 생긴다).

**대기 상한** (D-13: 2초). 락을 2초 안에 못 잡으면 기다리기를 포기하고 **자기가 DB 를 읽는다.** 이 요청은 `wait.timeout` 에 세고 `db_load` 에도 센다. 상한이 없으면 A 가 DB 에서 멈췄을 때 그 키를 보는 전원이 무한정 매달린다.

**비용의 위치**가 이 기법의 전부다. B·C 의 응답 시간은 A 의 DB 왕복만큼 늘어난다. C1 에서는 B·C 가 각자 DB 에 갔으므로 **응답 시간은 같고 DB 부하만 3배**였다. C3 는 DB 부하를 1/3 로 줄이고 **응답 시간은 그대로 지불**한다. 무엇을 얻고 무엇을 잃는지가 대칭이다.

> 이 락은 **JVM 로컬**이다. 3대면 인스턴스마다 하나씩 DB 에 가서 20 이 60 이 된다 — 실험 B 를 단일 인스턴스로 고정한 이유(브리프 3.4). 인스턴스를 넘는 단일 재계산은 W3 의 분산 락으로 같은 것을 만들 수 있지만, 그러면 미스마다 Redis 왕복이 셋 붙는다 ([`distributed-lock.md`](distributed-lock.md)).

### 3-3. C4 확률적 조기 갱신 — 만료가 오기 전에 갈아 끼운다

앞의 둘은 **만료된 뒤**에 대응한다. XFetch 는 만료 **전**에 움직인다.

```
캐시에 저장하는 것:  값 + Δ(이 값을 만드는 데 걸린 시간) + 만료 시각
읽을 때마다:         남은 시간 < −β · Δ · ln(rand)  이면  →  지금 갱신 (DB 읽고 다시 저장)
                     아니면                              →  캐시 값 그대로
```

`rand` 는 0 ~ 1 의 균등 난수다. `−ln(rand)` 는 평균 1, 대부분 0~3 사이의 값이다. 그래서 갱신 판정은 대략 **"만료까지 β·Δ 쯤 남았을 때부터 확률적으로"** 켜지고, 만료에 가까울수록 확률이 1 로 간다.

왜 확률인가 — 결정적으로 "남은 시간 < Δ 면 갱신" 이라고 하면 그 순간 도착한 요청 **전원이** 갱신하러 간다. 스탬피드가 자리만 옮긴다. 난수를 섞으면 첫 갱신은 한 요청이 하고, 갱신되는 순간 만료 시각이 60초 뒤로 밀려 나머지는 판정에서 빠진다.

**Δ 를 값과 함께 저장**하는 이유 — 갱신에 오래 걸리는 값일수록 더 일찍 시작해야 한다. Δ 는 고정 설정이 아니라 **직전 갱신에서 실측한 시간**이다. 이 프로젝트에서는 `load` 타이머가 재는 바로 그 값이다.

### 3-4. C4 에서 예상이 갈리는 지점 — Δ 가 작으면 파동은 남는다

계획 단계에서는 C4 를 *"갱신이 조기에 분산되어 db_load 가 낮게 깔린다"* 고 적었다. **스모크 숫자를 넣어 보면 그 예상이 틀렸을 가능성이 크다.**

```
Δ ≈ 8.6ms (스모크에서 역산한 미스 창), β = 1
→ 갱신 창 ≈ 만료 전 마지막 8.6ms 안팎
→ 키당 도착 490/초 → 그 창에 ≈ 4 개 도착
→ 그중 하나가 갱신하고 만료가 60초 뒤로 밀린다
```

즉 **갱신은 만료 직전 몇 ms 에 몰려서 일어난다.** 20개 키가 정렬돼 있으면 t=95 부근에 20번의 갱신이 한 초 안에 들어간다. `db_load` 그래프에는 여전히 **60초 간격 파동이 남고, 높이는 20** 이다.

달라지는 것은 파동의 **성분**이다.

| | C1 파동 | C4 파동 |
|---|---|---|
| 높이 | 84 | ≈ 20 |
| 성분 | 전부 **미스** (캐시가 비어 있었다) | 전부 **갱신** (캐시에 값이 있는 채로 DB 를 읽었다) |
| 그 요청의 응답 | 느리다 (DB 왕복) | 느리다 (DB 왕복 — 갱신은 그 요청이 직접 한다) |
| 나머지 요청 | 같은 키를 보던 3개가 같이 미스 | **히트** |
| `miss` 카운터 | 84 | ≈ 0 |

"낮게 깔린다" 가 성립하려면 Δ 가 요청 간격보다 **훨씬** 커야 한다 (갱신 창이 넓어 주기 안에 흩어진다). 이 실험의 조회는 PK 한 번이라 Δ 가 작고, 그래서 C4 는 **미스를 없애지만 파동은 못 없앤다.** C3 와 같은 높이(20)를 **기다리는 요청 없이** 얻는 것이 C4 의 위치가 될 것이다.

이 예상이 틀리면(파동이 정말 깔린다면) 그것도 결과다. 7장에 검증 대상으로 적는다.

### 3-5. 셋을 한 그림에

```
db_load
  84 ┤ █          C1  ─ 전부 미스, 한 초
     │ █
  20 ┤ █  ▌       C3  ─ 키당 1 (나머지 대기)   ·   C4  ─ 키당 1 갱신 (나머지 히트)
     │ █  ▌
   8 ┤ █  ▌ ▂▂▂▂  C2  ─ 20초에 걸쳐
   0 ┼─────────────────▶
```

C3 와 C4 는 높이가 같다. 갈리는 것은 **다른 요청들이 그동안 무엇을 했는가** — C3 는 기다렸고(`wait` 타이머), C4 는 옛 값을 받았다(`hit`). 둘의 차이는 `db_load` 그래프가 아니라 **`wait` 분포와 `miss` 카운터**에 있다. 계측을 셋으로 나눈 이유가 여기서 갚아진다 ([`cache-basics.md`](cache-basics.md) 4장).

## 4. 실무 설정 기준

| 기법 | 매개변수 | 이 프로젝트 | 근거 |
|---|---|---|---|
| **C2** | 지터 폭 J | **±10초** (TTL 의 ±17%) | 파동 폭 2J = 20초가 60초 주기의 1/3 — **퍼진 것이 보이면서도 파동 사이 0 구간이 남아** C1 과 대조된다. J=30 이면 첫 주기부터 평평해져 결과는 좋지만 "지터가 무엇을 했는가" 가 그림에서 안 보인다. 실무 관행은 TTL 의 10~20% |
| **C3** | 대기 상한 | **2초** (D-13) | NFR-03 판정선(500ms)의 4배 — 상한이 P99 관측을 자르지 않는다. 상한 도달 시 **자기가 DB 를 읽는다** (요청을 버리지 않는다) |
| **C3** | 락 단위 | 키별 `ReentrantLock`, 맵에 보관 | 전역 락 하나면 다른 키의 미스까지 줄을 선다. 키 20개라 맵이 커지지 않는다 — **실무에서는 키가 늘어나는 만큼 맵도 늘어나므로 정리가 필요**하다 |
| **C4** | β | **1.0** (논문 기본값) | β 는 "얼마나 일찍" 의 배수다. 1 이면 평균적으로 만료 Δ 전부터. 키우면 갱신이 앞당겨져 파동이 퍼지지만 DB 조회가 는다 — 3-4 의 예상을 먼저 확인한 뒤 손댄다 |
| **C4** | Δ | **직전 갱신의 실측값**, 값과 함께 저장 | 고정 상수로 두면 Δ 를 저장할 이유가 없고, 원본이 느려졌을 때 갱신이 늦어진다 |
| **C4** | 저장 형식 | `{value, delta, expiresAt}` JSON 한 덩어리 | 남은 시간을 매 요청 `PTTL` 로 물으면 Redis 왕복이 하나 는다. 만료 시각을 값 안에 두면 GET 한 번이다. Redis 키의 TTL 은 그대로 60초로 둔다 (실제 만료는 Redis 가 한다) |

### 어느 것을 먼저 쓰는가

| 상황 | 먼저 |
|---|---|
| 키가 많고 워밍업·배포로 만료가 뭉친다 | **C2**. 비용이 0 이다 — 코드 한 줄 |
| 키가 적고 뜨겁다 (독자가 몰린다) | **C3** 또는 **C4**. C2 는 할 일이 없다 |
| 원본이 느려 미스 한 번이 비싸다 | **C4**. 미스 자체를 없앤다 |
| 낡은 값을 1초도 못 준다 | **C3**. C4 는 갱신 중에 옛 값을 준다 |
| 셋 다 | 가능하다. 지터 + 뮤텍스는 흔한 조합이다. 이 실험은 **효과를 분리하려고** 하나씩만 켠다 |

## 5. 트레이드오프

| | 얻는 것 | 잃는 것 | 안 되는 것 |
|---|---|---|---|
| **C2 지터** | 파동이 퍼진다. 구현 비용 0 | 낡음이 ±J 만큼 불규칙해진다 | 키 하나의 동시 미스 |
| **C3 뮤텍스** | 키당 DB 조회 1 | **대기한 요청의 응답 시간**. 로더가 죽으면 상한까지 전원 대기 | 인스턴스 간 (JVM 로컬) |
| **C4 조기 갱신** | 미스 0. 기다리는 요청 없음 | 갱신을 맡은 요청 하나가 느리다. 만료 안 된 값을 **버리고** 다시 읽는다 (조회가 는다) | Δ 가 작으면 파동은 남는다 (3-4) |

### C3 와 C4 는 같은 값을 다른 사람에게 청구한다

둘 다 "키당 DB 조회 1" 이다. 차이는 **나머지 요청이 낸 대가**다.

- C3 — 나머지가 **시간**을 낸다. 최신값을 기다린다
- C4 — 나머지가 **정확도**를 낸다. 갱신 중 옛 값을 받는다 (TTL 안이므로 명세 위반은 아니다)

"stale 을 1초도 못 준다" 면 C3, "P99 를 1ms 도 못 낸다" 면 C4. 브리프 13장이 C3 의 대기 정책을 따로 열어 둔 것은 이 청구서가 갈리는 지점이기 때문이고, D-13 이 "대기" 를 고른 것은 **그 청구서를 측정하려는** 실험이기 때문이다.

## 6. 흔한 오해 · 안티패턴

| 오해 · 안티패턴 | 실제 |
|---|---|
| "지터를 넣었는데 DB 피크가 그대로다" | 키가 적거나 하나가 뜨거운 경우다. 지터는 **키 사이**를 흩뿌리지 **키 안**을 못 흩뿌린다 (3-1) |
| 락을 잡고 캐시를 다시 안 본다 | 직렬화만 되고 DB 조회 수는 같다. 더블 체크가 없는 뮤텍스는 뮤텍스가 아니다 (3-2) |
| 전역 락 하나로 뮤텍스를 만든다 | 키 7 의 미스가 키 3 의 미스를 기다린다. 락은 **키별**이어야 한다 |
| 락 대기에 상한을 안 둔다 | 로더가 DB 에서 멈추면 그 키의 요청 전원이 영원히 매달린다. C3 의 상한 2초는 안전장치이자 관측값이다 |
| C3 의 대기 대신 stale 을 즉시 준다 | 동작은 하지만 **비용이 0 이 되어 관측 대상이 사라지고**, soft TTL 이 필요해지는 순간 C4 와 구분되지 않는다 (D-13) |
| XFetch 의 Δ 를 상수로 박는다 | 원본이 느려지는 순간 갱신이 늦어져 미스가 돌아온다. Δ 는 **재야** 한다 |
| "XFetch 는 부하를 평평하게 만든다" | Δ 가 요청 간격보다 클 때만이다. Δ 가 작으면 갱신이 만료 직전에 몰려 **파동은 남고 성분만 바뀐다** (3-4) |
| 조기 갱신 판정을 결정적으로 (`남은 시간 < Δ`) 한다 | 그 창에 도착한 전원이 갱신한다. 스탬피드가 만료 직전으로 옮겨갈 뿐이다. **난수가 본질**이다 |
| 히트율로 방어 효과를 잰다 | 셋 다 99% 대다. 갈리는 것은 `db_load` 의 피크, `miss` 와 `db_load` 의 차이, `wait` 분포다 |

## 7. 이 프로젝트에서

### 구현 요지 (9단계)

셋 다 C1 과 **같은 키·같은 직렬화·같은 응답**을 쓴다. 차이는 만료를 다루는 부분뿐이다 (브리프 5.4).

| | C1 에서 달라지는 곳 | 메트릭 |
|---|---|---|
| **C2** | `bucket.set(json, 60 + U(−10, +10) 초)` — **이 한 줄**. 워밍업의 첫 채움부터 적용된다 | C1 과 동일 (`miss` = `db_load`) |
| **C3** | 미스 → `locks.computeIfAbsent(id)` 의 락을 `tryLock(2s)` → **캐시 재확인** → 없으면 DB + 채움 → 해제. 상한 도달 시 직접 DB | 로더: `miss` + `db_load` + `load`. 대기자: `miss` + **`wait`**. 상한: `wait.timeout` + `db_load` |
| **C4** | 저장 형식 `{value, delta, expiresAt}`. 히트 시 `expiresAt − now < −β · delta · ln(rand)` 면 DB 읽고 다시 저장 (새 delta). 진짜 미스면 C1 과 동일 | 조기 갱신: **`hit` + `db_load`** + `load` (캐시에 값이 있었으므로 미스가 아니다). 진짜 미스: `miss` + `db_load` |

C4 의 메트릭 규칙 때문에 세 카운터의 관계가 전략마다 달라진다 — 이것이 그래프 없이도 구현을 확인하는 방법이다.

| | `miss` 와 `db_load` | `wait` |
|---|---|---|
| C0 · C1 · C2 | **같다** | 0 |
| **C3** | `miss` **>** `db_load` (대기자는 미스지만 DB 를 안 읽는다) | **> 0** |
| **C4** | `miss` **<** `db_load` (갱신은 히트인데 DB 를 읽는다) | 0 |

### 예상 (검증 대상)

스모크의 C1 (파동당 84, 미스 창 ≈ 8.6ms) 을 기준으로.

| | 파동당 피크 `db_load` | 모양 | `miss` | `wait` 평균 | 전체 P99 |
|---|---|---|---|---|---|
| C1 (기준) | 84 | 60초 간격 톱니 | 462 | — | 85ms |
| **C2** | **4~10** | 20초 폭으로 퍼짐, 2주기부터 더 퍼짐 | ≈ 462 (총량은 같다) | — | ≈ C1 |
| **C3** | **20** | 60초 간격, 낮은 톱니 | ≈ 462 (대기자도 미스다) | **≈ 미스 창 (수 ms)** | ≈ C1 — **대기가 P99 에 안 잡힌다** |
| **C4** | **≈ 20** | 60초 간격, 낮은 톱니 (3-4) | **≈ 40** (jit·warm 의 첫 채움만) | — | ≈ C1 |

**C3 와 C4 가 같은 높이로 나오면 실험이 실패한 것이 아니다.** 둘을 가르는 것은 오른쪽 세 열이고, 그것을 보려고 타이머를 따로 두었다 ([`cache-stampede.md`](cache-stampede.md) 7장).

**틀릴 수 있는 것** — C4 의 갱신 창(≈ 8.6ms)에 요청이 하나도 안 들어오면 만료가 그냥 일어나 C1 과 같은 미스가 난다. 키당 490 req/s 면 창에 평균 4개가 들어오므로 대부분 잡히겠지만, 잡히지 않은 키는 파동 안에서 84 쪽으로 튄다. C4 의 `miss` 가 40 보다 눈에 띄게 크면 이 경우다.

### 결정 (9단계 착수)

| 항목 | 값 | 근거 |
|---|---|---|
| C2 지터 폭 J | **±10초** | 4장 |
| C3 대기 정책 · 상한 | 대기 · **2초** | **D-13** |
| C4 β | **1.0** | 4장 — 논문 기본값, 3-4 의 예상을 먼저 확인한다 |
| C4 Δ | 직전 갱신 실측값 | 4장 |

### 테스트 (응답 동일성 + 기법별)

- C2 · C3 · C4 모두 `AbstractCouponReadTest` 의 공통 검증(응답 = DB 값, 두 번 같은 응답, 없는 쿠폰은 빈 결과)을 통과한다
- **C3** — 같은 키에 동시 미스 N 개 → `db_load` 가 **1** 이고 나머지 N−1 은 `wait` 에 기록된다
- **C4** — 저장된 값에 `delta` 와 `expiresAt` 이 있다. 만료 직전 상태를 만들어 읽으면 `db_load` 가 늘고 `miss` 는 안 는다

### 측정값

> 11단계에서 채운다. 위 예상 표를 실측으로 바꾸고, 특히 **C4 의 파동이 정말 남는지**(3-4)와 **C3 의 대기가 정말 P99 에 안 잡히는지**를 적는다.
