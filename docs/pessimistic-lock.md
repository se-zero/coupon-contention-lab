# 비관적 락 (`SELECT ... FOR UPDATE`)

> **한 줄 정의:** 데이터를 **읽는 순간** 그 행을 잠가서 다른 트랜잭션이 손대지 못하게 하고, **커밋할 때까지** 그 잠금을 유지하는 방식.

---

## 1. 왜 필요한가

[`transaction-isolation.md`](transaction-isolation.md) 에서 본 문제가 출발점이다.

```
읽기 ......... 쓰기
      ↑
  여기에 남이 들어온다
```

이 틈을 없애는 방법은 두 가지뿐이다.

| 방법 | 하는 일 | 이름 |
|---|---|---|
| 틈 자체를 막는다 | **읽는 순간부터 남을 못 들어오게 한다** | **비관적 락** |
| 틈을 허용하고 나중에 잡는다 | 쓸 때 "그 사이에 바뀌었나?" 확인하고 바뀌었으면 다시 한다 | 낙관적 락 |

**"비관적"은 성능 평가가 아니라 가정(假定)의 이름이다.** *"어차피 충돌한다"* 고 가정하고 미리 막는다. 반대로 낙관적 락은 *"웬만하면 충돌 안 난다"* 고 가정하고 사후에 확인한다.

> 선착순 쿠폰처럼 **모두가 같은 행 하나를 노리는** 상황이라면 앞의 가정이 맞다. 충돌은 예외가 아니라 기본값이다.

---

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **행 락 (row lock)** | 테이블이 아니라 **조건에 걸린 행**만 잠근다. 다른 행은 영향 없다 |
| **배타 락 (X)** | `FOR UPDATE`. 다른 트랜잭션의 **쓰기와 다른 배타 락을 막는다** |
| **공유 락 (S)** | `FOR SHARE`. 여러 트랜잭션이 동시에 가질 수 있고, 쓰기만 막는다 |
| **락 대기** | 이미 잠긴 행을 잠그려는 트랜잭션이 **그 자리에 멈춰** 앞 트랜잭션의 종료를 기다리는 것 |
| **데드락** | 서로가 가진 락을 서로 기다려 영원히 못 끝나는 상태. DB 가 감지해 **한쪽을 죽인다** |

> **락을 푸는 명령은 없다.** 행 락은 **커밋 또는 롤백으로만** 풀린다. 이것이 비관적 락을 이해하는 데 가장 중요한 사실이다 — 락의 수명이 곧 **트랜잭션의 수명**이다.

## 3. 동작 원리

### 3-1. 무슨 일이 일어나는가

```
시각   트랜잭션 A                              트랜잭션 B
────────────────────────────────────────────────────────────────────────────
 t1   BEGIN
 t2   SELECT * FROM coupon WHERE id=1
        FOR UPDATE            → 행 1 잠금 획득 ✔
 t3                                           BEGIN
 t4                                           SELECT ... FOR UPDATE
                                                → 잠겨 있음. 여기서 멈춘다 ⏸
 t5   issued_count = 99 확인
 t6   UPDATE ... SET issued_count = 100
 t7   COMMIT               → 락 해제
 t8                                           → 깨어난다. 그리고 다시 읽는다
 t9                                           issued_count = 100 ✔ (99 가 아니다)
t10                                           검증 실패 → SOLD_OUT
────────────────────────────────────────────────────────────────────────────
```

핵심은 **t8** 이다. B는 t4 에서 읽으려다 멈췄고, 깨어난 뒤 **그 시점의 최신 값**을 읽는다. 스냅샷의 옛 값이 아니다.

> `FOR UPDATE` 는 "읽기"가 아니라 **"읽고 잠그기"** 다. 그리고 잠근 뒤에 읽으므로 읽은 값이 최신임이 보장된다.

### 3-2. 그래서 임계 구역이 어디까지인가

```
BEGIN ─── SELECT FOR UPDATE ─────── 검증 ─── UPDATE ─── COMMIT
             ↑                                              ↑
          락 획득 ══════════ 임계 구역 ══════════════════ 락 해제
```

**락 구간과 트랜잭션 구간이 같다.** 이게 W0(JVM 락)와의 결정적 차이를 만든다 — 5장에서 다룬다.

### 3-3. PostgreSQL 의 잠금 종류

| 구문 | 막는 것 | 쓰는 곳 |
|---|---|---|
| `FOR UPDATE` | 다른 `FOR UPDATE` / `UPDATE` / `DELETE`, 그리고 **외래키 참조까지** | 행을 지우거나 키를 바꿀 때 |
| `FOR NO KEY UPDATE` | 위와 같되 **외래키 참조는 막지 않는다** | 키 외 컬럼만 고칠 때 ← **이 프로젝트** (7장 참조) |
| `FOR SHARE` | 다른 트랜잭션의 **수정만** 막는다. 여러 개가 공존 가능 | "이 행이 사라지지 않는다"만 보장하면 될 때 |
| `FOR KEY SHARE` | 가장 약함 | 외래키 무결성 확인용 (DB 가 내부적으로 씀) |

### 3-4. 락은 어디에 저장되나 — PostgreSQL 의 특이점

MySQL·Oracle 은 **메모리의 락 테이블**에 락을 기록한다. 그래서 잠근 행이 많아지면 메모리를 먹고, 한계를 넘으면 행 락이 테이블 락으로 승격(lock escalation)되기도 한다.

**PostgreSQL 은 행 락을 행 자체(튜플 헤더의 `xmax`)에 기록한다.**

| 결과 | |
|---|---|
| 락 개수 제한이 없다 | 100만 행을 잠가도 메모리를 쓰지 않는다 |
| 락 승격이 없다 | 행 락이 테이블 락으로 바뀌는 일이 없다 |
| `pg_locks` 에는 행 락이 안 보인다 | 대신 **기다리는 쪽**이 `transactionid` 락을 기다리는 형태로 나타난다 |

> 그래서 "누가 누구를 기다리는가"를 볼 때는 `pg_locks` 에서 `granted = false` 인 행과 `pg_stat_activity.wait_event_type = 'Lock'` 을 본다.

### 3-5. 일반 `SELECT` 는 막히지 않는다

```
A: SELECT ... FOR UPDATE  (행 1 잠금)
B: SELECT * FROM coupon WHERE id=1      → 안 막힌다. 즉시 반환 ✔
C: SELECT ... FOR UPDATE                → 막힌다 ⏸
```

MVCC 덕분에 **읽기는 쓰기를 기다리지 않는다.** 잠긴 행도 "잠기기 전 버전"을 읽으면 그만이다.

이게 실무에서 자주 오해되는 지점이다. **`FOR UPDATE` 는 조회 API 를 느리게 만들지 않는다.** 막는 것은 같은 행을 **고치려는** 쪽뿐이다.

## 4. 실무 설정 기준

| 설정 | 기본값 | 권장 | 근거 |
|---|---|---|---|
| `lock_timeout` | `0` = **무한 대기** | **요청 타임아웃보다 짧게** (예: 3s) | 무한 대기면 커넥션이 영원히 묶인다. 앞 트랜잭션이 멈춰 있으면 뒤가 전부 멈춘다 |
| `statement_timeout` | `0` | 설정 권장 | 폭주하는 쿼리 한 방이 커넥션을 다 먹는 것을 막는다 |
| `deadlock_timeout` | `1s` | **기본 유지** | 데드락 *탐지 주기*다. 줄이면 탐지가 빨라지지만 검사 비용이 는다 |
| `idle_in_transaction_session_timeout` | `0` | 설정 권장 | **트랜잭션을 연 채 노는 세션**이 락을 붙들고 있는 최악의 경우를 끊는다 |

### 반드시 지킬 두 가지

**① 락을 잡는 순서를 고정한다.**

```
트랜잭션 A: 행 1 잠금 → 행 2 잠금
트랜잭션 B: 행 2 잠금 → 행 1 잠금     ← 데드락
```

여러 행을 잠가야 한다면 **항상 같은 순서**(예: id 오름차순)로 잠근다. 데드락은 튜닝으로 줄이는 게 아니라 **설계로 없애는 것**이다.

**② 락 구간 안에서 느린 일을 하지 않는다.**

```java
// 이렇게 하면 안 된다
tx.execute(status -> {
    couponRepository.findByIdForUpdate(id);   // 락 획득
    externalApi.notify(userId);               // 3초 걸림  ← 그동안 전원 대기
    ...
});
```

락을 쥔 시간만큼 **뒤에 선 전원이 기다린다.** 락 구간의 길이가 곧 시스템 전체의 직렬 구간이다.

## 5. 트레이드오프

| 선택 | 얻는 것 | 잃는 것 | 언제 |
|---|---|---|---|
| **비관적 락** | 확실하다. 재시도 로직이 필요 없다. 실패율이 낮다 | **대기 중에도 커넥션·트랜잭션을 점유한다.** 데드락 위험 | 경합이 잦을 때 |
| 낙관적 락 | 대기가 없다. 경합이 드물면 가장 빠르다 | 충돌 시 재시도. 경합이 심하면 **재시도 폭주** | 충돌이 드물 때 |
| 단일 원자 UPDATE | 왕복 자체가 없다 | 도메인 규칙이 SQL 로 들어간다 | 규칙이 한 문장일 때 |

### 이 방식의 진짜 비용 — 대기 중 커넥션 점유

**여기가 W1 의 예상 실패 모드(브리프 5.1)이고, 이 문서에서 가장 중요한 부분이다.**

락을 기다리는 순서를 보면:

```
① 커넥션 풀에서 커넥션을 빌린다
② BEGIN
③ SELECT ... FOR UPDATE  ← 여기서 기다린다
```

**기다리는 동안 ①의 커넥션을 쥐고 있다.** 아무 일도 안 하면서 자원 하나를 점유한다.

풀 크기가 30이면 이렇게 된다.

```
동시 요청 200건, 풀 30

  1건   락을 쥐고 실제로 일하는 중
 29건   커넥션을 쥔 채 락을 기다리는 중   ← 커넥션 29개가 놀고 있다
170건   커넥션조차 못 얻고 풀 대기 큐에서 대기
```

> **일하는 것은 1건인데 커넥션 30개가 묶인다.** 나머지는 풀 밖에서 줄을 선다.
> 이때 `hikaricp_connections_active` 는 **30 (가득)**, `hikaricp_connections_pending` 은 **170** 으로 나타난다.

W0(JVM 락)와 비교하면 차이가 분명하다.

| | 락이 있는 곳 | 대기 중 커넥션 | 풀에서 보이는 모습 |
|---|---|---|---|
| **W0** | JVM 안 | **점유하지 않는다** — 락을 잡은 *뒤에* 커넥션을 얻는다 | `active = 1`, `pending = 0` |
| **W1** | DB 안 | **점유한다** — 커넥션을 얻은 *뒤에* 락을 기다린다 | `active = 30`, `pending = 동시성 − 30` |

**처리량은 둘 다 `1 ÷ 직렬 구간` 으로 같은 천장에 걸린다.** 달라지는 것은 **그 천장에 도달하기까지 무엇이 먼저 고갈되는가**다.

## 6. 흔한 오해 · 안티패턴

- **오해:** `@Transactional` 안에서 `findById` 로 읽고 고치면 락이 걸린다
  → **실제:** 안 걸린다. 평범한 `SELECT` 일 뿐이다. 락은 `FOR UPDATE` 를 **명시해야** 걸린다. 이 착각이 갱신 손실의 가장 흔한 원인이다.

- **오해:** `FOR UPDATE` 는 테이블을 잠근다
  → **실제:** 조건에 걸린 **행만** 잠근다. 단 **인덱스를 타지 못해 풀스캔하면 결과적으로 스캔한 행이 전부 잠긴다.** `WHERE` 절이 인덱스를 타는지 반드시 확인한다.

- **오해:** 락이 걸리면 조회도 느려진다
  → **실제:** PostgreSQL 에서 일반 `SELECT` 는 잠긴 행도 즉시 읽는다 (3-5). 막히는 것은 같은 행을 고치려는 쪽뿐이다.

- **오해:** 락은 다 쓰면 풀어줘야 한다
  → **실제:** 푸는 명령이 없다. **커밋/롤백으로만** 풀린다. 락을 짧게 쥐고 싶으면 **트랜잭션을 짧게** 하는 수밖에 없다.

- **안티패턴:** `lock_timeout` 을 두지 않는다
  → 앞 트랜잭션이 멈추면 뒤가 **무한정** 기다린다. 커넥션 풀이 그대로 말라붙는다.

- **안티패턴:** 여러 행을 제각각인 순서로 잠근다 → 데드락.

- **안티패턴:** 락 구간 안에서 외부 API 호출·파일 IO
  → 락 구간의 길이가 전체 시스템의 직렬 구간이다.

## 7. 이 프로젝트에서

### W1 구현

```java
@Override
public IssueResult issue(long couponId, long userId) {
    return transactionTemplate.execute(status -> {
        couponRepository.findByIdForUpdate(couponId);  // 행 잠금
        return core.issue(couponId, userId);           // 공통 발급 본문
    });
}
```

```java
// 비관적 락 — W1 전용
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select c from Coupon c where c.id = :id")
Optional<Coupon> findByIdForUpdate(@Param("id") long id);
```

### 실제로 나간 SQL 은 `FOR UPDATE` 가 아니었다

**측정값:** Hibernate SQL 로그를 켜고 `W1ConcurrencyTest` (요청 2,000건)를 실행했다.

| 확인한 것 | 결과 |
|---|---|
| 쿠폰 조회 SQL 총 건수 | **2,000** (= 요청 수) |
| 그중 잠금 조회 | **2,000** |
| 잠금 없는 평범한 조회 | **0** |

```sql
select ... from coupon c1_0 where c1_0.id=? for no key update
                                             ^^^^^^^^^^^^^^^^^^
```

`PESSIMISTIC_WRITE` 를 썼는데 나간 것은 `for update` 가 아니라 **`for no key update`** 다.
(Hibernate 6.6.22 + PostgreSQL 방언)

**그래도 상호 배제는 성립한다.** PostgreSQL 의 행 잠금 충돌 규칙에서 `FOR NO KEY UPDATE` 는
`FOR KEY SHARE` 를 제외한 **모든 잠금과 충돌**하며, 특히 **자기 자신과 충돌한다.**
두 트랜잭션이 동시에 이 잠금을 가질 수 없으므로 임계 구역은 그대로 보장된다. 테스트 통과가 그 증거다.

**Hibernate 가 일부러 약한 쪽을 고른 이유**가 있다. `coupon_issue` 는 `coupon` 을 외래키로 참조하는데,
`coupon_issue` 에 INSERT 하면 PostgreSQL 이 부모 행에 `FOR KEY SHARE` 를 건다.
만약 `FOR UPDATE` 를 쥐고 있었다면 **다른 트랜잭션의 INSERT 가 외래키 때문에 불필요하게 막힌다.**
우리는 `id` 를 바꾸지 않으므로 키를 잠글 이유가 없다.

> 문서에 쓰는 것과 DB 가 받는 것이 다를 수 있다. **`@Lock` 을 붙였으니 `FOR UPDATE` 가 나갔겠지** 라고
> 넘기지 않고 로그로 확인한 결과다. 브리프 5.1 의 표기(`SELECT ... FOR UPDATE`)는 비관적 락의
> 통칭으로 읽고, 실제 구문은 이 절을 기준으로 한다.

### 본문의 `findById` 는 DB 를 다시 치지 않는다

위 표의 **"잠금 없는 평범한 조회 0건"** 이 그 증거다. 요청 2,000건에 쿠폰 조회도 정확히 2,000건이다.

같은 트랜잭션의 영속성 컨텍스트(1차 캐시)에 잠긴 엔티티가 이미 올라와 있어, `core.issue()` 의
`findById` 는 그 인스턴스를 그대로 돌려받는다. 즉 **잠근 상태로 읽은 값** 그대로 검증·차감이 진행된다.

> 이 구조 덕분에 `IssueCore` 를 한 줄도 고치지 않고 W1 을 만들 수 있다. 브리프 5.4 의 *"비교군 간 차이는 오직 동시성 제어 방식뿐"* 이 코드로 지켜진다.
> W0 가 `lock.lock()` 으로 본문을 감쌌다면, W1 은 **행 락**으로 같은 본문을 감싼다. 감싸는 방법만 다르다.

### 측정값 — 예상대로 풀이 꽉 찼다

1주차 W0 측정에서 커넥션 풀은 **한 번도 압박받지 않았다** (`active = 1.0`, `pending = 0.0`). 풀 30 은 놀고 있었다.
**예상은 "W1 에서 `pending` 이 0 에서 처음 떠오른다" 였고, 맞았다.**

**측정값:** 2주차 ramp (200 → 2,000 VU, 3회 평균)

| 지표 | W0 실측 (1주차) | W1 예상 | **W1 실측** |
|---|---|---|---|
| `hikaricp_connections_active` | 1.0 고정 | 30 (풀 가득) | **30.0** ✔ |
| `hikaricp_connections_pending` | 0.0 | 동시성 − 30 | **171** ✔ |
| 처리량 | 256 RPS | 비슷하거나 소폭 낮음 | **270 ± 27** (W0 은 290 ± 10) ✔ |
| 커넥션 획득 대기 | 0 | — | **680 ms** (W0 · W3 · W4 는 0) |

`pending` 이 동시성을 따라 올라가지 않고 **171 에서 멈춘 것**은 예상과 다른 부분이다. 톰캣 스레드가
200개라 요청이 2,000개여도 동시에 풀을 두드리는 것은 200개뿐이다. 30개가 일하고 **170개가 줄을 선다.**
즉 `pending` 의 천장은 동시성이 아니라 **스레드 수 − 풀 크기**다. 그래서 200 VU 에서 이미 포화하고
그 뒤로는 평평하다.

### 대기는 응답 시간이 아니라 에러로도 나타난다

풀 대기가 `connection-timeout`(3초)을 넘기면 요청은 느려지는 것이 아니라 **실패한다.**

| | ramp (3회) | spike (3회) |
|---|---|---|
| 5xx | 0 / 3 / 4 | 23 / 5 / 9 |
| 예외 클래스 | 전부 `CannotCreateTransactionException` | 〃 |

로그를 보면 `Connection is not available, request timed out after 3001ms` 다. 5장에서 "커넥션을 쥔 채
기다린다" 고 쓴 것의 마지막 결과가 이것이다 — **대기 줄이 3초보다 길어지는 순간 그 요청은 500 이 된다.**

다만 spike 의 5xx 는 **전부 재고 소진 전**에 났다(발급 경합이 가장 심한 구간). 소진 후 구간에서는
0 건이므로 **NFR-04 는 만족**이다.

### W1 만의 문제가 아니었다 — 30분을 돌리면 W0 도 같이 꺾인다

soak(200 VU, 30분)에서 W1 은 3회 모두 처리량이 한 단계 떨어졌다(−10.6 ~ −32.4%, 12~24분).
처음에는 이것을 **"락 대기 중 커넥션을 점유하는 비용이 시간이 갈수록 쌓인 것"** 으로 읽으려 했다.

그런데 **커넥션 풀을 전혀 압박하지 않는 W0 도 같은 폭으로 떨어졌다.**

| | 하락률 (각 3회) | 평균 |
|---|---|---|
| W0 로컬 락 | −14.5 / −33.7 / −31.5% | **−26.5% ± 10.5** |
| W1 비관적 락 | −32.4 / −10.6 / −31.7% | **−24.9% ± 12.4** |

편차 안에서 구분되지 않는다. **그러므로 이 열화는 비관적 락의 특성이 아니다.** 하락 시점에 커넥션
홀딩 시간이 함께 뛰므로(80 → 127 ms) 원인은 애플리케이션이 아니라 DB 쪽에 있다. 무엇인지는
2주차 범위에서 갈리지 않아 3주차로 넘겼다. 전체 결과는 [`results/week2-experiment-a/summary.md`](../results/week2-experiment-a/summary.md).

> 문서에 예상을 적어두면 이런 일이 생긴다. "W1 이 열화한다" 까지는 맞았지만 **원인을 락에 돌린 것은
> 틀렸고**, 그 틀림은 W0 을 3회 재고 나서야 드러났다.

### 연결되는 NFR · 메트릭

| | |
|---|---|
| **NFR-01 / NFR-02** | 행 락이 임계 구역을 보장하므로 단일 인스턴스에서 0건이어야 한다 |
| **NFR-03** (P99 ≤ 500ms) | 락 대기가 응답 시간에 그대로 쌓인다. 꺾이는 지점을 `ramp` 로 찾는다 |
| **NFR-07** (3 인스턴스) | **W1 은 3대에서도 깨지지 않는다.** 잠금의 주체가 애플리케이션이 아니라 DB 이기 때문이다. W0 와 갈라지는 지점 (브리프 5.2) |
| 메트릭 | `hikaricp_connections_active` / `pending` / `acquire`, `pg_stat_activity` 의 `wait_event_type = 'Lock'` |

### 거절 경로도 락을 잡는다

재고가 소진된 뒤의 요청도 `FOR UPDATE` 로 행을 잠근 다음에야 "품절"을 판정한다. **거절이 발급과 같은 속도로 직렬 처리된다.**

효율만 보면 소진 후에는 락 없이 판정하는 편이 낫지만, 그렇게 하면 전략마다 코드 경로가 달라져 비교가 깨진다 (5.4). 이 특성은 확정값 D-02 에서 spike 총 요청 수를 정할 때 실제로 문제가 됐다 — 브리프 D-02 개정 이력 참조.
