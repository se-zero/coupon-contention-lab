# DB 커넥션 풀 (HikariCP)

> **한 줄 정의:** DB 연결을 미리 만들어 두고 빌려주고 돌려받는 자원 관리 계층. **동시에 DB로 흘려보낼 작업 수의 상한선**이기도 하다.

---

## 1. 왜 필요한가

DB 연결 하나를 새로 여는 비용은 크다. PostgreSQL 기준으로:

1. TCP 3-way handshake
2. 인증 (비밀번호 / SCRAM)
3. **서버가 OS 프로세스를 하나 fork** ← PostgreSQL은 스레드가 아니라 **커넥션당 프로세스**다
4. 세션 초기화 (인코딩, 타임존, 트랜잭션 설정)

합치면 로컬에서도 수 ms, 네트워크를 건너면 수십 ms다. **쿼리 실행 시간이 1ms인데 연결에 20ms를 쓰는** 상황이 된다.

풀이 없으면 요청마다 이 비용을 낸다. 그리고 더 큰 문제 — **연결 수에 아무 제한이 없어진다.** 요청이 5,000개 들어오면 PostgreSQL에 프로세스 5,000개를 만들려 시도하고, `max_connections`(기본 100)에 막혀 `FATAL: sorry, too many clients already`가 터진다.

> 그래서 커넥션 풀의 역할은 두 개다.
> **(1) 연결 재사용으로 비용 절감** — 이건 다들 안다.
> **(2) DB로 가는 동시 작업 수의 상한(백프레셔)** — 실무에서 사고가 나는 건 대부분 이쪽이다.

## 2. 핵심 개념


| 용어                            | 의미                                                 |
| ----------------------------- | -------------------------------------------------- |
| **풀 크기** (`maximumPoolSize`)  | 동시에 열어둘 수 있는 커넥션의 최대 개수. **동시 실행 가능한 DB 작업 수의 상한** |
| **홀딩 시간** (holding time)      | 커넥션을 빌린 순간부터 반납할 때까지. 쿼리 시간이 아니라 **트랜잭션 전체 시간**    |
| **획득 대기** (acquire / pending) | 풀에 여유가 없어 요청 스레드가 줄 서서 기다리는 시간                     |
| **반납** (`close()`)            | 연결을 끊는 게 아니라 **풀로 되돌리는 것**. 이름이 오해를 부른다            |
| **누수** (leak)                 | 빌리고 반납하지 않은 커넥션. 풀이 서서히 말라 죽는다                     |


## 3. 동작 원리

```
요청 스레드                HikariCP 풀                        PostgreSQL
    │                          │                                  │
    │  getConnection()         │                                  │
    ├─────────────────────────►│                                  │
    │                          │   ① 유휴 커넥션 있나? ── YES ──────┐
    │                          │        │ NO                      │
    │                          │        ▼                         │
    │                          │   ② 풀이 가득 찼나?                │
    │                          │      ├ NO  → 새 연결 생성 ────────►│ 프로세스 fork
    │                          │      └ YES → ③ 대기 큐에 들어감    │
    │                          │           connectionTimeout(30s) │
    │                          │            초과 → 예외 발생 ✗     │
    │◄─────────────────────────┤◄─────────────────────────────────┘
    │                          │
    │  ══ 홀딩 시간 시작 ══                                         │
    │  BEGIN → SELECT → UPDATE → INSERT → COMMIT ────────────────►│
    │  ══ 홀딩 시간 끝 ══                                          │
    │                          │                                  │
    │  close() = 반납          │                                  │
    ├─────────────────────────►│  연결 유지한 채 유휴 상태로 전환    │
```

**중요한 것은 ③번 대기 큐다.** 부하가 높을 때 요청은 여기서 대기하고, 이 시간은 사용자 응답 시간에 **그대로 더해진다**. 쿼리는 1ms인데 P99가 800ms라면, 십중팔구 큐에서 799ms를 기다린 것이다.

### 풀 크기와 처리량의 관계 (Little's Law)

```
필요한 풀 크기 = 목표 처리량(TPS) × 평균 홀딩 시간(초)
```

- 500 TPS × 20ms → `500 × 0.02 = 10` 커넥션
- 500 TPS × 100ms → `500 × 0.1 = 50` 커넥션

**홀딩 시간이 길어지면 필요한 풀 크기가 선형으로 늘어난다.** 트랜잭션 안에서 외부 API를 호출하면 안 되는 이유가 이것이다.

## 4. 실무 설정 기준

### HikariCP 주요 설정


| 설정                       | 기본값                   | 권장                            | 근거                                          |
| ------------------------ | --------------------- | ----------------------------- | ------------------------------------------- |
| `maximumPoolSize`        | 10                    | `(코어 수 × 2) + 디스크 수`          | PostgreSQL 공식 위키 사이징 공식. 8코어 SSD면 **17 내외** |
| `minimumIdle`            | `maximumPoolSize`와 동일 | **건드리지 않는다**                  | 고정 크기 풀이 지연 스파이크가 가장 적다 (HikariCP 공식 권장)    |
| `connectionTimeout`      | 30,000ms              | **2,000~5,000ms**             | 30초는 너무 길다. 사용자는 이미 떠났고 스레드만 잡고 있다          |
| `maxLifetime`            | 1,800,000ms (30분)     | DB·LB timeout보다 **최소 30초 짧게** | 인프라가 먼저 끊은 좀비 커넥션을 잡는 것을 방지                 |
| `idleTimeout`            | 600,000ms (10분)       | 고정 크기 풀에서는 무의미                | `minimumIdle < max`일 때만 동작                  |
| `leakDetectionThreshold` | 0 (비활성)               | 개발·부하 테스트 시 **5,000ms**       | 반납 안 된 커넥션을 스택 트레이스와 함께 로그로 남긴다             |


### 풀 크기를 정하는 순서

1. **작게 시작한다.** 위 공식값이 출발점이다.
2. 부하를 걸고 `hikaricp.connections.pending`을 본다.
3. **pending이 지속적으로 0보다 크면** — 원인이 둘 중 무엇인지 먼저 구분한다.
  - 홀딩 시간이 긴가? → **쿼리·트랜잭션을 고친다.** 풀을 늘리지 않는다.
  - 홀딩 시간은 짧은데 요청이 많은가? → 그때 풀을 늘린다.
4. `max_connections`를 넘지 않는지 확인한다. **인스턴스 수 × 풀 크기 + 모니터링·운영 도구 여유**.

### 봐야 할 메트릭 (Micrometer)


| 메트릭                            | 의미              | 위험 신호                            |
| ------------------------------ | --------------- | -------------------------------- |
| `hikaricp.connections.active`  | 사용 중인 커넥션       | max에 붙어 있으면 포화                   |
| `hikaricp.connections.pending` | **대기 중인 스레드 수** | **&gt; 0 이 지속되면 포화. 가장 먼저 볼 지표** |
| `hikaricp.connections.acquire` | 획득 대기 시간        | 응답 시간 증가분의 정체                    |
| `hikaricp.connections.usage`   | 홀딩 시간           | 늘어나면 트랜잭션이 길어진 것                 |
| `hikaricp.connections.timeout` | 획득 실패 횟수        | 1건이라도 = 사용자에게 5xx                |


풀 고갈 시 나타나는 예외:

```
SQLTransientConnectionException: HikariPool-1 - Connection is not available,
request timed out after 30000ms
```

## 5. 트레이드오프


| 선택                         | 얻는 것             | 잃는 것                                                                         | 언제                       |
| -------------------------- | ---------------- | ---------------------------------------------------------------------------- | ------------------------ |
| **풀을 키운다**                 | 동시 DB 작업 수 증가    | PG 프로세스 증가 → 컨텍스트 스위칭·메모리(`work_mem × N`)·락 경합 증가. **코어 수를 넘으면 처리량이 오히려 감소** | 홀딩 시간이 짧고 CPU에 여유가 있을 때만 |
| **풀을 줄인다**                 | DB 안정, 예측 가능한 지연 | 앱에서 대기가 늘어남                                                                  | 대부분의 경우 이쪽이 정답           |
| `connectionTimeout` **짧게** | 빠른 실패, 스레드 회수    | 스파이크 때 실패율 상승                                                                | 사용자 대면 API               |
| `connectionTimeout` **길게** | 스파이크를 버텨냄        | 스레드가 묶여 **연쇄 장애로 번짐**                                                        | 배치 작업                    |


### 핵심 직관: 대기는 사라지지 않고 이동한다

풀을 키운다고 대기가 없어지는 게 아니다. **대기 장소가 앱에서 DB 안으로 옮겨갈 뿐이다.**

```
풀 30  : [앱에서 970개 대기] → [DB에서 30개 처리]     ← 대기가 앱에 보인다. 제어 가능.
풀 300 : [앱에서 700개 대기] → [DB에서 300개 경합]    ← 대기가 DB 안으로 숨는다. 제어 불가.
```

DB 안의 대기는 타임아웃도, 우선순위도, 취소도 걸 수 없다. **앱에서 기다리는 편이 낫다.** 이것이 커넥션 풀을 "성능 최적화 장치"가 아니라 **"백프레셔 장치"**로 보는 관점이다.

## 6. 흔한 오해 · 안티패턴

- **오해:** 풀을 키우면 빨라진다 → **실제:** 병목이 DB CPU/락이면 풀을 키워도 처리량은 그대로고 지연만 늘어난다. (7번 참조)
- **오해:** `connection.close()`가 연결을 끊는다 → **실제:** 풀로 반납한다. 반대로 `**close()`를 빠뜨리면 커넥션이 영원히 반납되지 않는다.**
- **안티패턴:** 트랜잭션 안에서 외부 API 호출 → 홀딩 시간이 네트워크 지연만큼 늘어나고, 상대 서버가 느려지면 **내 DB 풀이 고갈된다.**
- **안티패턴:** 톰캣 스레드 200 + 풀 10인데 원인 분석 없이 풀만 200으로 → DB가 죽는다. 스레드 풀 &gt; 커넥션 풀은 **정상적인 설계**다.
- **오해:** `pending > 0`이면 풀이 작다 → **실제:** 홀딩 시간이 긴 게 원인인 경우가 더 많다. `usage`를 먼저 본다.

## 7. 이 프로젝트에서

### W1(비관적 락)이 꺾이는 지점의 정체

`SELECT ... FOR UPDATE`는 쿠폰 행 **하나**를 잠근다. 모든 요청이 같은 행을 노리므로 **임계 구역이 완전히 직렬화**된다.

락 홀딩 시간을 `t`라고 하면:

```
W1의 최대 처리량 = 1 / t     ← 풀 크기와 무관하다
```

`t = 2ms`라면 상한은 **500 TPS**이고, 풀을 30에서 300으로 늘려도 500 TPS다. 늘어나는 것은 **PostgreSQL 안에서 락을 기다리는 프로세스 수**뿐이다.

> 위 `t = 2ms`는 예시 수치다. 실제 값은 실험 A 1단계에서 `hikaricp.connections.usage`로 측정해 이 문서에 `측정값:`으로 갱신한다.

동시성이 올라갈 때 W1에서 관측될 순서:


| 동시성   | 예상 관측                                              |
| ----- | -------------------------------------------------- |
| 낮음    | `active` &lt; max, `pending` = 0 — 여유              |
| 중간    | `active` = max, `pending` 상승 시작 ← **꺾이는 지점**       |
| 높음    | `acquire` 시간이 P99를 지배 → **NFR-03(P99 ≤ 500ms) 미달** |
| 매우 높음 | `connections.timeout` 발생 → 5xx → **NFR-04 미달**     |


**이것이 "쓰기 경로에서 가장 먼저 포화되는 구간은 어디인가"(브리프 2장 질문 1)에 대한 답이다.** 병목은 CPU도 디스크도 아니고 **커넥션 풀 대기 큐**일 것으로 예상하며, 실험 A가 이를 검증한다.

반대로 **W4(Redis 원자 연산)는 임계 구역이 DB 밖에 있으므로 커넥션을 아예 잡지 않는다.** 같은 그래프에 겹쳐 그리면 두 곡선이 갈라지는 지점이 나온다.

### 이 프로젝트의 커넥션 예산 (확정값)


| 구분                           | 값                                |
| ---------------------------- | -------------------------------- |
| **DB 커넥션 총량**                | **30** (고정)                      |
| 1단계 (단일 인스턴스)                | `maximumPoolSize = 30`           |
| 2단계 (3 인스턴스)                 | `maximumPoolSize = 10` × 3대 = 30 |
| PostgreSQL `max_connections` | 100 (앱 30 + 모니터링·psql 여유)        |


**30을 고른 이유:**

1. **3으로 나누어떨어진다** — 브리프 5.3의 "2단계에서 커넥션 총량 동일" 규칙을 만족하는 필수 조건
2. 사이징 공식값(8코어 → 17)보다 **의도적으로 위** — 풀이 즉시 포화되면 W1이 *어느 동시성에서* 꺾이는지 구분할 수 없다. 이 실험은 포화를 **피하는 게 아니라 관측하는 것**이 목적이다
3. `max_connections = 100` 안에 충분히 들어간다
4. 너무 크면(예: 48+) 병목이 풀에서 PG CPU로 옮겨가 **측정하려는 현상 자체가 바뀐다**

> ⚠️ **이 값은 실험 시작 전 확정값이며 변경하지 않는다.** 변경 시 브리프 5.3에 따라 이전 측정치를 전부 폐기하고 재측정해야 한다.
> `connectionTimeout`도 모든 비교군에서 동일해야 한다 (브리프 5.4: 비교군 간 차이는 오직 동시성 제어 방식뿐).
