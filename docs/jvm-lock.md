# JVM 로컬 락 (synchronized / ReentrantLock)

> **한 줄 정의:** 하나의 JVM 프로세스 안에서만 유효한 상호 배제 장치. 자바 힙 메모리에 있는 객체 하나로 스레드들의 진입을 통제한다.

---

## 1. 왜 필요한가

`issuedCount++` 는 자바 코드로는 한 줄이지만 실제로는 세 단계다.

```
① 현재 값 읽기  →  ② 1 더하기  →  ③ 값 쓰기
```

이 세 단계 사이에 다른 스레드가 끼어들 수 있다. 재고가 1개 남은 상황을 보자.

```
재고 100개 중 99개 발급됨 (issued_count = 99, total = 100)

스레드 A                             스레드 B
   │                                   │
   ├─ ① issued_count 읽기 → 99          │
   │                                   ├─ ① issued_count 읽기 → 99   ← 같은 값을 읽는다
   ├─ ② 99 < 100 → 발급 가능 판정        │
   │                                   ├─ ② 99 < 100 → 발급 가능 판정
   ├─ ③ issued_count = 100 쓰기         │
   │                                   ├─ ③ issued_count = 100 쓰기  ← A의 결과를 덮어씀
   ▼                                   ▼
        발급 2건, issued_count 는 100  →  초과 발급 1건 (NFR-01 위반)
```

이것을 **갱신 손실(lost update)** 이라 한다. B가 A의 갱신을 못 본 채 덮어썼다.

읽고-판단하고-쓰는 이 구간을 **한 번에 한 스레드만** 지나가게 만들어야 한다. 그 장치가 락이다.

## 2. 핵심 개념


| 용어                           | 의미                                          |
| ---------------------------- | ------------------------------------------- |
| **임계 구역** (critical section) | 한 번에 한 스레드만 실행해야 하는 코드 구간                   |
| **상호 배제** (mutual exclusion) | 임계 구역에 둘 이상이 동시에 들어가지 못하게 하는 성질             |
| **락 객체**                     | 통제의 기준이 되는 자바 객체. **이 객체가 같아야 상호 배제가 성립한다** |
| **재진입** (reentrant)          | 이미 락을 쥔 스레드가 같은 락을 다시 요청해도 막히지 않는 성질        |
| **공정성** (fairness)           | 대기 순서대로 락을 주는가. 기본값은 비공정(nonfair)           |


## 3. 동작 원리

`ReentrantLock` 은 **AQS(AbstractQueuedSynchronizer)** 위에 만들어져 있다. 내부에 `state` 정수 하나와 대기 스레드 FIFO 큐를 둔다.

```
lock.lock() 호출
      │
      ▼
 state 를 0 → 1 로 바꾸기 시도 (CAS, 원자적 연산)
      │
      ├─ 성공 → 락 획득, 그대로 진행                      [무경합: 수십 ns]
      │
      └─ 실패 → 대기 큐에 자기 노드를 추가
                      │
                      ▼
                LockSupport.park()   ← 스레드가 여기서 멈춘다
                                        OS 스케줄러가 CPU 를 회수해 간다
                      │
                      ▼
                (락을 쥔 스레드가 unlock 하면)
                      │
                      ▼
                LockSupport.unpark() → 깨어나서 재시도    [경합: 수 μs, 커널 왕복]
```

**핵심은 이 모든 일이 JVM 힙 메모리 안에서만 일어난다는 것이다.** 네트워크도, DB도, 다른 프로세스도 관여하지 않는다. 그래서 빠르고, 그래서 프로세스 경계를 넘지 못한다.

`synchronized` 는 문법만 다를 뿐 원리는 같다. 객체 헤더의 mark word 에 소유 스레드를 기록하고, 경합이 생기면 JVM 이 모니터를 부풀려(inflate) 대기 큐를 만든다.

### 비용


| 상황                    | 대략                    |
| --------------------- | --------------------- |
| 경합 없음 (CAS 한 번에 성공)   | 수십 ns — 사실상 공짜        |
| 경합 있음 (park / unpark) | 수 μs — 커널 컨텍스트 스위치 발생 |


> 락 자체의 비용은 작다. **문제가 되는 것은 락을 쥐고 있는 시간이다.** (5장 참조)

## 4. 실무 설정 기준

### synchronized vs ReentrantLock


| 필요한 것                        | 선택                                           |
| ---------------------------- | -------------------------------------------- |
| 단순한 상호 배제                    | `**synchronized**` — 블록을 벗어나면 자동 해제되어 실수가 없다 |
| 타임아웃 (`tryLock(3, SECONDS)`) | `ReentrantLock`                              |
| 인터럽트 가능한 대기                  | `ReentrantLock`                              |
| 공정 락                         | `ReentrantLock(true)`                        |
| 조건별 대기 큐 분리 (`Condition`)    | `ReentrantLock`                              |


`ReentrantLock` 을 쓰면 `**unlock()` 을 `finally` 에 두는 것이 필수**다. 빠뜨리면 락이 영원히 풀리지 않는다.

```java
lock.lock();
try {
    // 임계 구역
} finally {
    lock.unlock();   // 예외가 나도 반드시 해제
}
```

### 설정 기준


| 항목        | 기준                            | 근거                                              |
| --------- | ----------------------------- | ----------------------------------------------- |
| 락 범위      | **최소화한다**                     | 락 안의 시간이 곧 직렬 구간이고, 그것이 처리량의 상한을 정한다            |
| 락 안에서 I/O | **금지**                        | DB 왕복, 외부 API 호출이 들어가면 직렬 구간이 수 ms~수백 ms 로 늘어난다 |
| 대기 정책     | 사용자 대면 경로는 `tryLock(timeout)` | 무한 대기는 스레드를 묶어 연쇄 장애로 번진다                       |
| 공정성       | **기본값(비공정) 유지**               | 공정 락은 매번 큐를 거쳐 처리량이 크게 떨어진다. 기아가 실제로 관측될 때만 켠다  |
| 락 순서      | 여러 락을 쥘 때는 **획득 순서를 전역으로 고정** | 순서가 엇갈리면 데드락                                    |


## 5. 트레이드오프


| 선택             | 얻는 것                      | 잃는 것                 | 언제               |
| -------------- | ------------------------- | -------------------- | ---------------- |
| **락 범위 넓게**    | 구현이 단순, 실수 적음             | 직렬 구간이 길어져 처리량 급감    | 호출 빈도가 낮은 경로     |
| **락 범위 좁게**    | 처리량 확보                    | 경계 설계가 어려워지고 버그 위험   | 경합이 심한 핵심 경로     |
| **비공정 락** (기본) | 처리량 높음 (직전 소유자가 재획득하기 쉬움) | 특정 스레드가 계속 밀릴 수 있음   | 대부분              |
| **공정 락**       | 대기 순서 보장                  | 처리량이 눈에 띄게 하락        | 기아가 실제 문제일 때만    |
| **로컬 락**       | 빠름, 외부 의존성 없음             | **인스턴스가 2대 이상이면 무력** | 단일 인스턴스가 확정된 경우만 |


### 핵심 직관: 락 안의 시간이 처리량의 역수다

임계 구역을 통과하는 데 걸리는 시간을 `t` 라 하면, 그 구간은 한 번에 하나씩만 지나가므로:

```
최대 처리량 = 1 / t        ← 스레드를 아무리 늘려도 변하지 않는다
```

`t = 4ms` 면 상한은 250 TPS 다. 스레드를 200개로 늘려도, 서버를 32코어로 올려도 250 TPS 다. 늘어나는 것은 **대기 줄의 길이**뿐이고, 그것은 응답 시간이 되어 사용자에게 돌아간다.

```
응답 시간 = 내 앞에 서 있는 사람 수 × t
```

그래서 락 최적화는 "락을 빠르게 만드는 것"이 아니라 **"락 안에서 하는 일을 줄이는 것"** 이다.

## 6. 흔한 오해 · 안티패턴

- **오해:** 로컬 락이 DB 행이나 테이블을 잠근다 → **실제:** DB 는 이 락의 존재를 모른다. 락은 자바 메서드 입구를 막는 경비원이지 DB 문의 자물쇠가 아니다. **DB 를 잠가서 하나씩 처리되는 게 아니라, 자바 입구에서 하나씩만 들여보내니 결과적으로 DB 에도 하나씩 가는 것**이다.
- **오해:** `synchronized` 를 붙였으니 스레드 안전하다 → **실제:** **락 객체가 같아야** 의미가 있다. 요청마다 새 객체를 만들어 잠그면 아무도 배제되지 않는다.
- **오해:** 서버를 늘리면 해결된다 → **실제:** 로컬 락은 서버를 늘리는 순간 **깨진다.** (7장 참조)
- **안티패턴:** 락 안에서 DB 쿼리나 외부 API 호출 → 직렬 구간이 I/O 시간만큼 늘어난다. 상대 서버가 느려지면 내 처리량이 그대로 무너진다.
- **안티패턴 (가장 위험):** **트랜잭션 안에 락을 넣는 것**

```java
@Transactional                       // ← 트랜잭션이 먼저 시작된다
public void issue() {
    lock.lock();
    try {
        // 재고 확인 + 차감
    } finally {
        lock.unlock();               // ← 락은 여기서 풀린다
    }
}                                    // ← 커밋은 여기서 일어난다 (락이 풀린 뒤!)
```

락 해제와 커밋 사이에 **경합 창(race window)** 이 열린다. 다음 스레드가 락을 얻고 들어와 아직 커밋되지 않은 이전 값을 읽는다. 락을 걸었는데도 갱신 손실이 발생한다.

**락은 트랜잭션보다 바깥에 있어야 한다.**

```
올바른 순서:  락 획득 → 트랜잭션 시작 → 작업 → 커밋 → 락 해제
잘못된 순서:  트랜잭션 시작 → 락 획득 → 작업 → 락 해제 → 커밋   ← 경합 창
```

> 스프링에서는 `@Transactional` 이 프록시로 동작하므로 같은 빈 안에서 호출하면 아예 적용되지 않는 함정도 있다. 경계를 눈으로 확인하려면 `TransactionTemplate` 으로 직접 여닫는 편이 안전하다.

## 7. 이 프로젝트에서

### W0 구현

`app/src/main/java/com/experiment/coupon/strategy/W0LocalLockStrategy.java:31`

```java
@Override
public IssueResult issue(long couponId, long userId) {
    lock.lock();  // 임계 구역 진입
    try {
        // 커밋까지 락 유지 — 락 해제가 커밋보다 빠르면 경합 창이 열린다
        return transactionTemplate.execute(status -> core.issue(couponId, userId));
    } finally {
        lock.unlock();  // 임계 구역 이탈
    }
}
```

`@Transactional` 대신 `TransactionTemplate` 을 쓴 이유가 6장의 안티패턴이다. 락이 트랜잭션을 **감싸야** 커밋 완료 후에 락이 풀린다.

### 200 동시 요청이 실제로 어떻게 흐르는가

```
k6         200 VU         200개 요청이 동시에 날아감
   ↓
Tomcat     스레드 200      200개 전부 스레드를 받음          ← 여기까지는 진짜 동시
   ↓
W0         ReentrantLock   1개만 통과, 199개는 park() 상태   ← 병목
   ↓
HikariCP   풀 30           실제로 빌려가는 건 1개 (29개는 유휴)
   ↓
PostgreSQL                 트랜잭션 1개만 실행
```

**W0 에서는 커넥션 풀 30이 아무 역할도 하지 않는다.** 락이 앞에서 1개로 조여버리기 때문이다. 그래서 W0 로는 "풀이 언제 고갈되는가"를 관측할 수 없고, 브리프가 W0 를 **"락 오버헤드의 하한선 참고값"** 으로 규정한 이유가 이것이다.

반면 W1(비관적 락)은 스레드 30개를 전부 DB 로 들여보낸 뒤 DB 안의 행 락에서 줄을 세운다. 커넥션 30개가 모두 락 대기로 묶여 반납되지 않으므로 그때 비로소 `hikaricp_connections_pending` 이 0에서 떠오른다.

### 측정값 (1주차 파이프라인 검증 실행)

> 조건: 단일 인스턴스, 풀 30, 200 VU, 총 20,000건. 2주차 정식 측정은 1,000,000건으로 다시 한다.


| 항목            | 값                           |
| ------------- | --------------------------- |
| 처리량           | 256 RPS                     |
| 평균 응답 시간      | 778ms                       |
| P99           | 1.77s (NFR-03 판정선 500ms 초과) |
| 역산한 직렬 구간 `t` | **3.9ms**                   |


세 숫자가 서로 검증된다. `200 VU ÷ 0.778s = 257 RPS`, `1 ÷ 256 = 3.9ms`, `200 × 3.9ms = 780ms`.

즉 **응답 시간 778ms 중 실제 일한 시간은 3.9ms 이고 나머지 774ms 는 앞사람 199명을 기다린 시간**이다.

그리고 이 3.9ms 안에는 **커밋 fsync 가 들어 있다.** 락을 커밋까지 쥐고 있으므로 디스크 I/O 시간까지 직렬화된다. W2/W4 처럼 락 없이 커밋이 병렬로 몰리는 전략은 PostgreSQL 의 group commit 이 fsync 를 묶어주므로 이 비용을 분산시킨다. 이 비대칭은 노이즈가 아니라 실험 A 가 드러내야 할 차이다.

### 3 인스턴스에서 깨지는 이유

`new ReentrantLock()` 은 **JVM 마다 자기만의 객체**를 만든다. 서로 다른 프로세스의 힙에 있으므로 남남이다.

```
[JVM 1] 락1 ─ 스레드 통과 ┐
[JVM 2] 락2 ─ 스레드 통과 ├→ 3개가 동시에 같은 쿠폰 행을 읽고 쓴다 → 갱신 손실 → 초과 발급
[JVM 3] 락3 ─ 스레드 통과 ┘
```

각자 자기 집 문만 지키므로 셋이 동시에 통과한다. 1장의 갱신 손실 그림이 인스턴스 단위로 재현되는 것이다.


| 전략     | 잠그는 대상      | 그것이 있는 곳            | 3 인스턴스 |
| ------ | ----------- | ------------------- | ------ |
| **W0** | Java 객체     | **JVM 힙** (3개로 쪼개짐) | **깨짐** |
| W1     | 쿠폰 **행**    | PostgreSQL (1개)     | 유지     |
| W3     | Redis **키** | Redis (1개)          | 유지     |


잠금 장치가 **프로세스 밖에 하나만 있는가**가 갈림길이다.

> **W0 가 깨지는 것은 결함이 아니라 관측 대상이다.** (브리프 작업 규칙 4)
> 고치지 않는다. 3주차 2단계에서 이 붕괴를 숫자로 재현하는 것이 실험 A 의 하이라이트다.
> UNIQUE 제약은 중복 발급(NFR-02)만 막을 뿐 **초과 발급(NFR-01)은 막지 못하므로**, 서로 다른 유저가 재고를 초과해 발급받는 형태로 관측된다.
