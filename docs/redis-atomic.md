# Redis 단일 스레드 모델과 Lua 원자성

> **한 줄 정의:** Redis 는 명령을 **한 번에 하나씩** 처리한다. 그래서 한 스크립트 안에 넣은 여러 단계는 **끼어들 틈 없이** 실행되고, 이것만으로 락 없이 임계 구역이 만들어진다.

---

## 1. 왜 필요한가

W0~W3 는 방법이 달라도 뼈대가 같다.

```
줄 세우기(락) ──▶ DB 읽기 ──▶ 검증 ──▶ DB 쓰기 ──▶ 커밋(fsync) ──▶ 줄 풀기
```

아무리 잘 짜도 요청 하나가 **DB 를 여러 번 왕복하고 디스크에 한 번 쓴다.** 1주차 W0 의 256 RPS 는 요청당 3.9ms 이고, 그 대부분이 이 뼈대의 비용이다 ([`transaction-isolation.md`](transaction-isolation.md) 7장).

다른 접근이 있다. **판정에 필요한 것만 메모리로 옮기고, 판정을 메모리에서 끝낸다.** 재고 숫자와 "받은 사람" 명단이면 충분하다. DB 는 나중에 따라오면 된다.

그러면 락은? 메모리(Redis)에서 "확인 → 차감" 사이에 남이 끼어들면 똑같이 갱신 손실이다. 그런데 Redis 에는 그 틈이 **구조적으로 없다.** 이 문서는 그 이유와 대가를 다룬다.

---

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **단일 스레드 이벤트 루프** | 명령을 실행하는 스레드가 **하나**다. (6.0+ 의 I/O 스레드는 읽기·쓰기 소켓 처리만 나눈다) 동시에 두 명령이 실행되는 일이 없다 |
| **원자성 (Redis 의)** | **끼어들 수 없음.** 트랜잭션의 원자성(실패하면 되돌림)과 **다르다** — Redis 스크립트는 되돌리지 않는다 (3-5) |
| **Lua 스크립트** | 여러 명령을 하나의 실행 단위로 묶는다. `EVAL` 로 보내고, 캐시된 뒤에는 `EVALSHA` 로 해시만 보낸다 |
| **`KEYS` / `ARGV`** | 스크립트에 넘기는 키 목록과 인자. 키를 명시해야 클러스터에서 같은 슬롯인지 검사할 수 있다 |
| **`MULTI`/`EXEC`** | 명령 묶음을 한 번에 실행. 원자적이지만 **중간 결과로 분기할 수 없다** — "재고가 있으면 차감"은 못 쓴다 |

> Lua 가 필요한 이유는 **조건 분기**다. `DECR` 하나는 원자적이지만 "0 이하면 차감하지 마라"는 표현이 없다. `MULTI` 는 분기가 없다. 읽고 → 판단하고 → 쓰는 것을 한 덩어리로 만드는 도구가 스크립트다.

## 3. 동작 원리

### 3-1. 왜 명령 하나는 원자적인가

```
클라이언트 A ──▶ ┐
클라이언트 B ──▶ ├──▶ [이벤트 루프] ──▶ 명령 1 ──▶ 명령 2 ──▶ 명령 3 ──▶ ...
클라이언트 C ──▶ ┘                    (한 번에 하나, 끝나야 다음)
```

DB 는 여러 커넥션이 동시에 실행되기 때문에 락으로 순서를 만든다. Redis 는 **애초에 한 줄**이다. 순서를 만들 필요가 없다. 명령 하나가 실행되는 동안 다른 명령은 소켓 버퍼에서 기다린다.

이 단순함이 Redis 가 빠른 이유이자, 뒤에 나올 함정(3-6)의 이유다.

### 3-2. 그래서 여러 명령을 하나로 — 관측한 스크립트

`W4ConcurrencyTest` 실행 중 `redis-cli MONITOR` 로 잡은 발급 스크립트다. 이것이 W4 의 임계 구역 전부다.

```lua
local c = redis.call('hmget', KEYS[1], 'stock', 'start', 'end')   -- 재고·기간 한 번에 읽기
if not c[1] then return 0 end                                      -- 미적재 → 앱이 DB 에서 적재 후 재시도
local now = tonumber(ARGV[2])
if now < tonumber(c[2]) or now > tonumber(c[3]) then return -1 end -- 기간 외      (NOT_IN_PERIOD)
if tonumber(c[1]) <= 0 then return -2 end                          -- 소진         (SOLD_OUT)
if redis.call('sismember', KEYS[2], ARGV[1]) == 1 then return -3 end -- 중복       (DUPLICATE)
redis.call('hincrby', KEYS[1], 'stock', -1)                        -- 차감
redis.call('sadd', KEYS[2], ARGV[1])                               -- 명단 등록
redis.call('rpush', KEYS[3], ARGV[3])                              -- 반영 큐 적재
return 1                                                           -- 발급         (ISSUED)
```

검증 순서(기간 → 소진 → 중복)는 `IssueCore` 와 같다. 응답 코드도 같다. **비교군 간 차이는 판정을 어디서 하느냐뿐**이다 (브리프 5.4).

마지막 세 줄이 핵심이다. 차감·명단·큐가 한 스크립트 안이므로 **"차감은 됐는데 큐에 없다"는 상태가 존재하지 않는다.** 아웃박스나 외부 브로커로 갈랐다면 두 시스템 사이에 그 틈이 생긴다.

### 3-3. 락이 없는데 왜 안전한가 — 줄이 어디에 있는가

W3 와 W4 모두 "한 번에 하나"다. 다른 것은 **줄이 서 있는 위치**다.

```
W3:  스레드 199개가 Redis 락 채널에서 대기 ──▶ 한 명씩 DB 왕복 (ms 단위) ──▶ 다음 사람 깨우기
W4:  요청 200개가 Redis 소켓 버퍼에서 대기 ──▶ 스크립트 하나 (μs 단위) ──▶ 다음 스크립트
```

W3 는 줄이 **클라이언트 쪽**에 있고 한 사람의 차례가 DB 왕복만큼 길다. W4 는 줄이 **Redis 안**에 있고 한 사람의 차례가 메모리 연산 몇 개다. 직렬화 정도는 같은데 **한 칸의 길이가 천 배 다르다.**

관측값: 요청당 Redis 왕복 **1회**. W3 의 3.7회 + DB 왕복과 비교된다 (7장).

### 3-4. 사실이 두 곳에 있다 — Redis 가 원본, DB 가 사본

```
요청 ──▶ [Lua] 차감 + 명단 + RPUSH ──▶ 201 응답        ← 여기서 "발급됐다"가 확정
                          │
                          ▼  큐 (Redis LIST)
              워커 (100ms 마다 최대 500건)
                          │
                          ▼
             INSERT 묶음 + issued_count += N ──▶ 커밋 ──▶ LTRIM (큐에서 제거)
```

사용자가 201 을 받는 순간 DB 에는 아무것도 없다. 그 사실은 **Redis 의 큐에만** 있다. 워커가 옮겨 쓴 뒤에야 DB 가 따라잡는다. 이 간격이 **반영 지연**이고, 이 구간에 Redis 가 죽으면 201 을 받은 발급이 **어디에도 남지 않는다.**

워커의 순서가 중요하다. **커밋한 뒤에 큐에서 지운다.** 반대로 하면(지우고 → 쓰기) 쓰기 전에 죽었을 때 유실된다. 이 순서면 죽어도 다음 주기에 같은 항목을 다시 쓰고, 그때의 중복 INSERT 는 `ON CONFLICT DO NOTHING` 이 흡수한다 (at-least-once).

### 3-5. 스크립트는 롤백하지 않는다

Lua 스크립트 중간에 오류가 나면 **이미 실행된 명령은 그대로 남는다.** DB 트랜잭션처럼 되돌려 주지 않는다.

그래서 스크립트의 모양이 정해진다 — **읽기와 검증을 전부 먼저, 쓰기는 마지막에 몰아서.** 3-2 의 스크립트가 정확히 그 모양이다. 쓰기 세 줄은 그 위의 어떤 분기에서도 실패할 수 없는 명령들이고, 첫 쓰기가 실행됐다면 나머지도 실행된다.

### 3-6. 긴 스크립트는 전체를 멈춘다

3-1 의 뒷면이다. 스크립트가 실행되는 동안 **Redis 전체가** 멈춘다. 명단 집합에 10만 명이 들어 있을 때 `SMEMBERS` 로 전부 읽는 스크립트를 넣으면 그 시간 동안 모든 클라이언트가 기다린다.

3-2 의 스크립트는 `HMGET` / `SISMEMBER` / `HINCRBY` / `SADD` / `RPUSH` — **전부 O(1)** 이다. 명단이 10만이든 100만이든 실행 시간이 같다. 스크립트에 넣을 명령을 고를 때 이것이 첫 번째 기준이다.

## 4. 실무 설정 기준

| 설정 | 기준 |
|---|---|
| **스크립트 모양** | 검증 먼저, 쓰기 마지막 (3-5). 명령은 O(1) 만 (3-6). 키는 `KEYS` 로 명시 |
| **적재 방식** | 첫 요청이 DB 에서 읽어 **없을 때만** 쓴다 (`EXISTS` → `HSET`, 스크립트로 원자화). 이미 차감이 진행된 값을 덮어쓰면 재고가 되살아난다 |
| **워커 주기 / 배치** | 처리량이 발급 속도를 넘도록. 이 프로젝트 **100ms / 500건** = 최대 5,000건/초. 1주차 W0 속도라면 100ms 에 26건 — 쌓이면 그것도 결과다 |
| **큐 제거 시점** | **커밋 뒤** (3-4). 유실보다 중복이 낫고, 중복은 UNIQUE 가 있다 |
| **영속성 (AOF / RDB)** | 켜면 Redis 재시작 후에도 재고·큐가 남는다. 이 프로젝트는 **`appendonly no`** — 장애 시 공백을 관측하려는 의도다 (7장) |
| **`maxmemory-policy`** | 반드시 **`noeviction`**. 캐시처럼 LRU 로 두면 메모리가 차는 순간 재고 키가 지워지고, 다음 요청이 DB 에서 다시 적재해 **재고가 되살아난다** |

### 반드시 지킬 세 가지

1. **쓰기는 스크립트 끝에 몰아둔다.** 되돌릴 수 없으므로 중간 실패가 있으면 안 된다.
2. **적재는 없을 때만.** 두 요청이 동시에 적재해도 나중 것이 앞의 차감을 덮어쓰지 않아야 한다.
3. **큐 제거는 커밋 뒤에.** 순서를 바꾸는 순간 at-most-once 가 되어 유실이 생긴다.

## 5. 트레이드오프

| | W3 분산 락 | W4 Redis 원자 연산 |
|---|---|---|
| Redis 에 있는 것 | 열쇠 | **재고 + 명단 + 큐** |
| 판정하는 곳 | DB (락 잡고 읽어서) | **Redis** (스크립트 안) |
| 요청당 Redis 왕복 | 3.7회 | **1회** |
| 요청 경로의 DB | 읽기 + 쓰기 + 커밋 | **없음** |
| "발급됐다" 의 원본 | DB 커밋 | **Redis 스크립트 결과** |
| Redis 장애 시 | 새 요청 실패. **커밋된 것은 안전** | 새 요청 실패. **큐에 남은 것은 유실** |
| 반영 지연 | 없음 | **있음** (측정 대상) |

### 이 방식의 진짜 비용 — 사실이 메모리에만 있는 구간

W3 까지는 "Redis 가 죽어도 이미 끝난 발급은 DB 에 있다"가 성립했다. W4 는 아니다. 201 을 받았지만 워커가 옮기기 전에 Redis 가 죽으면 **그 발급은 없던 일이 된다.** 사용자는 받았다고 알고 있고 서버는 모른다.

이것을 없애는 방법은 전부 W4 를 W4 가 아니게 만든다 — AOF 를 켜면 fsync 가 돌아오고, 브로커를 두면 요청 경로에 두 번째 시스템이 들어오고, 요청 경로에서 DB 에 쓰면 W1/W2 가 된다.

### 빠른 이유와 위험한 이유가 같은 곳에 있다

W4 가 빠른 이유는 요청 경로에 디스크가 없어서다. W4 가 위험한 이유는 요청 경로에 디스크가 없어서다. 이 실험이 재는 것은 그 하나의 선택이 만드는 **두 개의 수치** — 처리량과 공백 — 다.

## 6. 흔한 오해 · 안티패턴

| 오해 · 안티패턴 | 실제 |
|---|---|
| "Lua 스크립트는 트랜잭션이다" | 끼어들 수 없다는 뜻이지 되돌린다는 뜻이 아니다. 중간에 실패하면 앞의 쓰기가 남는다 (3-5) |
| `DECR` 하고 음수면 `INCR` 로 되돌린다 | 동작은 한다. 그러나 왕복이 2회고, 되돌리는 사이에 남이 음수를 본다. 스크립트 하나면 끝날 일이다 |
| 스크립트 안에서 `TIME` 으로 현재 시각을 읽는다 | 복제본에서 같은 스크립트를 재실행하면 시각이 달라진다. 시각은 `ARGV` 로 넘긴다 — 이 프로젝트가 그렇게 한다 |
| 큐에서 먼저 지우고 DB 에 쓴다 | at-most-once. 쓰기 전에 죽으면 유실. 반대 순서여야 한다 (3-4) |
| 재고는 Redis 에 두고 DB 도 요청 경로에서 쓴다 | 둘의 비용을 다 낸다. 비동기 반영이 아니면 Redis 로 옮긴 의미가 없다 |
| 워커를 여러 인스턴스에서 돌린다 | `LRANGE` + `LTRIM` 은 두 워커가 같은 구간을 읽는다. 여러 개가 필요하면 Streams 의 consumer group 이 답이다. 이 프로젝트는 **한 인스턴스만** 돌린다 (D-06) |
| 명단을 `SMEMBERS` 로 읽어 검사한다 | O(N). 명단이 커지면 Redis 전체가 멈춘다 (3-6). `SISMEMBER` 는 O(1) 이다 |

## 7. 이 프로젝트에서

### W4 구현

```java
public IssueResult issue(long couponId, long userId) {
    long code = tryIssue(couponId, userId);          // Lua 한 번
    if (code == NOT_LOADED) {
        if (!load(couponId)) return IssueResult.COUPON_NOT_FOUND;   // 요청 경로에서 DB 를 만나는 유일한 지점
        code = tryIssue(couponId, userId);
    }
    if (code == ISSUED) return IssueResult.ISSUED;
    ...
}
```

```java
// W4DbSyncWorker — 같은 JVM 의 스레드 하나. W4 일 때만 만든다
@Scheduled(fixedDelay = 100)
public void drain() {
    List<String> items = queue.range(0, BATCH_SIZE - 1);            // LRANGE
    if (items.isEmpty()) return;
    transactionTemplate.executeWithoutResult(status -> {
        int[] inserted = jdbc.batchUpdate("INSERT ... ON CONFLICT DO NOTHING", ...);
```

W0~W3 가 `IssueCore` 를 공유했다면 W4 는 공유하지 않는다 — **본문이 DB 에 없기 때문이다.** 대신 검증 순서와 응답 코드를 스크립트가 그대로 재현한다 (3-2).

### 확정값 (D-06)

| 항목 | 값 | 근거 |
|---|---|---|
| DB 반영 방식 | **Redis 큐 + 앱 내 배치 워커** | 브리프 D-06. 차감과 큐 적재가 원자적이고, 요청 경로에 DB 가 없고, 실패 모드를 감추지 않는다 |
| 아웃박스를 고르지 않은 이유 | 요청 경로에 DB INSERT 가 다시 들어온다 | 경합은 없어도 커넥션은 잡는다. 풀 30 앞에 줄이 생기면 W4 의 정체성이 사라진다 |
| 메시지 큐를 고르지 않은 이유 | 컨테이너·장애 지점·변수가 하나씩 는다 | Redis 판정과 브로커 발행이 원자적이지 않아 어차피 틈이 있고, 브로커의 내구성이 "Redis 장애 시 정합성 공백" 을 **가려** 관측 대상이 사라진다 |
| 워커 | 100ms / 최대 500건, 커밋 후 제거 | 4장 |
| 적재 | 첫 요청이 DB 에서 읽어 없을 때만 씀 | `run-experiment.ps1` 은 앱 기동 **뒤에** Redis 를 `FLUSHALL` 하므로 기동 시 적재는 쓸 수 없다 |
| 3주차 | 워커는 한 인스턴스만 | 워커는 실험 변수가 아니다 |

### 실제로 나간 Redis 명령

**측정값:** `W4ConcurrencyTest` (요청 2,000건, 64 스레드) 실행 중 `redis-cli MONITOR`.

| 확인한 것 | 결과 |
|---|---|
| 발급 스크립트 실행 | **2,128** = 요청 2,000 + 적재 후 재시도 128 |
| 그중 발급 (`HINCRBY`·`SADD`·`RPUSH` 실행) | **101** (재고 100 + NFR-02 의 1) |
| 그중 거절 (`HMGET` 까지만) | 900 (소진) + 999 (중복) + 128 (미적재 → 적재 후 재시도) |
| 적재 스크립트 실행 | 128 — 실제 `HSET` 은 **2** (테스트 메서드당 1) |
| 워커 `LRANGE` / `LTRIM` | 17 / **3** (배치 46, 54, 1) |
| **요청당 Redis 왕복** | **1회** |
| **요청 경로의 DB 접근** | **0** (적재 시 1회 제외) |

W3 와 같은 테스트(1,000건, MONITOR 없이)에서 W0 4.6초, W3 5.5초, **W4 0.5초** — 수렴 대기까지 포함한 시간이다. 측정이 아니라 방향 확인이다.

### 적재 경쟁 — 첫 요청이 스레드 수만큼 DB 를 읽는다

적재 스크립트가 128회 실행됐는데 `HSET` 은 2회다. 테스트 메서드 두 개가 각각 빈 Redis 에서 시작하고, **64개 스레드가 동시에 "미적재"를 받아 전부 DB 를 읽으러 갔다.** 적재는 `EXISTS` 로 막아 한 번만 됐고, 나머지 63개는 헛걸음한 뒤 재시도로 발급됐다.

정합성에는 영향이 없다. 그러나 spike 에서는 톰캣 스레드 200개가 첫 순간에 동시에 DB 를 읽는다. 한 번뿐이고 150,000건 중 200건이라 P99 에는 안 보이겠지만, **첫 1초의 응답 시간 그래프에 튀는 점이 있으면 이것이다.** 고치지 않는다 — 관측한 뒤 결정한다.

### 이 단계에서 확인하려는 것

| 지표 | W3 예상 | **W4 예상** |
|---|---|---|
| `hikaricp_connections_active` | 1.0 | **≈ 0** (워커의 100ms 마다 1개뿐) |
| 처리량 | W0 보다 낮음 | **W0 의 수 배.** 병목이 DB 에서 톰캣 스레드 200 또는 Redis 단일 스레드로 옮겨간다 |
| P99 | W0 보다 나쁨 | **가장 좋음.** 대기가 μs 단위 |
| `coupon_w4_queue_size` | — | 부하 중 쌓였다가 종료 후 0 으로. **워커 5,000건/초 상한**이 발급 속도보다 낮으면 쌓인다 |
| `reflect_wait_s` | — | 큐가 비는 데 걸린 시간. **수 초 이내** 예상. 폴링이 1초 단위라 그만큼의 오차가 있다 |
| chaos 후 | 커밋된 발급은 DB 에 있음 | **k6 의 `coupon_issued` > DB 행 수** — 유실된 만큼 차이. 그 수가 NFR-05 의 측정값 |

**이 예상이 맞는지가 관전 지점이다.** 특히 마지막 줄 — 틀리면(차이가 0 이면) 워커가 죽기 전에 다 옮겼다는 뜻이고 그것도 기록한다 (브리프 작업 규칙 4).

**7단계 축소 실행에서 미리 본 것** (200 VU, 60,000건, 발급 11,441건에서 kill — 정식 측정이 아니라 파이프라인 검증이다):
k6 발급 − DB 행 = **+6,779**, 5xx 384. `verify.sql` 은 초과 0 · drift 0 으로 **깨끗했다.** 6,779명이 "받았다" 는 답을 받았고 서버는 모른다.
유실은 kill 순간의 큐 백로그 전부이고, 백로그가 이만큼 쌓인 것은 **200 VU 에서 이미 워커(100ms / 500건)가 발급 속도를 못 따라갔기 때문**이다. 1,000 VU 정식 측정에서는 더 클 것이다. 워커 용량은 W4 의 설계 변수이므로 그대로 두고 잰다.

### 연결되는 NFR · 메트릭

| | |
|---|---|
| **NFR-01 / NFR-02** | Redis 판정으로 0건. DB 에서도 0건 — 워커의 `ON CONFLICT` 와 실제 INSERT 건수만큼의 카운터 증가가 `verify.sql` 의 `counter_drift` 를 0 으로 만든다 |
| **NFR-03** (P99 ≤ 500ms) | 가장 유리한 전략. 못 지키면 병목은 DB 가 아니라 다른 곳이다 |
| **NFR-04** (소진 후 5xx 0건) | 소진 후 요청은 `HMGET` 한 번으로 끝난다. **가장 싼 거절 경로** |
| **NFR-05** (Redis 장애) | **정합성 공백이 실제로 생기는가**, 생기면 몇 건인가. 이 전략의 존재 이유이자 대가 |
| **NFR-07** (3 인스턴스) | 유지된다. 판정 주체가 Redis 하나라 인스턴스 수와 무관하다 |
| 메트릭 | `coupon_w4_queue_size`, `coupon_w4_reflected_total`, `runs.tsv` 의 `reflect_wait_s`, `verify.sql` 의 `counter_drift` |

### 거절 경로 — 락이 없으니 잡을 것도 없다

W1/W3 는 소진 후에도 락을 잡은 뒤 "품절"을 판정했다. W4 는 같은 스크립트를 실행하지만 `HMGET` 한 번에 `-2` 를 돌려받고 끝난다. 코드 경로는 같은데(5.4 유지) 비용이 다르다 — **거절이 발급보다 싸다.** D-02 에서 문제가 됐던 "거절도 발급만큼 비싸다"는 W4 에서는 성립하지 않는다.
