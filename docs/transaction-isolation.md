# 트랜잭션과 격리 수준

> **한 줄 정의:** 트랜잭션은 여러 작업을 *전부 성공하거나 전부 없던 일이 되는* 한 단위로 묶는 장치이고, 격리 수준은 **동시에 도는 트랜잭션들이 서로의 중간 상태를 얼마나 볼 수 있는지**를 정하는 눈금이다.

---

## 1. 왜 필요한가

이 프로젝트의 발급 본문은 이렇게 생겼다 (`IssueCore.issue()`).

```java
Coupon coupon = couponRepository.findById(couponId);   // ① 조회
if (IssueValidator.soldOut(coupon)) return SOLD_OUT;   // ② 검증
coupon.increaseIssuedCount();                          // ③ 차감
issueRepository.saveAndFlush(new CouponIssue(...));    // ④ 저장
```

읽기 쉽고, 도메인 규칙이 그대로 드러난다. 그리고 **동시 요청 두 개가 들어오면 깨진다.**

재고가 1장 남은 상태에서 A와 B가 동시에 들어온 경우:

```
시각   스레드 A                        스레드 B                     DB의 issued_count
───────────────────────────────────────────────────────────────────────────────────
 t1   ① 조회 → issued_count = 99                                        99
 t2                                   ① 조회 → issued_count = 99        99
 t3   ② 검증 99 < 100  → 통과                                           99
 t4                                   ② 검증 99 < 100  → 통과           99
 t5   ③ 차감 → 100                                                      99
 t6                                   ③ 차감 → 100                      99
 t7   ④ COMMIT                                                         100
 t8                                   ④ COMMIT                         100  ← B가 A를 덮었다
───────────────────────────────────────────────────────────────────────────────────
결과: 발급 행은 2개, issued_count 는 100. 재고 100장인데 101장이 나갔다.
```

이것이 **갱신 손실(lost update)** 이다. A의 `+1` 이 사라졌다.

> **NFR-01 "초과 발급 0건" 이 1건이라도 깨지면 즉시 탈락**이다. 위 코드는 그 조건을 지키지 못한다.

### 여기서 대부분이 걸려 넘어지는 지점

> **"`@Transactional` 을 붙이면 되는 것 아닌가?"**

**아니다.** 위 다이어그램의 ①~④는 **이미 트랜잭션 안에서 실행된 것**이다. 트랜잭션을 걸었는데도 그대로 깨진다.

트랜잭션이 보장하는 것과 보장하지 않는 것이 다르기 때문이다.

| 트랜잭션이 보장하는 것 | 보장하지 않는 것 |
|---|---|
| ③에서 예외가 나면 ①~②도 **없던 일이 된다** (원자성) | 내가 ①을 읽은 뒤 ③을 쓰기까지 **남이 끼어들지 않는 것** |
| 커밋된 데이터만 보인다 (READ COMMITTED 기준) | 내가 읽은 값이 **쓸 때까지 그대로인 것** |

**원자성(A)은 "실패하면 되돌린다"이지 "혼자 쓴다"가 아니다.** 혼자 쓰는 것을 다루는 글자는 A가 아니라 **I(격리성)** 이고, 그 눈금이 격리 수준이다.

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **트랜잭션** | 전부 성공하거나 전부 없던 일이 되는 작업 묶음. `BEGIN` 부터 `COMMIT`/`ROLLBACK` 까지 |
| **격리 수준** | 동시에 도는 트랜잭션이 서로의 중간 상태를 얼마나 볼 수 있는지의 눈금. 4단계 |
| **갱신 손실** | 두 트랜잭션이 같은 값을 읽고 각자 계산해 쓸 때, 나중 쓰기가 앞 쓰기를 **덮어 없애는** 것 |
| **MVCC** | 읽기가 쓰기를 막지 않도록 행마다 **여러 버전**을 두고, 트랜잭션마다 볼 버전을 정하는 방식. PostgreSQL 의 기본 구조 |
| **스냅샷** | 한 트랜잭션이 "이 시점의 DB" 로 보기로 고정한 화면. **떠온 물과 같아서, 떠온 뒤 원본이 바뀌어도 내 그릇의 물은 그대로다** |

## 3. 동작 원리

### 3-1. 표준이 정의한 4단계

격리 수준은 **"이 이상현상을 허용할 것인가"** 로 정의된다.

| 격리 수준 | 더티 리드 | 반복 불가능한 읽기 | 팬텀 리드 |
|---|---|---|---|
| READ UNCOMMITTED | 가능 | 가능 | 가능 |
| **READ COMMITTED** ← PostgreSQL 기본 | 불가 | 가능 | 가능 |
| REPEATABLE READ | 불가 | 불가 | 가능 *(표준)* / **불가** *(PostgreSQL)* |
| SERIALIZABLE | 불가 | 불가 | 불가 |

| 이상현상 | 무슨 일인가 |
|---|---|
| **더티 리드** | 남이 **아직 커밋하지 않은** 값을 읽는다. 그 트랜잭션이 롤백하면 없는 값을 읽은 셈이 된다 |
| **반복 불가능한 읽기** | 같은 행을 두 번 읽었는데 **값이 달라진다** (중간에 남이 커밋) |
| **팬텀 리드** | 같은 조건으로 두 번 조회했는데 **행 개수가 달라진다** (중간에 남이 INSERT) |

### 3-2. 이 표에 갱신 손실이 없다

위 세 가지는 **전부 "읽기" 문제**다. *잘못된 값을 읽었는가.*

그런데 우리 문제는 읽기 문제가 아니다. **A도 B도 99를 정확히 읽었다.** 문제는 *읽고 나서 그 값으로 계산해 쓰는 사이에* 남도 같은 일을 했다는 것이다.

> **갱신 손실은 표준(ANSI SQL-92)이 정의한 3대 이상현상에 들어 있지 않다.**
> 그래서 "격리 수준을 뭘로 해야 막히나?" 라는 질문 자체가 표를 벗어난다.

이것이 이 문서가 존재하는 이유다. **격리 수준만 알고 있으면 이 문제를 못 푼다.**

### 3-3. PostgreSQL 이 실제로 하는 일

PostgreSQL 은 MVCC 기반이라 표준과 다르게 동작하는 부분이 있다.

| 항목 | 실제 |
|---|---|
| READ UNCOMMITTED | **존재하지 않는다.** 지정해도 READ COMMITTED 로 동작한다 |
| 기본값 | **READ COMMITTED** |
| REPEATABLE READ | 스냅샷 격리라서 **팬텀 리드까지 막힌다** (표준보다 강함) |
| SERIALIZABLE | SSI 방식. 충돌을 감지하면 **예외를 던지고 트랜잭션을 죽인다** |

### 3-4. 왜 `UPDATE ... SET x = x + 1` 은 안전한데 우리 코드는 아닌가

READ COMMITTED 에서 **하나의 UPDATE 문**은 갱신 손실이 나지 않는다.

```sql
UPDATE coupon SET issued_count = issued_count + 1 WHERE id = 1;
```

B가 이 문장을 실행할 때 A가 같은 행을 잠그고 있으면, **B는 그 자리에서 멈춰 A의 커밋을 기다린다.** 그리고 A가 커밋하면 **B는 조건을 다시 읽어(re-check) 최신 값 100 에 +1 을 한다.** 스냅샷의 99가 아니라 실제 값 100 을 쓴다.

우리 코드가 깨지는 이유가 여기서 분명해진다.

```
안전한 것:   [읽기 + 쓰기]  ← DB 안에서 한 덩어리. DB가 대기와 재확인을 책임진다
위험한 것:    읽기 ... 쓰기  ← 그 사이가 애플리케이션이다. DB는 둘을 한 덩어리로 보지 않는다
                    ↑
              여기에 남이 들어온다
```

**"조회 → 검증 → 차감" 이라는 코드 모양 자체가 이 틈을 만든다.** 읽은 시점의 값을 애플리케이션 메모리에 들고 있다가 나중에 쓰기 때문이다.

### 3-5. 그럼 격리 수준을 올리면 되는가

REPEATABLE READ 로 올리면 어떻게 되는지 보자.

```
 t1   A: BEGIN (스냅샷 확보) → 조회 99
 t2   B: BEGIN (스냅샷 확보) → 조회 99
 t5   A: UPDATE → 100
 t7   A: COMMIT                                   ✔
 t8   B: UPDATE →  ERROR: could not serialize access
                   due to concurrent update        ✘ 트랜잭션 강제 종료
```

**갱신 손실은 막힌다.** 대신 **B가 죽는다.**

> 격리 수준을 올리면 문제가 *해결되는* 것이 아니라 **문제가 예외로 바뀐다.** 그 예외를 잡아 재시도하는 것은 애플리케이션의 몫이다.
> 그리고 *조건부로 실패시키고 앱이 재시도한다* 는 것은 **낙관적 락(W2)이 하는 일 그 자체**다.

SERIALIZABLE 은 더 넓은 범위의 충돌을 잡아내지만, 그만큼 **더 자주 죽고 더 비싸다.**

**그래서 실무의 선택지는 "격리 수준을 올린다" 가 아니라 네 갈래가 된다.** 이 네 갈래가 곧 이 프로젝트의 비교군이다.

| 접근 | 하는 일 | 이 프로젝트 |
|---|---|---|
| 애플리케이션 안에서 직렬화 | 한 번에 하나만 들어가게 한다 | **W0** (JVM 락) |
| DB 행을 잠근다 | 읽는 순간부터 남을 막는다 | **W1** (`FOR UPDATE`) |
| 충돌하면 다시 한다 | 막지 않고, 덮어쓰기를 감지해 재시도 | **W2** (조건부 UPDATE + 재시도) |
| DB 밖에서 직렬화·원자화 | 경합을 DB 밖으로 옮긴다 | **W3** (분산 락), **W4** (Redis 원자 연산) |

## 4. 실무 설정 기준

| 설정 | 기본값 | 권장 | 근거 |
|---|---|---|---|
| PostgreSQL `default_transaction_isolation` | `read committed` | **바꾸지 않는다** | 올리면 직렬화 실패 예외가 앱 전역에 퍼진다. 특정 트랜잭션만 필요하면 그 자리에서 올린다 |
| Spring `@Transactional(isolation=)` | `DEFAULT` (= DB 기본값) | **DEFAULT 유지** | 전역이 아니라 문제가 되는 지점을 락으로 푼다 |
| 트랜잭션 경계 | — | **최대한 짧게** | 트랜잭션이 열려 있는 동안 커넥션이 점유된다. [`db-connection-pool.md`](db-connection-pool.md) 의 홀딩 시간이 곧 트랜잭션 길이다 |
| 트랜잭션 안의 외부 호출 | — | **금지** | 외부 API 응답이 3초 걸리면 커넥션을 3초 쥔다. 풀 30개면 동시 30건에서 막힌다 |
| 락 해제 시점 | — | **커밋 이후** | 5-2 참조. 이 프로젝트에서 실제로 조심한 지점이다 |

### 격리 수준을 올려야 하는 드문 경우

- **한 트랜잭션 안에서 같은 데이터를 여러 번 읽고 그 값들이 서로 일치해야 할 때** (집계 리포트, 정산 대사)
  → REPEATABLE READ. 스냅샷이 고정되므로 중간에 값이 바뀌지 않는다.
- 그 외에는 **격리 수준이 아니라 락이나 원자 연산으로 푸는 것이 일반적**이다.

## 5. 트레이드오프

| 선택 | 얻는 것 | 잃는 것 | 언제 |
|---|---|---|---|
| **격리 수준 올리기** | 코드를 안 고쳐도 갱신 손실이 막힌다 | 직렬화 실패 예외 처리가 앱 전역에 필요. 실패율이 경합에 비례 | 읽기 일관성이 필요한 트랜잭션에 국한해서 |
| **행 락** (`FOR UPDATE`) | 확실하다. 재시도 로직이 필요 없다 | **락을 기다리는 동안 커넥션을 쥔다** → 풀 고갈 | 경합이 있고, 실패보다 대기가 나은 경우 |
| **조건부 UPDATE + 재시도** | 락 대기가 없다. 경합이 드물면 가장 빠르다 | 경합이 심하면 **재시도가 폭주**해 오히려 느려진다 | 충돌이 드문 경우 |
| **단일 원자 UPDATE** | 읽기-쓰기 왕복 자체가 없다. 가장 단순하고 빠르다 | 도메인 규칙이 SQL 안으로 들어간다. 복잡한 검증은 표현이 어렵다 | 규칙이 한 문장으로 표현되는 경우 |

### 잠깐 — 그냥 단일 UPDATE 한 방이면 되는 것 아닌가

우리 문제는 사실 한 문장으로 쓸 수 있다.

```sql
UPDATE coupon SET issued_count = issued_count + 1
WHERE id = :id AND issued_count < total_quantity;
```

영향 행 수가 0이면 품절. 락도 재시도도 필요 없고, 3-4 에서 본 대로 READ COMMITTED 에서 안전하다. **실무라면 이게 가장 먼저 검토할 답이다.**

그런데 이 프로젝트는 이 형태를 쓰지 않는다.

> 브리프 5.4 — **모든 전략은 동일한 인터페이스를 구현하고, 응답 포맷·검증 로직·로깅이 완전히 동일해야 한다. 비교군 간 차이는 오직 동시성 제어 방식뿐이어야 한다.**

한 전략만 "조회 → 검증 → 차감"을 한 문장으로 접어 버리면, 그 전략이 빠른 이유가 **동시성 제어 방식 때문인지 왕복 횟수가 줄어서인지 구분할 수 없다.** 측정이 오염된다.

그래서 다섯 전략 전부가 `IssueCore` 의 같은 본문을 공유하고, **바깥에서 그 본문을 어떻게 보호하는지만 다르게 한다.** 이건 실무 설계로서의 선택이 아니라 **실험 설계로서의 통제**다. (4주차 리포트에 이 한계를 명시한다.)

## 6. 흔한 오해 · 안티패턴

- **오해:** `@Transactional` 을 붙였으니 동시성 문제는 해결됐다
  → **실제:** 원자성과 격리성은 다른 글자다. 트랜잭션은 *실패하면 되돌린다* 를 보장할 뿐, 같은 행을 남이 동시에 건드리는 것을 막지 않는다. 1장의 다이어그램은 트랜잭션 안에서 일어난 일이다.

- **오해:** 격리 수준을 SERIALIZABLE 로 올리면 다 해결된다
  → **실제:** 해결되는 게 아니라 **예외로 바뀐다.** PostgreSQL 은 충돌을 감지하면 트랜잭션을 죽이고, 재시도는 앱 몫이다. 그리고 그 재시도 구조가 곧 낙관적 락이다.

- **오해:** READ UNCOMMITTED 가 제일 빠르다
  → **실제:** PostgreSQL 에는 그 수준이 **없다.** 지정해도 READ COMMITTED 로 동작한다.

- **오해:** 격리 수준이 높을수록 데이터가 안전하다
  → **실제:** 안전해지는 대신 **실패율이 올라간다.** 죽은 트랜잭션을 재시도하지 않으면 사용자 입장에서는 그냥 실패다. "안전"의 대가를 누가 무는지가 달라질 뿐이다.

- **안티패턴:** 트랜잭션 안에서 외부 API 호출·파일 IO·긴 계산
  → 홀딩 시간이 그만큼 늘어 커넥션 풀이 마른다. 트랜잭션 길이는 **곧 커넥션 점유 시간**이다.

- **안티패턴:** 락을 커밋보다 먼저 푼다
  → 다음 절 참조. 이 프로젝트에서 실제로 조심한 지점이다.

### 락 해제가 커밋보다 빠르면

```java
lock.lock();
try {
    transactionTemplate.execute(status -> core.issue(couponId, userId));
} finally {
    lock.unlock();   // 커밋이 끝난 뒤에 풀린다 — 이 순서가 맞다
}
```

반대로 트랜잭션 **안에서** 락을 풀면 (예: `@Transactional` 메서드 안에서 `unlock()`), 락이 풀린 시점에 커밋은 아직 끝나지 않았다. 그 틈에 들어온 다음 요청은 **아직 반영되지 않은 재고**를 읽는다. 1장의 다이어그램이 그대로 재현된다.

> **임계 구역은 커밋까지 덮어야 한다.** 락의 범위가 트랜잭션의 범위보다 좁으면 락이 없는 것과 같다.

## 7. 이 프로젝트에서

### 실험 A 전체의 전제

W0~W4 는 전부 **1장의 갱신 손실을 어떻게 막을 것인가**에 대한 서로 다른 답이다. 그래서 이 문서는 개별 전략 문서보다 앞에 온다.

| 전략 | 이 문서의 어느 갈래인가 |
|---|---|
| **W0** | 애플리케이션 안에서 직렬화 (JVM 락). 프로세스 경계를 못 넘는다 → 3 인스턴스에서 붕괴 |
| **W1** | DB 행 락. 5장의 "대기 중 커넥션 점유" 가 그대로 실패 모드가 된다 |
| **W2** | 3-5 의 "충돌을 예외로 만들고 재시도". 단, PostgreSQL 의 격리 수준이 아니라 **`version` 컬럼 조건부 UPDATE** 로 직접 구현한다 |
| **W3** | DB 밖(Redis)에서 직렬화 |
| **W4** | DB 밖에서 원자 연산. 경합 자체를 DB 에서 들어낸다 |

### 격리 수준은 전 비교군 공통으로 고정한다

**다섯 전략 모두 PostgreSQL 기본값 READ COMMITTED 에서 돈다.** 전략별로 격리 수준을 다르게 하면 5.4 의 공정성 규칙이 깨져 비교가 성립하지 않는다.

W2 도 마찬가지다. REPEATABLE READ 로 올려 직렬화 실패를 유도하는 대신 **애플리케이션 레벨 `version` 컬럼**을 쓴다. 이유는 두 가지다.

1. 격리 수준을 W2 에서만 바꾸면 **다른 네 전략과 조건이 달라진다**
2. `Coupon` 엔티티에 `@Version` 을 붙이면 JPA 낙관적 락이 **전 전략에 암묵 적용**되어, 이 실험의 하이라이트인 **W0 의 다중 인스턴스 붕괴가 가려진다** (브리프 5.2)

### 연결되는 NFR · 메트릭

| | |
|---|---|
| **NFR-01** 초과 발급 0건 | 갱신 손실이 곧 초과 발급이다. `verify.sql` 의 `over_issue` 로 판정 |
| **NFR-02** 1인 1매 | `UNIQUE (coupon_id, user_id)` 가 최후 방어선. 전략이 못 막은 중복은 `coupon.issue.constraint.violation` 카운터에 잡힌다 |
| 커넥션 홀딩 시간 | **트랜잭션 길이 = 커넥션 점유 시간.** `hikaricp_connections_usage` 로 관측 |

### 측정값 — 트랜잭션 길이가 처리량의 천장이다

**측정값:** 1주차 W0 spike (단일 인스턴스, 풀 30, 200 VU, 총 20,000건)

| 항목 | 값 |
|---|---|
| 처리량 | 256 RPS |
| 평균 응답 시간 | 778 ms |
| 역산한 **직렬 구간** `t` | **3.9 ms** |

```
1 ÷ 256 = 3.9 ms        ← 한 번에 하나씩 통과하는 구간의 길이
200 × 3.9 ms = 780 ms   ≈ 실측 778 ms
```

이 3.9 ms 가 **`BEGIN` 부터 `COMMIT` 까지의 시간**이고, 그 대부분이 커밋 시 WAL 을 디스크에 기록하는 대기다. W0 는 이 구간 전체를 락으로 덮으므로 **`최대 처리량 = 1 ÷ 트랜잭션 길이`** 가 된다. 서버를 늘려도, 동시 접속을 늘려도 이 천장은 올라가지 않는다.

> **트랜잭션을 짧게 하라는 말이 성능 조언이 아니라 산술인 이유가 이것이다.**
