# 낙관적 락 (버전 조건부 UPDATE)

> **한 줄 정의:** 아무것도 잠그지 않고 일단 진행한 뒤, **쓰는 순간 "내가 읽은 뒤로 바뀌었나?"를 확인해서** 바뀌었으면 그 작업을 무효로 하고 처음부터 다시 하는 방식.

---

## 1. 왜 필요한가

[`pessimistic-lock.md`](pessimistic-lock.md) 의 비관적 락은 확실하지만 대가가 있다. **아무도 안 건드릴 때조차 잠근다.**

```
1,000번 수정하는데 그중 충돌이 2번뿐이라면?
→ 998번은 아무 이유 없이 락을 잡고 풀었다
```

낙관적 락은 반대 가정에서 출발한다.

| | 가정 | 하는 일 |
|---|---|---|
| 비관적 락 | *"어차피 충돌한다"* | **미리 막는다** — 읽는 순간 잠근다 |
| 낙관적 락 | *"웬만하면 충돌 안 난다"* | **사후에 확인한다** — 쓸 때 바뀌었는지 본다 |

> **"낙관적 락"은 락이 아니다.** 아무것도 잠그지 않는다. 이름 때문에 생기는 오해가 많다.
> 정확히는 **충돌 감지(conflict detection) + 재시도**다.

---

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **버전 (version)** | 행이 바뀔 때마다 1씩 오르는 숫자. "이 행이 몇 번 수정됐나"를 세는 카운터 |
| **CAS (compare-and-set)** | "값이 아직 X면 Y로 바꿔라"를 **한 번에** 하는 것. 낙관적 락의 핵심 동작 |
| **충돌** | 내가 읽은 버전과 지금 버전이 다른 상태. **영향 행 수 0** 으로 나타난다 |
| **재시도 한계 (N)** | 충돌했을 때 다시 시도할 횟수의 상한. 넘기면 실패로 응답한다 |
| **백오프** | 재시도 전에 잠깐 쉬는 것. 쉬면 DB 부하는 줄고 응답 시간은 길어진다 |

## 3. 동작 원리

### 3-1. 한 문장이 전부다

```sql
UPDATE coupon
   SET issued_count = issued_count + 1,
       version      = version + 1
 WHERE id = 1
   AND version = 5      ← "내가 읽었을 때 5였는데, 아직도 5 맞지?"
```

| 결과 | 뜻 |
|---|---|
| **1행** 영향 | 아무도 안 건드렸다 → 성공 |
| **0행** 영향 | 그 사이 남이 6으로 올렸다 → **충돌. 다시 읽고 다시 시도** |

이 한 문장이 **읽기와 쓰기 사이의 틈**을 없앤다. 조건 검사와 값 변경이 **DB 안에서 한 덩어리**로 일어나기 때문이다 ([`transaction-isolation.md`](transaction-isolation.md) 3-4 참조).

### 3-2. 타임라인

```
시각   트랜잭션 A                          트랜잭션 B
──────────────────────────────────────────────────────────────────────
 t1   SELECT → version = 5
 t2                                       SELECT → version = 5
 t3   UPDATE ... AND version = 5
        → 1행. version 6 이 됨 ✔
 t4   COMMIT
 t5                                       UPDATE ... AND version = 5
                                            → 0행. 아무것도 안 바뀜 ✘
 t6                                       충돌 감지 → 재시도
 t7                                       SELECT → version = 6 (다시 읽는다)
 t8                                       UPDATE ... AND version = 6
                                            → 1행 ✔
──────────────────────────────────────────────────────────────────────
```

**B는 막히지 않았다.** 그냥 아무 일도 안 일어났을 뿐이고, 그걸 **영향 행 수 0** 으로 알아챈다.

### 3-3. 그런데 정말 대기가 없는가 — **교과서와 다른 부분**

"낙관적 락은 대기가 없다"는 설명을 자주 보는데, **단일 행을 경합할 때는 사실이 아니다.**

t5 에서 B의 `UPDATE` 가 실행될 때 A가 아직 커밋하지 않았다면 어떻게 될까?

```
B의 UPDATE → id=1 행을 찾는다
           → 그 행은 A가 잠그고 있다
           → ⏸ 여기서 기다린다 (행 락 대기)
           → A 커밋
           → 깨어나서 조건을 다시 평가한다: version 이 6 이네?
           → 조건 불일치 → 0행 ✘
```

**기다렸다가 실패한다.** PostgreSQL 의 READ COMMITTED 는 갱신 충돌이 나면 앞 트랜잭션을 기다린 뒤 **조건을 재평가**한다.

> 그래서 **모두가 같은 행 하나를 노리는 상황에서 낙관적 락은 최악의 조합**이 된다.
> **대기는 그대로 있는데, 기다린 끝에 얻는 것이 실패다.** 비관적 락은 적어도 기다린 보람이 있다.
>
> 낙관적 락이 유리한 것은 **서로 다른 행을 건드릴 때**다. 그때는 애초에 부딪히지 않는다.

### 3-4. JPA `@Version` 과의 관계

JPA 의 `@Version` 은 위 SQL 을 **자동으로 만들어주는 기능**이다.

```java
@Version
private Long version;   // 이것만 붙이면
```
```sql
-- Hibernate 가 알아서 이렇게 내보낸다
UPDATE coupon SET ..., version = 6 WHERE id = 1 AND version = 5
-- 0행이면 OptimisticLockException 을 던진다
```

편하지만 **엔티티 전체에 적용된다.** 그 엔티티를 쓰는 모든 코드가 낙관적 락을 갖게 된다. 이 프로젝트에서 문제가 되는 지점이며, 7장에서 다룬다.

## 4. 실무 설정 기준

| 설정 | 권장 | 근거 |
|---|---|---|
| **재시도 한계 N** | **3 ~ 5** | 요청 하나가 DB 를 최대 N+1 번 친다. 크게 잡으면 실패율은 조금 내려가는 대신 **DB 부하가 N 배**가 되고 응답 시간이 그만큼 늘어난다 |
| **백오프** | 경합이 심하면 넣는다 (지수 + 지터) | 즉시 재시도는 DB 를 계속 때린다. 다만 쉰 시간만큼 응답이 늦어진다 |
| 재시도 트랜잭션 | **매 시도마다 새로 연다** | 같은 트랜잭션에서 다시 읽으면 스냅샷이 그대로라 **영원히 같은 값**을 읽는다. 무한 루프가 된다 |
| 버전 컬럼 타입 | `BIGINT` | `INTEGER` 는 21억 번 수정되면 넘친다. 핫 로우면 생각보다 가깝다 |

### 언제 쓰고 언제 안 쓰는가

| 상황 | 선택 |
|---|---|
| 서로 다른 행을 수정 (주문, 게시글, 프로필) | **낙관적** — 충돌이 드물어 락 비용이 순수 낭비다 |
| 같은 행 하나에 몰림 (선착순, 재고, 좌석) | **비관적 또는 원자 연산** — 낙관적은 재시도만 폭주한다 |
| 사용자가 화면을 열어놓고 오래 편집 | **낙관적** — 비관적으로 잠그면 그동안 아무도 못 쓴다 |
| 재시도 자체가 위험 (결제, 정산) | **비관적** — 재시도가 중복 처리를 부를 수 있다 |

> 판단 기준은 하나다. **"두 사람이 같은 것을 동시에 건드릴 확률이 얼마나 되는가."**

## 5. 트레이드오프

| 선택 | 얻는 것 | 잃는 것 | 언제 |
|---|---|---|---|
| **낙관적 락** | 충돌이 없으면 **비용이 0**. 락 관리가 없어 데드락도 없다 | 충돌하면 일한 것이 **전부 버려진다.** 경합이 심하면 재시도 폭주 | 충돌이 드물 때 |
| 비관적 락 | 한 번 잡으면 확실히 끝난다. 실패율이 낮다 | 대기 중 커넥션 점유. 데드락 위험 | 경합이 잦을 때 |

### 순위가 뒤집히는 지점

```
충돌률 낮음 ────────────────────────────► 충돌률 높음

  낙관적이 빠르다          교차점            비관적이 빠르다
  (락 비용 0)                               (재시도 낭비 없음)
```

**"낙관적이 빠르다"는 조건부 명제다.** 경합이 심해지면 반드시 뒤집힌다.

이유는 단순하다. 비관적 락에서 기다린 요청은 **기다린 뒤 성공**하지만, 낙관적 락에서 충돌한 요청은 **한 일을 전부 버리고 처음부터 다시 한다.** 경합이 심해질수록 버려지는 일의 양이 기하급수로 는다.

> **이 교차점이 어디인지를 숫자로 보이는 것**이 실험 A 의 목적 중 하나다 (브리프 2장 질문 2).

## 6. 흔한 오해 · 안티패턴

- **오해:** 낙관적 락도 락이니까 뭔가 잠근다
  → **실제:** 아무것도 잠그지 않는다. 읽을 때도 쓸 때도 잠금이 없다. **버전을 비교할 뿐**이다.

- **오해:** 낙관적 락은 대기가 없어서 빠르다
  → **실제:** 같은 행을 경합하면 `UPDATE` 가 **행 락에서 대기한다.** 기다린 끝에 실패까지 한다 (3-3).

- **오해:** 재시도 횟수를 넉넉히 잡으면 실패가 없어진다
  → **실제:** 실패가 줄어드는 만큼 **DB 부하와 응답 시간이 그대로 늘어난다.** 경합 자체는 그대로다. 공짜가 없다.

- **오해:** `@Version` 을 붙이면 안전해진다
  → **실제:** 붙인 **엔티티 전체**가 낙관적 락을 갖는다. 그 엔티티를 쓰는 다른 코드의 동작까지 바뀐다.

- **안티패턴:** 같은 트랜잭션 안에서 재시도
  → 스냅샷이 고정돼 있어 **다시 읽어도 같은 값**이다. 영원히 충돌한다. **트랜잭션을 닫고 다시 열어야** 한다.

- **안티패턴:** 충돌을 예외로 던져놓고 아무도 안 잡는다
  → 사용자가 500 을 받는다. 충돌은 **정상적인 흐름**이지 장애가 아니다.

- **안티패턴:** 재시도 전에 부수효과(외부 API 호출, 메일 발송)를 이미 실행했다
  → 재시도할 때마다 중복 실행된다. **부수효과는 성공이 확정된 뒤에.**

## 7. 이 프로젝트에서

### `@Version` 을 쓰지 않는 이유

```java
// Coupon.java
// W2 낙관적 락용 — @Version 이 아니라 평범한 컬럼이다
@Column(nullable = false)
private long version;
```

`@Version` 을 붙이면 **W0~W4 전부**가 낙관적 락을 갖게 된다. 그러면 이 실험의 하이라이트가 사라진다.

> 3 인스턴스 환경에서 **W0 는 깨져야 한다.** 각 JVM 이 자기 안에서만 상호 배제하므로 초과 발급이 나야 한다 (브리프 5.2).
> 그런데 `@Version` 이 붙어 있으면 두 JVM 이 같은 버전을 읽고 각자 UPDATE 할 때 **한쪽이 자동으로 튕긴다.** W0 가 안 깨진다.
>
> **"분산 락이 왜 필요한가"를 W0 가 깨지는 숫자로 증명하는 것**이 이 프로젝트의 목적인데, `@Version` 한 줄이 그 증거를 지워버린다.

그래서 버전 컬럼은 두되 매핑은 평범한 컬럼으로 하고, **W2 만** 조건부 UPDATE 로 이 값을 쓴다.

### 구현

```java
// W2OptimisticLockStrategy
for (int retry = 0; ; retry++) {
    IssueResult result = attempt(couponId, userId);
    if (result != IssueResult.CONFLICT || retry == MAX_RETRY) {
        return result;
    }
    // 백오프 없음 — 대기 시간을 넣으면 비교군 간 새 변수가 된다
    metrics.recordRetry();
}
```

```java
// 매 시도마다 새 트랜잭션 — 같은 트랜잭션에서 다시 읽으면 스냅샷이 그대로다
private IssueResult attempt(long couponId, long userId) {
    return transactionTemplate.execute(status ->
            core.issue(couponId, userId, coupon ->
                    couponRepository.increaseIfVersionMatches(coupon.getId(), coupon.getVersion()) == 1));
}
```

**확정값**

| 항목 | 값 | 근거 |
|---|---|---|
| 재시도 한계 N | **3** (최대 4회 시도) | 크게 잡으면 재시도 폭주가 실패율에 가려져 **관측 대상 자체가 사라진다.** 실행 시간도 예측 불가능해진다 |
| 백오프 | **없음** (즉시 재시도) | "몇 ms 쉬었나"가 새 변수가 되어, W2 가 느린 이유가 재시도 때문인지 백오프 때문인지 구분할 수 없게 된다 |

### 실제로 나간 SQL

```sql
update coupon c1_0
   set issued_count = (c1_0.issued_count+1),
       version      = (c1_0.version+1)
 where c1_0.id = ? and c1_0.version = ?
```

JPQL 벌크 UPDATE 라 영속성 컨텍스트를 거치지 않고 그대로 나간다. 3-1 의 형태와 일치한다.

### 측정값 — 재시도 폭주를 눈으로 확인했다

**측정값:** `W2ConcurrencyTest` (요청 2,000건 = NFR-01 1,000 + NFR-02 1,000, 스레드 64, 재고 100, N=3)

| 항목 | 값 |
|---|---|
| 발급 성공 (INSERT) | **101** |
| 조건부 UPDATE 실행 | **2,205** |
| → 그중 충돌(0행) | **2,104** |
| 시도 횟수 (쿠폰 조회) | **3,637** |
| → 그중 재시도 | **1,637** |
| **발급 1건당 UPDATE 횟수** | **약 21.8회** |

> **쿠폰 한 장을 발급하려고 DB 에 UPDATE 를 22번 날렸다.** 그중 21번은 버려졌다.
> 이것이 브리프 5.1 이 예상한 **"동시성이 높을수록 재시도 폭주"** 다.
>
> 그리고 이건 **스레드 64개짜리 테스트**다. 정식 측정은 VU 1,000 이므로 이 비율은 더 나빠진다.

**정합성은 지켜졌다.** 초과 발급 0건, 중복 발급 0건. 버전 CAS 가 한 버전당 승자를 한 명으로 제한하므로 `issued_count` 가 재고를 넘을 수 없다.

### 2단계에서 열어둔 쟁점 — 테스트에서는 안 났고, 실제 측정에서 났다

공통 테스트가 `발급 수 == 재고` 를 단언하는데, **W2 는 재시도를 소진하면 정당하게 미달 발급할 수 있다**고 우려했다.

**테스트에서는 일어나지 않았다.** 요청이 재고의 10배(1,000 : 100)이기 때문이다. 어떤 요청이 재시도를 다 써서 포기해도 **뒤이은 요청이 남은 재고를 마저 가져간다.** 매 라운드에 승자가 한 명씩 나오므로 재고는 결국 소진된다.

**그러나 정식 측정(spike)에서는 났다.** 경합비가 1.5 : 1(요청 150,000 : 재고 100,000)이기 때문이다.

| spike 3회 | 발급된 재고 |
|---|---|
| 1회차 | 56,974 |
| 2회차 | 59,278 |
| 3회차 | 59,495 |

**재고 100,000 중 약 58,600 만 팔렸다.** 다섯 전략 중 유일하게 매진에 실패했다. 나머지 넷은 세 번 모두 정확히 100,000 이다.

> 왜 갈렸나 — 미달 발급이 나려면 **재고가 남았는데 남은 요청 전원이 재시도를 소진**해야 한다.
> 요청이 재고의 10배면 뒤에 줄이 길어 그런 일이 없지만, 1.5배면 요청이 먼저 바닥난다.
> **"테스트에서 안 났다" 가 "안 난다" 는 뜻이 아니었다.** 조건이 달랐을 뿐이고, 그 조건 차이를
> 미리 알아채지 못했다.

### 정식 측정 — 재시도 비율은 부하가 길수록 나빠진다

**측정값:** 2주차 정식 측정 (1,000 VU / 200 VU, 각 3회)

| | 발급 | CONFLICT | 재시도 | **발급 1건당 재시도** |
|---|---|---|---|---|
| ramp (200~2,000 VU) | 37,860 | 62,452 | 234,534 | **6.2회** |
| spike (1,000 VU) | 59,340 | 92,468 | 352,824 | **5.9회** |
| **soak (200 VU, 30분)** | 44,696 | 149,150 | 493,694 | **11.0회** |

동시성이 가장 낮은 soak 에서 비율이 가장 나쁘다. 동시에 몰리는 양보다 **얼마나 오래 경합이 이어지느냐**가
더 크게 작용한다는 뜻이다. 실제로 soak 30분에서 W2 는 3회 모두 5 ~ 10분 만에 꺾여 **초당 12 ~ 13건**으로
주저앉았다(−79.6% ± 2.2). 그 상태에서는 **발급(44,424)보다 5xx(17,954)가 40% 에 이른다.**

| | 처리량 (soak) | NFR-03 (1,000 VU P99) | NFR-06 |
|---|---|---|---|
| W2 | **117/s** (W0 의 41%) | 8,906 ms — 미달 | **미달** (3/3 재현) |

**정합성은 끝까지 지켜졌다.** 47회 측정 전부 초과 0 · 중복 0. 버전 CAS 는 제 일을 했다 —
문제는 그 일을 하기 위해 치른 비용이다. 전체 결과는 [`results/week2-experiment-a/summary.md`](../results/week2-experiment-a/summary.md).

> 다른 전략의 NFR-06 미달이 "환경이 만든 한 계단" 이라면 W2 의 것은 **전략이 만든 붕괴**다.
> 셋 다 "미달" 이지만 성질이 다르므로 리포트에서 구분해 쓴다.
