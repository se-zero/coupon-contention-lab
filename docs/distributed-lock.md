# 분산 락 (Redisson `RLock`)

> **한 줄 정의:** 잠금을 **프로세스 밖의 공유 저장소(Redis)** 에 두어, 서버가 몇 대든 **같은 열쇠 하나**를 놓고 줄을 서게 하는 방식.

---

## 1. 왜 필요한가

W0(JVM 로컬 락)의 문제는 락이 **자기 프로세스 안에만** 있다는 것이다.

```
서버 A  [ReentrantLock A]  ──┐
서버 B  [ReentrantLock B]  ──┼──▶  coupon 행 하나
서버 C  [ReentrantLock C]  ──┘

A 의 락은 B 를 막지 못한다. 열쇠가 세 개다.
```

서버가 한 대일 때는 아무 문제 없다. 두 대가 되는 순간 각 서버가 "나는 락을 잡았다"고 믿으며 **동시에** 같은 행을 고친다. 갱신 손실이 그대로 돌아온다 ([`transaction-isolation.md`](transaction-isolation.md) 1장).

해법은 단순하다. **열쇠를 모두가 보는 곳에 하나만 둔다.**

| 열쇠를 두는 곳 | 이름 | 비고 |
|---|---|---|
| DB 행 자체 | 비관적 락 (W1) | 이미 공유 저장소다. 별도 시스템이 필요 없다 |
| **Redis** | **분산 락 (W3)** | DB 밖에 열쇠를 둔다. 이 문서 |
| ZooKeeper / etcd | 분산 락 | 합의 알고리즘 기반. 더 강한 보장, 더 느림 |

**"분산 락"은 락이 분산되어 있다는 뜻이 아니다.** 반대다 — **분산된 프로세스들이 공유하는 락 하나**라는 뜻이다.

> 그러면 W1 이 이미 분산 락 아닌가? 맞다. DB 행 락은 인스턴스 수와 무관하게 성립한다 (브리프 5.2). W3 의 차이는 **잠금과 트랜잭션이 서로 다른 시스템에 있다**는 것이고, 그 분리가 만드는 비용과 위험이 이 문서의 주제다.

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **락 키** | Redis 키 하나가 곧 락이다. 이 프로젝트는 `coupon:lock:{couponId}` |
| **소유자 식별자** | 클라이언트 UUID + 스레드 ID. **남의 락을 풀지 못하게** 하는 장치 |
| **leaseTime (TTL)** | 락의 만료 시간. 소유자가 죽어도 락이 영원히 남지 않게 한다 |
| **watchdog** | leaseTime 대신, 소유자가 살아 있는 동안 만료를 **자동 연장**하는 백그라운드 작업 |
| **waitTime** | 락을 못 잡았을 때 얼마나 기다릴지. 넘기면 포기한다 |
| **원자성** | "없으면 만든다"가 한 번에 일어나야 한다. Redis 는 단일 스레드라 명령 하나는 원자적이고, 여러 단계는 Lua 로 묶는다 |

> 비관적 락에서 가장 중요한 사실이 *"락을 푸는 명령은 없다"* 였다면, 분산 락에서 가장 중요한 사실은 **"락을 푸는 것도, 안 풀리게 하는 것도, 커밋과 맞추는 것도 전부 내 코드의 책임이다"** 이다. DB 가 대신 해주던 일이 전부 애플리케이션으로 넘어온다.

## 3. 동작 원리

### 3-1. 가장 단순한 형태 — `SET key value NX PX ttl`

```
서버 A ──▶ SET coupon:lock:1 "A" NX PX 30000  ──▶ OK      (락 획득)
서버 B ──▶ SET coupon:lock:1 "B" NX PX 30000  ──▶ (nil)   (실패, 이미 있음)
```

`NX` = 없을 때만 만든다. Redis 가 명령을 한 번에 하나씩 처리하므로 둘 중 **정확히 하나만** OK 를 받는다. 이것이 상호 배제의 전부다.

해제는 `DEL` 인데, **내 락인지 확인하고 지워야** 한다. 확인과 삭제 사이에 내 락이 만료되고 남이 잡았다면, 남의 락을 지우게 된다. 그래서 Lua 로 묶는다.

```lua
if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) end
```

### 3-2. Redisson 이 실제로 하는 일 — 관측한 스크립트

`W3ConcurrencyTest` 실행 중 `redis-cli MONITOR` 로 잡은 스크립트는 정확히 3개다. (Redisson 3.52.0)

**락 획득**

```lua
if ((redis.call('exists', KEYS[1]) == 0)
    or (redis.call('hexists', KEYS[1], ARGV[2]) == 1)) then   -- 비어 있거나 내 것이면
    redis.call('hincrby', KEYS[1], ARGV[2], 1);                 -- 재진입 카운트 +1
    redis.call('pexpire', KEYS[1], ARGV[1]);                    -- 만료 설정
    return nil;                                                 -- 성공
end;
return redis.call('pttl', KEYS[1]);                             -- 실패: 남은 만료 시간
```

문자열이 아니라 **해시**다. `{소유자ID: 재진입횟수}`. `ReentrantLock` 처럼 같은 스레드가 다시 잡을 수 있다.

**락 해제**

```lua
local val = redis.call('get', KEYS[3]);                         -- 해제 래치 (중복 호출 방지)
if val ~= false then return tonumber(val); end;
if (redis.call('hexists', KEYS[1], ARGV[3]) == 0) then return nil; end;  -- 내 것이 아니면 거부
local counter = redis.call('hincrby', KEYS[1], ARGV[3], -1);
if (counter > 0) then                                           -- 재진입 남음
    redis.call('pexpire', KEYS[1], ARGV[2]);
    redis.call('set', KEYS[3], 0, 'px', ARGV[5]); return 0;
else                                                            -- 완전 해제
    redis.call('del', KEYS[1]);
    redis.call('publish', KEYS[2], ARGV[1]);                    -- 대기자에게 알림
    redis.call('set', KEYS[3], 1, 'px', ARGV[5]); return 1;
end;
```

**만료 연장 (watchdog)**

```lua
for i = 1, #KEYS, 1 do
    if (redis.call('hexists', KEYS[i], ARGV[i + 1]) == 1) then   -- 아직 내 것이면
        redis.call('pexpire', KEYS[i], ARGV[1]);                  -- 만료 연장
    end;
end;
```

### 3-3. 대기는 어떻게 하나 — 폴링이 아니라 pub/sub

락을 못 잡은 클라이언트가 계속 `SET NX` 를 던지면 Redis 가 그 폭탄을 다 받는다. Redisson 은 다르게 한다.

```
1. 획득 시도 → 실패 (남은 만료 시간을 받음)
2. 락 채널 SUBSCRIBE → 로컬 세마포어에서 잠든다
3. 소유자가 unlock → 스크립트 안의 PUBLISH
4. 메시지를 받은 클라이언트가 깨어나 1 로 돌아간다
```

**구독은 JVM 당 1개다.** 대기 스레드 200개가 각자 구독하는 게 아니라, 같은 락을 기다리는 스레드들이 하나의 구독을 공유하고 메시지 하나에 **한 스레드만** 깨운다. 관측값에서 `SUBSCRIBE` 가 테스트 메서드당 1회(총 2회)뿐인 것이 그 증거다.

그래도 깨어난 스레드가 반드시 잡는다는 보장은 없다. 그 사이 **새로 도착한** 요청이 먼저 `SET NX` 를 성공시킬 수 있다 (비공정 락, `ReentrantLock` 기본값과 같다). 관측값: **획득 1건당 시도 2.7회.** 자세한 수치는 7장.

### 3-4. 락 수명과 트랜잭션 수명 — 이 프로젝트의 핵심 주의점

W1 에서는 DB 가 락과 트랜잭션을 **함께** 관리했다. 커밋 전에 락이 풀리는 일은 원리적으로 불가능했다.

W3 는 다르다. **락은 Redis 에, 트랜잭션은 PostgreSQL 에** 있다. 둘의 순서를 지키는 것은 코드의 책임이다.

```
올바른 순서
  lock ──▶ tx begin ──▶ 읽기 ──▶ 차감 ──▶ commit ──▶ unlock
  └──────────────── 락 구간 ──────────────────────┘
                    └───── 트랜잭션 구간 ─────┘

잘못된 순서 (leaseTime 이 트랜잭션보다 짧을 때)
  lock ──▶ tx begin ──▶ 읽기 ──▶ [락 만료] ──▶ 차감 ──▶ commit
                                    ↑
                          여기서 남이 lock 성공 → 두 트랜잭션이 같은 값을 읽는다
```

leaseTime 을 5초로 주고 DB 가 6초 걸리면 정합성이 깨진다. **소리 없이** 깨진다 — 예외도, 로그도 없다. 그래서 계획서에 "관측 대상이 아니라 버그"라고 못 박았다.

watchdog 이 이 문제를 없앤다. leaseTime 을 주지 않으면 Redisson 이 `lockWatchdogTimeout`(기본 30초)으로 잡고 **10초마다 연장**한다. `unlock()` 전에는 절대 만료되지 않고, JVM 이 죽으면 연장이 멈춰 30초 뒤 소멸한다. 트랜잭션이 얼마나 걸리든 안전하다.

### 3-5. 그래도 완벽하지 않다 — 만료된 줄 모르는 소유자

watchdog 도 못 막는 경우가 있다. 소유자가 **멈췄다가** 다시 움직이는 경우다.

```
서버 A: lock ──▶ [GC 정지 40초] ──▶ 차감 ──▶ commit ──▶ unlock
                      ↑ 30초에 락 만료, 서버 B 가 획득
                                         ↑ A 는 자기 락이 아직 있는 줄 알고 진행
```

Redis 락은 **"내가 락을 쥐고 있다"는 믿음**과 **실제 락 상태**가 어긋날 수 있다. 완전한 해법은 락에 단조 증가 번호(fencing token)를 붙여 저장소가 오래된 번호를 거부하게 하는 것인데, 그러면 저장소가 락을 이해해야 한다 — 결국 W1 이다.

> 이 프로젝트에서 이 틈은 DB 의 `UNIQUE(coupon_id, user_id)` 가 **중복(NFR-02)** 만 막아준다. **초과 발급(NFR-01)** 은 막지 못한다. 이것이 chaos 시나리오(NFR-05)가 W3 에서 들여다보려는 지점이다.

## 4. 실무 설정 기준

| 설정 | 기준 |
|---|---|
| **waitTime** | 요청이 견딜 수 있는 시간 이내. 정상 줄서기 길이의 몇 배로 잡아 **고장일 때만 걸리게** 한다. 너무 짧으면 멀쩡한 요청이 실패하고, 너무 길면 고장 시 스레드가 갇힌다 |
| **leaseTime** | 임계 구역의 시간 상한을 **확실히 알 때만** 명시한다. 트랜잭션·외부 호출이 안에 있으면 상한을 모르는 것이다 → watchdog |
| **락 키 단위** | 경합하는 자원 단위. 쿠폰별 락이지 전역 락이 아니다. 단위가 크면 무관한 요청끼리 줄을 선다 |
| **재진입** | 필요 없으면 없는 게 단순하다. Redisson `RLock` 은 기본이 재진입이다 |
| **클라이언트 설정** | 커넥션 풀·명령 타임아웃·재시도. 이 프로젝트는 **기본값**(풀 64, 타임아웃 3초, 재시도 3회) — 튜닝하면 비교군 간 새 변수가 된다 |

### 반드시 지킬 세 가지

1. **`unlock()` 은 `finally` 에서.** 예외가 나면 락이 남는다. watchdog 이 있어도 30초다.
2. **커밋 뒤에 `unlock()`.** `@Transactional` 메서드 **안에서** lock/unlock 을 하면 unlock 이 커밋보다 먼저 실행된다 (6장).
3. **소유자 확인 없는 `DEL` 금지.** 3-1 의 Lua 가 이것이다. Redisson 은 해시의 소유자 필드로 검사한다.

## 5. 트레이드오프

| | W0 로컬 락 | W1 DB 행 락 | W3 분산 락 |
|---|---|---|---|
| 잠금 주체 | JVM | PostgreSQL | Redis |
| 인스턴스 확장 | **깨진다** | 유지 | 유지 |
| 요청당 추가 왕복 | 0 | 0 (조회에 포함) | **Redis 3~4회** |
| 대기 중 점유 | 스레드 | 스레드 + **DB 커넥션** | 스레드 (DB 커넥션 없음) |
| 락 수명 관리 | JVM 이 | DB 가 (커밋과 동일) | **코드가** (watchdog) |
| 장애 지점 | — | DB | DB + **Redis** |

### 이 방식의 진짜 비용 — 장애 지점이 하나 더 생긴다

Redis 가 죽으면 락을 잡을 수 없다. 두 갈래뿐이다.

- **실패시킨다** — 요청이 전부 5xx. 가용성 손실.
- **락 없이 진행하거나 다른 락으로 대체한다** — 정합성 손실. 그리고 이 순간 W3 는 더 이상 W3 가 아니다.

이 프로젝트는 앞쪽을 택한다 (7장). 뒤쪽을 택하면 chaos 시나리오에서 관측하는 것이 W3 가 아니라 대체 전략이 된다.

### 대기가 DB 밖에서 일어난다 — W1 과 반대

W1 의 진짜 비용은 **락 대기 중 DB 커넥션을 쥔다**는 것이었다 ([`pessimistic-lock.md`](pessimistic-lock.md) 5장). W3 는 락을 잡은 **뒤에야** 트랜잭션을 연다. 대기하는 199개 스레드는 DB 커넥션을 하나도 쥐지 않는다.

```
W1:  락 대기 29건이 커넥션 29개를 쥔 채 정지  →  풀 30 이 가득 참
W3:  락 대기 199건은 Redis 채널에서 대기      →  커넥션은 1개만 사용 중 (W0 와 같은 모양)
```

단일 인스턴스에서 W3 는 **W0 의 직렬화에 Redis 왕복만 얹은 것**이다. 이것이 브리프 5.2 가 말하는 "근거 없이 느린 선택지처럼 보인다"의 정체다. 정당화는 3주차에 W0 가 깨질 때 온다.

## 6. 흔한 오해 · 안티패턴

| 오해 · 안티패턴 | 실제 |
|---|---|
| "Redis 락을 잡았으니 DB 트랜잭션은 필요 없다" | 락은 **순서**를, 트랜잭션은 **원자성과 롤백**을 준다. 차감 뒤 INSERT 가 실패하면 되돌려야 한다. 둘 다 필요하다 |
| `@Transactional` 메서드 안에서 `lock()` / `unlock()` | Spring 트랜잭션 프록시가 메서드 **바깥**에 있다. `unlock()` 이 `commit` 보다 **먼저** 실행되어 3-4 의 경합 창이 열린다. 가장 흔한 실수다 |
| leaseTime 을 넉넉히 주면 안전하다 | 안전은 하다. 대신 소유자가 죽으면 **그 시간만큼 전원이 대기**한다. 안전과 복구 시간의 교환이다 |
| `SET NX` 뒤에 `EXPIRE` 두 명령 | 사이에 클라이언트가 죽으면 만료 없는 락이 남는다. `SET NX PX` 한 명령이거나 Lua 여야 한다 |
| 소유자 확인 없이 `DEL` | 내 락이 만료된 뒤 남이 잡았다면 남의 락을 지운다. 3-1 참조 |
| Redis 장애 시 로컬 락으로 대체 | 대체하는 순간 인스턴스 간 상호 배제가 사라진다. 조용히 W0 가 된다 |
| Redis 락이면 W1 보다 빠르다 | 단일 인스턴스에서는 **더 느리다.** 왕복이 추가될 뿐 직렬화 정도는 같다 (5장) |

## 7. 이 프로젝트에서

### W3 구현

```java
@Override
public IssueResult issue(long couponId, long userId) {
    RLock lock = redisson.getLock("coupon:lock:" + couponId);
    try {
        // leaseTime 없음 — watchdog 이 unlock 까지 자동 연장한다
        if (!lock.tryLock(WAIT_SECONDS, TimeUnit.SECONDS)) {
            return IssueResult.LOCK_TIMEOUT;
        }
    } catch (InterruptedException e) { ... }
    try {
        // 커밋까지 락 유지
        return transactionTemplate.execute(status -> core.issue(couponId, userId));
    } finally {
        lock.unlock();
    }
}
```

W0 의 `lock.lock()` 자리에 `tryLock(3초)` 가, `ReentrantLock` 자리에 `RLock` 이 들어갔다. 본문 `core.issue()` 와 `TransactionTemplate` 으로 감싸는 구조는 W0 와 글자 단위로 같다. **감싸는 열쇠만 바뀌었다.**

### 확정값

| 항목 | 값 | 근거 |
|---|---|---|
| 락 대기 한계 | **3초** | 정상 줄서기 최대 ≈ 톰캣 200 × 4ms ≈ 1초대. 3초는 그 두세 배 — 평소엔 안 걸리고 고장일 때만 걸린다. 비교군 간 조건은 사실상 같다 |
| 초과 시 응답 | **503 + `LOCK_TIMEOUT`** | 아래 참조 |
| leaseTime | **없음 (watchdog)** | 3-4. 트랜잭션보다 짧은 leaseTime 은 버그다 |
| Redis 장애 시 | **예외를 잡지 않는다** | 5장. 대체하면 전략이 바뀐다. catch-all 이 500 으로 내리고 NFR-05 는 장애 **후** 정합성을 본다 |
| 클라이언트 설정 | Redisson 3.52.0 기본값 | 4장 |

**429 가 아니라 503 인 이유.** 처음 추천은 429 였다 — 5xx 를 피해 NFR-04(소진 후 5xx 0건) 판정을 지키려는 의도였다. 그런데 429 는 *클라이언트가* 너무 많이 보냈다는 코드다. 여기서는 클라이언트가 한 번 보냈을 뿐이고 **서버가 못 받은 것**이므로 503 이 맞다.

더 중요한 것은 NFR-04 의 뜻이다. "소진 후에도 **정상 응답**"은 매진된 쿠폰을 요청한 사람에게 매진이라고 답해주는 것이다. 락 타임아웃은 그 답을 못 한 것이다. 4xx 로 포장하면 코드만 4xx 고 실제로는 미달인 상태 — **판정을 피하려고 코드를 고른 것**이 된다. 그래서 503 그대로 두고, `IssueResult` 에 넣어 `result=LOCK_TIMEOUT` 으로 따로 센다. 소진 후 구간에 이것이 나오면 W3 는 NFR-04 미달로 기록한다. 그것이 W3 의 진짜 얼굴이다.

### 실제로 나간 Redis 명령

**측정값:** `W3ConcurrencyTest` (요청 2,000건) 실행 중 테스트 컨테이너에 `redis-cli MONITOR` 를 붙였다. 부착 시점 이후 **1,877건의 발급 요청**이 잡혔다.

| 확인한 것 | 결과 |
|---|---|
| 락 획득 (성공) | **1,877** |
| 락 획득 스크립트 호출 | **5,103** — **획득 1건당 2.7회** |
| 그중 실패 (`PTTL` 반환) | 3,226 |
| 락 해제 스크립트 호출 | 1,877 (= `PUBLISH` 1,877) |
| watchdog 연장 스크립트 호출 | **1,175** |
| `SUBSCRIBE` | **2** (테스트 메서드당 1회 — JVM 당 구독 1개) |
| 요청 경로의 Redis 왕복 | **획득 1건당 약 3.7회** (시도 2.7 + 해제 1) |

**획득 1건당 시도 2.7회**는 3-3 의 비공정성이다. 깨어난 스레드가 새로 도착한 스레드에게 지고 다시 잠드는 일이 평균 1.7번 일어났다. 이 재시도는 Redis 왕복이므로 응답 시간에 그대로 들어간다.

### watchdog 이 예상보다 자주 뛴다

10초마다 연장한다면 30초짜리 테스트에서 연장은 몇 번이어야 한다. **1,175회**가 나왔다.

Redisson 3.52.0 의 `RenewalTask` 를 확인한 결과: 락을 획득할 때마다 10초 뒤 타이머를 **새로** 걸고, 해제할 때 그 타이머를 **취소하지 않는다.** 10초 뒤 타이머가 깨어나면 그 시점에 이 JVM 이 쥔 락이 있는지 보고, 있으면 연장한다. 경합 상황에서는 거의 항상 누군가 락을 쥐고 있으므로 타이머 대부분이 실제 명령을 보낸다 — 1,175회 중 946회가 `PEXPIRE` 를 실행했다.

요청 경로 밖(비동기)이라 **응답 시간에는 들어가지 않는다.** 그러나 Redis 명령 수에는 들어간다. 측정에서 `redis_commands_processed_total` 을 볼 때 **획득 1건당 약 0.6회의 백그라운드 명령**이 섞여 있다고 읽어야 한다.

> 문서에 "watchdog 이 10초마다 연장한다"고 쓰고 넘어갔다면 이 수치를 설명하지 못했을 것이다. W1 에서 `for no key update` 를 로그로 잡은 것과 같은 교훈이다 — **구현 → 관측 → 문서** 순서를 지킨다.

### 이 단계에서 확인하려는 것

W1 의 관전 지점이 커넥션 풀이었다면, W3 는 **풀이 압박받지 않는데 느린가**이다.

| 지표 | W0 실측 (1주차) | W1 예상 | **W3 예상** |
|---|---|---|---|
| `hikaricp_connections_active` | 1.0 | 30 | **1.0 (W0 와 같은 모양)** |
| `hikaricp_connections_pending` | 0.0 | 동시성 − 30 | **0.0** |
| 처리량 | 256 RPS | 비슷 | **W0 보다 낮음** (왕복 3.7회 ≈ +1~2ms) |
| Redis 명령 수 | — | — | 요청당 약 4.3회 (경로 3.7 + watchdog 0.6) |
| `LOCK_TIMEOUT` | — | — | **0건** 이어야 한다. 나오면 대기 한계가 잘못됐거나 고장이다 |

참고로 같은 테스트(1,000건, 64 스레드)에서 W0 는 4.6초, W3 는 5.5초가 걸렸다. 측정이 아니라 방향 확인이다.

**이 예상이 맞는지가 관전 지점이다.** 틀리면 그것도 결과다 — 그대로 기록한다 (브리프 작업 규칙 4).

**7단계 축소 실행에서 미리 본 것** (200 VU, 20,000건, 발급 5,053건에서 Redis kill → 10초 뒤 빈 상태 재시작 — 파이프라인 검증이다):
k6 발급 − DB 행 = **−1**, 5xx 563. 정전 중 요청은 실패했고 살아난 뒤 정상 재개됐다. −1 은 kill 순간 락을 쥐고 있던 요청 하나 — 트랜잭션은 커밋됐는데 `unlock()` 이 실패해 클라이언트는 500 을 받았다. **DB 에는 있고 사용자는 못 받은 줄 아는** 1건. W4 의 유실과 방향이 반대다.

### 연결되는 NFR · 메트릭

| | |
|---|---|
| **NFR-01 / NFR-02** | 단일 인스턴스에서 0건이어야 한다. 테스트 통과가 그 증거다 |
| **NFR-03** (P99 ≤ 500ms) | 락 대기 + Redis 왕복이 응답 시간에 쌓인다. W0 대비 얼마나 밀리는지를 `ramp` 로 본다 |
| **NFR-04** (소진 후 5xx 0건) | `LOCK_TIMEOUT` 이 나오면 미달. 위 확정값 참조 |
| **NFR-05** (Redis 장애) | 장애 중 500 은 예상된 비용. 판정은 장애 **후** 초과·중복 0건 — 3-5 의 틈이 실제로 열리는지 본다 |
| **NFR-07** (3 인스턴스) | **W3 는 3대에서도 유지된다.** W0 와 갈라지는 지점 (브리프 5.2). 이 오버헤드가 정당화되는 순간 |
| 메트릭 | `coupon_issue_total{result="LOCK_TIMEOUT"}`, `redis_commands_processed_total`, `hikaricp_connections_active` (W1 과 대조) |

### 거절 경로도 락을 잡는다

W1 과 같다. 재고 소진 뒤의 요청도 락을 잡은 다음에야 "품절"을 판정한다. 소진 후 50,000건이 3.7회씩 Redis 를 두드린다. 효율만 보면 락 없이 판정하는 편이 낫지만, 그러면 전략마다 코드 경로가 달라져 비교가 깨진다 (브리프 5.4).
