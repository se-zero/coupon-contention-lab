# 캐시 기초 — Cache-Aside / Write-Through / Write-Back

> **한 줄 정의:** 캐시는 원본보다 가까운 곳에 둔 **사본**이다. 읽기를 싸게 만드는 대신, 같은 사실이 두 곳에 있게 되고 **그 둘이 언제 얼마나 어긋나도 되는지**를 설계로 정해야 한다.

---

## 1. 왜 필요한가

지금의 조회 경로(C0)는 이렇다.

```java
@Transactional(readOnly = true)
public Optional<CouponResponse> findById(long couponId) {
    return couponRepository.findById(couponId).map(CouponResponse::from);
}
```

PK 조회 한 번이다. 이 읽기 **자체**는 싸다 — 실험 A 의 soak 30분 내내 PostgreSQL 버퍼 캐시 히트율이 **1.00** 이었고([`results/week3-soak-followup/summary.md`](../results/week3-soak-followup/summary.md) 2장) 실험 B 도 같은 테이블을 읽는다. 디스크까지 가지 않는다.

그런데도 이 경로에는 두 가지 문제가 있다.

**1. 커넥션은 읽기와 쓰기가 같은 예산을 나눠 쓴다.** D-01 의 30 은 총량이다. 조회가 30 을 물고 있으면 발급이 쓸 것이 없다. 200명이 동시에 상세 페이지를 열면 30 만 DB 에 들어가고 나머지는 풀 앞에 줄을 선다. **조회가 빠른 것과 조회가 자원을 안 쓰는 것은 다른 말이다.**

**2. 거의 변하지 않는 값을 매번 묻는다.** 응답 7개 필드 중 이벤트 도중 변하는 것은 `issuedCount` 와 `remaining` 둘뿐이고 나머지(이름·총수량·기간)는 고정이다. 그리고 **조회는 발급보다 훨씬 많다** — 받는 사람은 한 번 받지만 보는 사람은 계속 본다.

캐시는 이 왕복을 Redis 메모리 조회로 바꾼다. 여기서 관점을 하나 정해 두면 이후가 전부 따라온다.

> **캐시는 빠르게 하는 장치이기 전에 원본을 보호하는 장치다.**
> 실험 B 의 핵심 지표가 응답 시간이 아니라 **DB QPS 의 피크값**인 것이 그래서다 (브리프 6장).

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **히트 / 미스** | 캐시에 값이 있었는가. 미스는 "조금 느린 히트" 가 아니라 **원본에 일이 생기는 사건**이다 — 이 구분이 실험 B 전체의 주제다 |
| **TTL** (Time To Live) | 사본의 유효 기간. 만료되면 캐시에서 사라진다. **TTL 은 허용하는 낡음의 상한**이지 "갱신 주기" 가 아니다 |
| **Cache-Aside** (look-aside) | 애플리케이션이 캐시를 직접 다룬다 — 없으면 원본에서 읽어 **자기가** 넣는다. 가장 흔하고, 이 프로젝트가 쓰는 방식 |
| **Read-Through / Write-Through / Write-Back** | 캐시 계층이 원본 접근을 대신해 주는 방식들. 읽기를 대신하면 Read-Through, 쓰기를 즉시 원본까지 전달하면 Write-Through, 나중에 모아 쓰면 Write-Back |
| **stale** (낡은 값) | 원본은 바뀌었는데 사본은 아직 옛 값인 상태. 캐시를 붙인 이상 **없앨 수 없고 상한만 정할 수 있다** |

> Write-Back 은 낯선 이름이지만 이 프로젝트에 이미 있다. **W4 가 정확히 Write-Back 이다** — Redis 에서 판정하고 201 을 준 뒤 워커가 DB 에 모아 쓴다 ([`redis-atomic.md`](redis-atomic.md) 3-4). 쓰기 경로에서 그 대가(반영 지연 39분, 장애 시 유실 45,868건)를 이미 측정했다. 실험 B 는 같은 구조를 **읽기 경로**에서 본다.

## 3. 동작 원리

### 3-1. Cache-Aside 읽기 — 네 단계

```
요청 ──▶ ① 캐시 조회 ──[히트]──▶ 그대로 응답                        (DB 접근 0)
             │
          [미스]
             ▼
         ② DB 조회 ──▶ ③ 캐시에 저장 (TTL 60초) ──▶ ④ 응답
```

핵심은 **③ 이 요청 경로 안에 있다**는 것이다. 미스를 만난 요청이 자기 시간으로 DB 를 읽고 자기 시간으로 캐시를 채운다. 그래서 미스는 그 요청 하나만 느려지게 하는 것이 아니라, **같은 키를 보는 다른 요청들이 채워지기를 기다리는 동안 무엇을 하는가**라는 문제를 만든다. 그것이 다음 문서([`cache-stampede.md`](cache-stampede.md))의 주제다.

### 3-2. 쓰기가 섞이면 — 세 가지 선택

| 방식 | 쓰기가 하는 일 | 캐시가 낡는 구간 | 대가 |
|---|---|---|---|
| **무효화** (invalidate) | 원본에 쓰고 캐시 키를 **지운다** | 거의 없다 | 지운 직후가 곧 미스 — 인기 키면 스탬피드를 **직접 만든다** |
| **Write-Through** | 원본에 쓰고 캐시도 **같이 갱신** | 없다 | 쓰기가 두 시스템을 기다린다. 둘 중 하나만 성공하는 틈이 남는다 |
| **Write-Back** | 캐시에만 쓰고 원본은 **나중에** | 원본이 낡는다 (반대 방향) | 가장 빠르고 가장 위험하다 — 반영 전 장애는 유실이다 (W4) |

**이 프로젝트는 읽기 경로만 바꾸고 쓰기 경로는 건드리지 않는다.** 실험 B 의 부하에 발급 요청이 없기 때문이다 (D-12 — 쓰기 전략은 W0 로 고정하되 호출되지 않는다). 이유는 변수 통제다. 쓰기를 섞으면 DB QPS 피크가 **TTL 만료 때문인지 무효화 때문인지** 분리되지 않고, 그 순간 실험 B 는 브리프 6장이 노리는 그림을 못 그린다.

> 대신 리포트에는 적어야 한다 — **실무의 스탬피드는 만료보다 무효화에서 더 자주 온다.** 이 실험이 재는 것은 그중 만료 쪽 하나다.

### 3-3. 사본이 들고 있는 값 하나는 계속 변한다

```java
public record CouponResponse(
        Long id, String name, int totalQuantity,   // 이벤트 내내 고정
        int issuedCount, int remaining,            // ← 발급마다 변한다
        LocalDateTime startAt, LocalDateTime endAt) { }
```

TTL 60초로 캐시한다는 것은 **"남은 수량이 최대 60초 낡을 수 있다"** 는 뜻이다. 초당 290건이 나가는 부하라면(2주차 W0 실측) 60초는 **17,400건**이다. 화면의 "남은 수량" 이 그만큼 틀릴 수 있다.

이것이 결함인지 명세인지는 **제품이 정한다.** 재고 표시가 목적이면 허용될 수 있고, "지금 누르면 받을 수 있다" 의 근거로 쓰면 안 된다. 어느 쪽이든 **판정은 발급 API 가 다시 한다** — 조회가 낡았다고 초과 발급이 생기지는 않는다. NFR-01 은 쓰기 경로가 지킨다.

> 8단계의 응답 동일성 테스트가 이 지점을 건드린다. C0~C4 는 같은 `CouponResponse` 를 줘야 하지만, **TTL 안에서 stale 이 나오는 것은 실패가 아니라 명세다.** 테스트가 그 둘을 구분해야 한다 (작업 규칙 8).

### 3-4. 미스는 히트보다 훨씬 비싸다 — 그래서 히트율이 아니라 미스의 절대량을 센다

| | 하는 일 | 커넥션 |
|---|---|---|
| 히트 | Redis 왕복 1회 + 역직렬화 | 0 |
| 미스 | Redis 왕복 + **DB 왕복** + 직렬화 + Redis 쓰기 | **1** |

히트율 99% 를 "DB 부하가 1/100" 으로 읽으면 틀린다. **DB 는 비율이 아니라 절대 건수와 동시성으로 아프다.** 총 10,000 QPS 의 1% 는 100 QPS 이고, 그 100 이 1초에 고르게 퍼져 있느냐 **한 순간에 몰려 있느냐**가 실험 B 의 질문이다.

그래서 8단계에서 만드는 메트릭은 히트율이 아니라 **`db_load` — 미스로 DB 를 실제로 읽은 횟수**다. Prometheus 스크레이프가 1초라 **초당 증가분이 그대로 "그 초의 DB QPS"** 가 된다.

## 4. 실무 설정 기준

| 설정 | 기준 |
|---|---|
| **TTL** | **허용하는 낡음에서 역산한다.** "얼마나 낡아도 되는가" 에 답하지 못하면 캐시를 붙일 준비가 안 된 것이다. 이 프로젝트의 **60초는 실험값** — 5분 부하에서 만료를 4~5회 보기 위한 값이지 서비스 권장값이 아니다 (D-12) |
| **키 이름** | `coupon:detail:{id}` 처럼 **용도:종류:식별자**. 응답 모양이 바뀌면 접두의 버전을 올려 통째로 갈아탄다 — 배포 중 옛 모양과 새 모양이 섞이는 것이 캐시 사고의 단골이다 |
| **저장 단위** | **응답 DTO 하나를 통째로.** 필드를 쪼개 저장하면 읽을 때 왕복이 늘고 부분 만료가 생긴다 |
| **값 크기** | 수 KB 이내. 큰 값은 Redis 의 단일 스레드를 직렬화·네트워크로 오래 점유한다 ([`redis-atomic.md`](redis-atomic.md) 3-6) |
| **eviction** | 캐시 전용 Redis 라면 `allkeys-lru` 가 맞다. **이 프로젝트는 `noeviction`** — 같은 Redis 가 W4 의 재고를 들고 있어 LRU 로 두면 재고 키가 지워질 수 있다 (redis-atomic 4장). 실험 B 는 키 20개 × 수백 바이트라 메모리가 문제되지 않는다 |
| **없는 키** | 존재하지 않는 id 를 반복 조회하면 매번 미스 → 매번 DB 다 (캐시 관통). 방어는 "없음" 자체를 짧은 TTL 로 캐시하는 것. **이 실험에는 해당 없다** — 실재하는 20개만 조회한다 (D-12). 해당 없음을 conditions 에 적는다 |
| **측정** | `hit` / `miss` / **`db_load`** 세 카운터. 앞의 둘만으로는 방어 기법의 효과가 안 보인다 — C3 는 **미스지만 DB 를 읽지 않는** 요청을 만들기 때문이다 |

### 반드시 구분할 세 숫자

1. **미스 수** — 캐시에 없었던 요청 수
2. **`db_load`** — 그중 실제로 DB 를 읽은 수
3. **피크 `db_load`** — 1초 안에 몰린 최대값 ← **실험 B 의 핵심 지표**

C1 은 1 = 2 다. C3 · C4 가 하는 일은 **1 은 그대로 두고 2 를 줄이는 것**이고, 셋을 따로 세지 않으면 그 차이가 그래프에 나타나지 않는다.

## 5. 트레이드오프

| 선택 | 얻는 것 | 잃는 것 | 언제 |
|---|---|---|---|
| **캐시 없음** (C0) | 항상 최신. 구조가 단순하다 | 모든 읽기가 커넥션 예산을 쓴다 | 읽기가 적거나 낡음을 1초도 허용 못 할 때 |
| **짧은 TTL** | 낡음이 작다 | 미스가 잦다 — 원본 부하가 높게 유지된다 | 값이 자주 변하고 정확도가 중요할 때 |
| **긴 TTL** | 미스가 드물다 | 낡음이 크다. **피크 크기는 줄지 않는다** (다음 문서 5장) | 값이 거의 안 변할 때 |
| **Write-Through** | 읽기가 항상 최신 | 쓰기가 느려지고 두 시스템에 걸린다 | 쓰기가 드물고 읽기가 많을 때 |
| **Write-Back** | 쓰기가 가장 빠르다 | 반영 전 장애는 유실 | 유실을 감수할 수 있을 때. W4 가 그 대가를 실측했다 |

### 캐시는 지연을 줄이는 게 아니라 **갈라놓는다**

히트와 미스는 비용이 자릿수로 다르다. 평균 응답 시간은 내려가지만 **분포는 둘로 쪼개진다.** 히트율 99% 면 상위 1% 의 요청이 미스이고, 그들이 그대로 P99 를 만든다. 캐시를 붙인 뒤 "평균은 좋아졌는데 P99 는 그대로" 인 것은 고장이 아니라 **캐시의 정의**다.

여기에 한 줄이 더 붙는다 — 미스가 **동시에** 오면 그 1% 는 서로 줄까지 서게 되어 P99 가 좋아지기는커녕 나빠진다. 그것이 스탬피드다.

## 6. 흔한 오해 · 안티패턴

| 오해 · 안티패턴 | 실제 |
|---|---|
| "히트율 99% 면 DB 부하가 1/100" | DB 는 비율이 아니라 **절대 건수와 동시성**으로 아프다. 10,000 QPS 의 1% 는 100 QPS 이고, 그것이 한 순간에 몰리면 동시 요청 100개다 |
| "캐시는 빠르게 하려고 붙인다" | 먼저 **원본을 보호**하려고 붙인다. 실험 B 의 핵심 지표가 응답 시간이 아니라 DB QPS 피크인 이유다 |
| "TTL 은 길수록 좋다" | 만료 **빈도**만 줄고 **피크 크기는 그대로**다. 낡음만 커진다 |
| "`@Cacheable` 을 붙이면 끝" | 키마다 다른 TTL(C2)과 **남은 TTL 읽기**(C4)를 표현할 수 없다. D-11 이 Redisson 을 직접 쓰는 이유다 |
| "로컬 캐시(Caffeine)면 Redis 가 필요 없다" | 인스턴스마다 **자기 사본과 자기 시계**를 갖는다. 3대면 같은 키를 3번 읽고 만료도 3번 따로 온다. 실험 B 를 단일 인스턴스로 고정한 이유(3.4)와 같은 문제다 |
| "읽기는 가벼우니 커넥션은 신경 안 써도 된다" | 읽기든 쓰기든 커넥션은 하나다. D-01 의 30 은 **공유 예산**이고, 200 VU 가 동시에 미스하면 대부분이 풀 앞에 줄을 선다 |
| 미스가 나면 "일단 DB 에서 읽고 보자" | 한 명이 읽을 일을 **같은 키를 보던 전원이** 읽는다. 다음 문서의 주제이자 C3 가 푸는 문제다 |
| 캐시 장애 시 원본으로 자동 우회 | 안전해 보이지만, 캐시가 죽는 순간 **평소에 캐시가 막아 주던 부하 전부**가 DB 로 간다. 우회는 원본이 그 부하를 견딜 때만 안전하다 |

## 7. 이 프로젝트에서

### 비교군에서의 위치 (브리프 6장)

| | 전략 | 이 문서가 다루는가 |
|---|---|---|
| **C0** | 캐시 없음 — 매 요청 DB 조회 | ✔ 기준선 |
| **C1** | Cache-Aside + 고정 TTL 60초 | ✔ 이 문서의 Cache-Aside 그대로 |
| C2 | TTL 지터 | [`cache-stampede.md`](cache-stampede.md) · 방어 문서(9단계) |
| C3 | 뮤텍스 / 단일 재계산 | 〃 |
| C4 | 확률적 조기 갱신 (XFetch) | 〃 |

**C0 와 C1 의 차이는 "캐시를 붙였는가" 하나뿐이고, C1~C4 의 차이는 "만료를 어떻게 다루는가" 뿐이다.** 쓰기 경로에서 지킨 공정성 규칙(브리프 5.4)을 읽기 경로에도 그대로 적용한다.

### 8단계에서 만드는 것

| | |
|---|---|
| `CouponReadStrategy` | C0~C4 가 같은 인터페이스를 구현하고 `COUPON_CACHE` 설정값으로 고른다. 쓰기의 `CouponIssueStrategy` 와 같은 방식 |
| 캐시 클라이언트 | **Redisson `RBucket`** (D-11). W3·W4 가 쓰는 클라이언트를 그대로 쓴다 — 클라이언트가 둘이 되면 C0~C4 의 차이가 전략 차이인지 클라이언트 차이인지 분리되지 않는다 |
| 메트릭 | `coupon.cache` (`result` 라벨 hit/miss)와 **`coupon.cache.db_load`**. 전 비교군이 같은 카운터를 낸다 — C0 는 전부 `db_load` 다 |
| 교차 확인 | `pg_stat_statements` 의 해당 SELECT `calls` 증가분과 `db_load` 가 맞는지 본다. 앱이 센 수와 DB 가 센 수가 다르면 계측을 먼저 고친다 |
