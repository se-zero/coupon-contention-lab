# TTL 과 캐시 스탬피드

> **한 줄 정의:** 캐시가 비는 순간 그 키를 보던 요청들이 **한꺼번에** 원본으로 몰려가는 현상. 캐시가 고장나서가 아니라 **TTL 이 정확해서** 생긴다.

---

## 1. 왜 필요한가

[`cache-basics.md`](cache-basics.md) 의 Cache-Aside 를 그대로 구현하면 C1 이 된다. 히트율은 99% 를 넘고, DB 조회는 거의 사라지고, 평균 응답 시간은 내려간다. **평균만 보면 완벽하다.**

그런데 DB 쪽 그래프를 1초 해상도로 그리면 이렇게 생겼다.

```
 db_load (초당 DB 조회)
     │
 200 ┤  ▲              ▲              ▲              ▲
     │  │              │              │              │
 100 ┤  │              │              │              │
     │  │              │              │              │
   0 ┼──┴──────────────┴──────────────┴──────────────┴──────▶ 시간
     0             60초           120초           180초
```

59초 동안 0 이다가 1초 동안 몰린다. **5분 평균으로는 초당 3 회지만, 실제로 DB 가 만나는 것은 200 이 동시에 오는 순간**이다. 원본이 죽는 것은 평균 때문이 아니라 이 순간 때문이다.

그리고 이 그림에는 더 나쁜 버전이 있다. 몰린 요청 때문에 DB 가 느려지면 → 값을 채우는 데 더 오래 걸리고 → 그 사이 도착한 요청이 전부 또 미스가 되고 → 더 몰린다. 원본이 한 번 밀리면 **캐시가 있어도 회복하지 못하는** 구간이 생긴다.

실험 B 의 질문은 그래서 "캐시를 붙일까" 가 아니라 **"이 톱니를 없앨 수 있는가, 없앨 때 무엇을 지불하는가"** 다 (브리프 2장 4·5번).

## 2. 핵심 개념

| 용어 | 의미 |
|---|---|
| **스탬피드** (stampede · dog-pile · thundering herd) | 하나면 될 일을 **N 개가 동시에** 하는 현상. 캐시에서는 "하나의 미스" 가 "N 개의 DB 조회" 가 되는 것 |
| **미스 창** (d) | 캐시가 빈 순간부터 누군가 채워 넣을 때까지의 시간. **이 창 안에 도착한 요청은 전부 미스**다. 길이는 DB 왕복 + 직렬화 + Redis 쓰기 |
| **동시 만료** | 여러 키가 **같은 시각에** 만료되는 것. 같은 시각에 넣었으면 같은 시각에 나간다 |
| **동시 미스** | 키 **하나**에 독자가 많아 미스 창 안에 여러 요청이 겹치는 것. 키가 하나뿐이어도 일어난다 |
| **캐시 관통** (penetration) | 원본에도 없는 값을 반복 조회해 매번 미스가 되는 것. 만료와 무관한 별개 문제 — 이 실험에는 해당 없다 |

> **스탬피드의 두 얼굴을 구분하는 것이 이 문서의 목적이다.** 둘은 원인이 다르고, 그래서 **푸는 도구가 다르다.** 이 구분을 못 하면 지터(C2)를 넣어 놓고 왜 효과가 없는지 모르게 된다.

## 3. 동작 원리

### 3-1. 미스 창 — 한 명이 채우는 동안 도착한 전원이 미스다

```
시각   t0        t0+1ms    t0+2ms    t0+3ms                t0+d
       │          │         │         │                     │
만료 ──┤          │         │         │                     │
       ▼          ▼         ▼         ▼                     ▼
      요청A     요청B     요청C     요청D  ...             요청A 완료 → 캐시 채움
      미스!     미스!     미스!     미스!                   이후 도착분은 히트
       │          │         │         │
       └── DB ────┴── DB ───┴── DB ───┴── DB   ← 전부 같은 값을 읽으러 간다
```

**요청 A 가 DB 를 다녀오는 d 동안, 캐시는 여전히 비어 있다.** B·C·D 는 A 가 이미 읽으러 갔다는 사실을 알 방법이 없다. Cache-Aside 에는 "누가 채우는 중" 이라는 상태가 없기 때문이다 (cache-basics 3-1).

동시 미스의 개수는 이렇게 정해진다.

```
동시 미스 ≈ 그 키의 도착률 × 미스 창 d
```

d 가 5ms 이고 그 키에 초당 2,000건이 오면 **10건**이 겹친다. d 가 길어지면(=DB 가 느려지면) 비례해서 늘어난다. 1장에서 말한 악순환이 이 식에 들어 있다.

### 3-2. 왜 하필 다 같이 만료되는가

```
워밍업:  t=0    키1..키20 을 전부 캐시에 넣는다 (TTL 60초)
          ↓
만료:    t=60   키1..키20 이 전부 동시에 사라진다
```

**같은 시각에 넣었으면 같은 시각에 나간다.** TTL 은 절대 시각이 아니라 "넣은 때 + 60초" 이므로, 넣는 시점이 뭉쳐 있으면 만료도 뭉친다.

실무에서 이것이 뭉치는 순간은 정해져 있다.

| 상황 | 왜 뭉치는가 |
|---|---|
| **배포 / 재시작 직후** | 캐시가 비어 있어 초반 트래픽이 한꺼번에 채운다 → 정확히 TTL 뒤에 한꺼번에 만료 |
| **캐시 서버 교체·flush** | 위와 같다 |
| **이벤트 오픈** | 트래픽이 한 시점에 몰려 들어오며 동시에 채운다 |
| **배치가 캐시를 미리 채움** | 워밍업의 의도가 정확히 동시 만료를 만든다 |

> 이 실험의 워밍업(전 키 1회 조회 → TTL 시계 시작)은 **일부러 최악을 만든다.** C1 이 재는 것은 "평균적인 서비스" 가 아니라 **동시 만료가 완전히 정렬된 상태**다. 7장에 한계로 적는다.

### 3-3. 두 얼굴 — 원인이 다르면 약도 다르다

| | **동시 만료** | **동시 미스** |
|---|---|---|
| 무엇이 겹치는가 | 여러 **키**의 만료 시각 | 한 **키**에 붙은 여러 요청 |
| 키가 1개면 | 일어나지 않는다 | 그대로 일어난다 |
| 키가 10,000개면 | 심해진다 | 키당 독자가 적어 거의 없다 |
| 푸는 도구 | **C2 지터** — 만료 시각을 흩뿌린다 | **C3 뮤텍스** — 한 명만 보낸다 |
| C2 로 풀리나 | ✔ | ✘ (키 하나 안에서는 흩뿌릴 것이 없다) |
| C3 로 풀리나 | 부분적 (키 수만큼은 여전히 간다) | ✔ |

**이 표가 D-12 의 키 수를 정한 근거다.** 키 20개 · 200 VU 면 키당 독자 10명이라 **두 얼굴이 동시에 관측된다.** 키가 1개면 C2 가 할 일이 없고, 1,000개면 키당 독자 0.2명이라 C3 가 막을 것이 없다. 어느 쪽이든 비교군 다섯 중 하나가 아무 일도 하지 않는 실험이 된다.

### 3-4. 피크의 크기는 TTL 과 무관하다

```
TTL 30초,  5분 부하 →  파동 10회,  파동당 피크 200
TTL 60초,  5분 부하 →  파동  5회,  파동당 피크 200   ← 이 프로젝트
TTL 300초, 5분 부하 →  파동  1회,  파동당 피크 200
```

TTL 을 늘리면 **빈도가 줄 뿐 한 번의 크기는 그대로**다. 원본이 못 견디는 것은 크기 쪽이므로, **TTL 조정은 스탬피드의 해법이 아니다.** 낡음만 커지고 문제는 남는다.

이것이 C2·C3·C4 가 따로 필요한 이유다 — 셋 다 빈도가 아니라 **한 번의 크기**를 건드린다.

### 3-5. 히트율은 이 현상을 보여주지 못한다

예상되는 C1 의 숫자로 계산해 보면 (7장의 예상 표),

```
5분 부하 전체 요청 수      : 수십만 ~ 백만 건
미스 수 (5 파동 × 최대 200): 1,000 건 안팎
히트율                     : 99.8% 이상
```

**히트율 99.8% 와 "DB 가 순간적으로 200 건을 맞는다" 는 같은 실행의 두 얼굴이다.** 히트율만 보고하면 C1 은 완벽한 전략으로 보이고, C2~C4 와도 구분되지 않는다 (전부 99% 대).

그래서 이 실험이 보는 것은 **1초 해상도의 `db_load` 피크**다. 이 지표가 아니면 브리프 6장이 노리는 그림이 나오지 않는다.

## 4. 무엇을 재야 "봤다" 고 할 수 있는가

이 문서는 현상과 **진단**까지 다룬다. 처방(C2·C3·C4)은 9단계의 `docs/cache-stampede-defense.md` 로 넘긴다. 그래서 4장은 설정값 대신 **계측 요건**이다.

| 요건 | 기준 | 근거 |
|---|---|---|
| **1초 해상도** | Prometheus 스크레이프 1초 (이미 그렇다) | 15초 스크레이프면 200건 피크가 **초당 13** 으로 뭉개져 톱니가 사라진다. 이 실험은 스크레이프 간격이 결과를 지우는 종류의 실험이다 |
| **`db_load` 를 미스와 따로 센다** | 카운터 2개 | C3·C4 는 **미스지만 DB 를 안 읽는** 요청을 만든다. 하나로 세면 그 차이가 사라진다 (cache-basics 4장) |
| **미스 요청의 응답 시간을 따로 잰다** | 미스 전용 타이머 | **전체 P99 로는 C3 의 대가가 안 보인다** — 미스가 전체의 1% 미만이면 P99 는 히트가 정한다 (7장) |
| **DB 쪽에서 교차 확인** | `pg_stat_statements` 의 해당 SELECT `calls` | 앱이 센 `db_load` 와 DB 가 센 호출 수가 다르면 계측을 먼저 고친다. 2주차의 `app_5xx` 처럼 **기록만의 버그**가 결론을 바꿀 수 있다 |
| **피크 / 평균 비** | 파고율 = 피크 `db_load` ÷ 평균 `db_load` | C1 은 크고 C4 는 1 에 가깝다. 방어 효과를 한 숫자로 요약할 때 쓴다 |

> 키별 라벨(`key="coupon:detail:101"`)을 붙이면 두 얼굴을 직접 나눠 볼 수 있다. 키가 20개라 카디널리티도 문제없다. 다만 필수는 아니므로 **8단계에서 판단한다.**

## 5. 트레이드오프

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| **TTL 을 늘린다** | 파동 횟수가 준다 | 낡음이 커진다. **피크 크기는 그대로** (3-4) |
| **TTL 을 줄인다** | 낡음이 작다 | 파동이 잦아지고 평균 DB 부하가 는다. 피크는 역시 그대로 |
| **캐시를 아예 안 쓴다** (C0) | 피크가 없다 — 항상 최대 부하다 | 평상시에도 DB 가 전부 받는다. 톱니가 없는 대신 **선 전체가 높다** |
| **워밍업을 한다** | 첫 요청이 느리지 않다 | **동시 만료를 만든다** (3-2). 의도와 반대 결과가 될 수 있다 |

### C0 와 C1 은 "좋고 나쁨" 이 아니라 **모양이 다르다**

```
C0:  ████████████████████████████████  ← 항상 높다 (피크 = 평균)
C1:  ▁▁▁▁█▁▁▁▁▁▁▁▁█▁▁▁▁▁▁▁▁█▁▁▁▁▁▁▁  ← 대부분 0, 가끔 뾰족하다
```

총 DB 조회 수는 C1 이 압도적으로 적다. 그런데 **DB 가 감당해야 하는 순간 최대치는 둘 다 존재**하고, C1 의 피크가 C0 의 평상시보다 높을 수도 있다. "캐시를 붙였으니 DB 는 안심" 이 성립하지 않는 지점이 여기다.

그래서 캐시를 붙이고도 **커넥션 풀을 줄이면 안 된다.** 풀이 30 인데 동시 미스가 50 이면 나머지 20 은 풀 앞에 줄을 서고, 줄을 서는 동안 미스 창 d 가 길어져 동시 미스가 더 늘어난다 (3-1 의 식).

## 6. 흔한 오해 · 안티패턴

| 오해 · 안티패턴 | 실제 |
|---|---|
| "히트율이 99% 면 스탬피드는 없다" | 히트율 99.8% 와 순간 200건 피크는 **같은 실행의 두 얼굴**이다 (3-5) |
| "TTL 을 늘리면 해결된다" | 빈도만 준다. 한 번의 크기는 같다 (3-4) |
| "평균 DB QPS 를 보면 된다" | 5분 평균 초당 3 회, 실제 피크 200. 평균은 이 현상을 **정의상** 감춘다 |
| "캐시를 미리 채워 두면 안전하다" | 워밍업은 만료 시각을 **정렬시킨다.** 안전해지는 것은 첫 요청뿐이고 60초 뒤에 전부 함께 터진다 |
| "미스는 그냥 한 번 느린 요청" | 동시에 오면 원본을 넘어뜨린다. **미스는 지연 문제가 아니라 부하 문제**다 |
| "랜덤 TTL 이면 다 해결된다" | **동시 만료만** 푼다. 키 하나에 독자가 몰린 동시 미스는 그대로다 (3-3) |
| "캐시가 있으니 커넥션 풀은 작아도 된다" | 풀이 필요한 순간이 바로 피크다. 풀 < 동시 미스면 미스 창이 길어져 **동시 미스가 더 늘어난다** |
| "캐시가 죽으면 DB 로 우회하면 된다" | 평소 캐시가 막아 주던 부하 **전부**가 한 번에 간다. 스탬피드의 가장 큰 버전이다 |

## 7. 이 프로젝트에서

### C1 이 이 현상을 만든다

| | |
|---|---|
| 구현 | Cache-Aside + **모든 키 동일 TTL 60초** (브리프 6장) |
| 워밍업 | 전 키를 1회 조회해 캐시를 채운다 — 여기서 **TTL 시계가 동시에 시작**된다 |
| 부하 | 200 VU constant, 5분 (D-12) |
| 기대 | 60초 간격 톱니 4~5개. **이것이 스탬피드 재현이자 8단계의 스모크 기준**이다 |

### 예상 (검증 대상)

W0 의 붕괴를 미리 적고 실측과 대조했듯이(`plan/week3.md` 1장), 여기서도 먼저 적는다.

키당 동시 독자는 200 VU ÷ 20 키 = **10명**이고, k6 는 닫힌 루프(요청을 보내고 응답을 기다린 뒤 다음 요청)이므로 **키 하나의 동시 미스는 10 을 넘을 수 없다.**

| | `db_load` 의 모양 | 파동당 피크 (예상) |
|---|---|---|
| **C0** | 평평하고 높다. 전 요청이 DB | 피크 = 평균 = 처리량 전체 |
| **C1** | 60초마다 뾰족하고 사이는 0 | **20키 × 최대 10 = 최대 200** |
| **C2** (지터 ±J) | 톱니가 2J 폭으로 퍼진다 | 200 ÷ 2J 초 — J=10초면 초당 10 안팎 |
| **C3** (뮤텍스) | 파동은 남고 높이가 낮아진다 | **20** (키당 1) · 나머지 180 은 대기 |
| **C4** (조기 갱신) | 피크가 사라지고 낮게 깔린다 | 뚜렷한 파동 없음 |

**히트율은 다섯 전략 모두 99% 대일 것**이고, 그 숫자로는 아무것도 구분되지 않는다 (3-5). 구분되는 것은 위 표의 피크값 하나다.

> 부수 소득 하나 — 실측 동시 미스를 키당 독자 10 과 비교하면 **미스 창 d 를 역산**할 수 있다. 10 에 가까우면 d 가 요청 간격보다 충분히 길다는 뜻이고, 3~4 에 그치면 d 가 그만큼 짧다는 뜻이다.

### 계측 설계에서 바로잡아야 할 것 — 전체 P99 로는 C3 의 대가가 안 보인다

브리프 6장은 C3 의 관찰 포인트를 "대기 요청의 P99 악화 여부" 로, 측정 항목을 "락 대기로 인해 오히려 늘어난 응답 시간" 으로 적었다. 위 예상대로라면 **미스는 전체 요청의 1% 에도 못 미친다.** 그러면 전체 P99 는 여전히 히트가 정하고, C3 가 만든 대기는 P99.9 뒤에 숨는다.

그래서 8단계에 **미스 전용 타이머**를 넣는다.

| 메트릭 | 재는 것 |
|---|---|
| `coupon.cache.load` | 미스 후 **DB 를 읽은** 요청의 소요 시간 |
| `coupon.cache.wait` | 미스 후 **남이 채우기를 기다린** 요청의 대기 시간 (C3 전용) |
| `coupon.cache.wait.timeout` | 대기 상한 2초에 걸린 건수 (D-13) |

C3 의 비용은 전체 P99 가 아니라 **이 두 분포**로 보고한다. 전체 P99 도 함께 기록하되, **"전체 P99 는 거의 안 변했다" 자체가 결과**다 — 방어의 비용이 소수의 요청에 집중된다는 뜻이기 때문이다.

### 확정값

| 항목 | 값 | 근거 |
|---|---|---|
| 키 수 · 부하 | 쿠폰 20종 · 200 VU · 5분 · TTL 60초 | **D-12** — 3-3 의 두 얼굴이 둘 다 관측되는 지점 |
| C3 대기 정책 | **대기, 상한 2초** | **D-13** — stale 즉시 반환은 위의 관측 포인트를 0 으로 만든다 |
| 인스턴스 | 1 | 브리프 3.4 |

### 이 실험이 재지 못하는 것 (한계)

1. **동시 만료가 인위적으로 정렬돼 있다.** 워밍업이 전 키의 TTL 시계를 같은 순간에 시작한다. 실제 서비스는 키가 시간에 걸쳐 채워져 **자연 지터**가 있으므로, C1 의 피크는 최악값이고 C2 의 개선 폭은 실제보다 크게 보일 수 있다.
2. **닫힌 루프라 동시 미스에 상한이 있다.** 키당 10 을 넘지 못하므로 1장의 악순환(느려질수록 더 몰림)은 재현되지 않는다. 열린 부하였다면 d 가 길어질수록 동시 미스가 늘어난다.
3. **무효화 스탬피드는 보지 않는다.** 실무에서 더 흔한 쪽이지만, 쓰기를 섞으면 피크의 원인이 분리되지 않는다 (cache-basics 3-2).
4. 2주차 한계 1·2·4(로컬 환경, k6 동거, 무제한 컨테이너)는 그대로다.

### 측정값 — 톱니는 정확히 그 모양으로 왔다

**측정값:** 3주차 실험 B, C1 3회 ([`results/week3-experiment-b/summary.md`](../results/week3-experiment-b/summary.md) 2장).

| | 예상 | 실측 |
|---|---|---|
| 파동 | 60초 간격 5개 | **15개 전부 60초 간격**(98 · 158 · 218 · 278 · 338초), 사이의 모든 초는 **정확히 0** |
| 파동당 피크 | 최대 200 (키 20 × 독자 10) | **102 ± 23** — 파동 평균 81, **키당 4.1개** 겹침 |
| 히트율 | 99% 대라 변별력 없음 | **99.98%** — 다섯 전략 전부 99.96~99.99% |
| 파동 중 DB 읽기 | 미스 창 ≈ 8.6ms (역산) | **10~31ms** — 80~100건이 커넥션 30개에 줄을 선다. 역산값은 겹침 수의 상한을 잘못 짚었다 |

"키당 10 을 넘을 수 없다" 는 상한은 맞았지만 실제 겹침은 그 절반이었다. 요청이 겹치는 정도를 정하는 것은 VU 수가 아니라 **한 명이 캐시를 채우는 데 걸리는 시간**이고, 파동 중에는 그 시간이 풀 대기로 길어지는데도 4개에 그친 것은 닫힌 루프의 VU 가 다른 키에서 줄을 서느라 이 키에 못 오기 때문이다 — 동기화된 파동이 스스로를 조절한다. 이 해석은 C2 에서 뒤집힌 방향으로 다시 나타난다 (방어 문서 7장).

계측 설계에서 바로잡은 것도 확인됐다. **C3 의 대기 734건(평균 60ms)은 전체 P99 에 나타나지 않았다** (90.8 vs C1 87.5). 미스 전용 타이머가 없었으면 그 비용은 어디에도 기록되지 않았다.
